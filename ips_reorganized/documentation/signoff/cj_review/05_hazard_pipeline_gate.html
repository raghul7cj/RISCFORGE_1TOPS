What this document is, and what it is not

What it is

A single entry point for the hazard-unit and pipeline benches: what they check, the evidence a bounded development campaign produced, and one core defect that campaign found.

What it is not

Not a technical sign-off, not a coverage closure, and not a decision on the interrupt and MDU policy. No RTL was changed.

How to read a claim

Contract, as-coded behavior, independent expectation and observed evidence stay separate. A quiet log is not a pass, and a registered finding is not reported as a pass.

Two benches, one new gate. The unit bench drives the combinational hazard unit with generated vectors against a reference model. The pipeline bench runs the production core with the real multiplier/divider and configurable memory waits, and checks retirement order, retired values, CSR effects and memory effects against an independent interpreter. Both are new in this workspace and are not yet upstreamed.

The unit and the pipeline under test

The hazard unit is combinational and produces the forwarding selects and the stall and flush strobes for each pipeline register. Its flush outputs are where this gate found a defect: the flush that should remove a trap-squashed instruction does not reach the two pipeline transfers that carry that instruction forward.

Why the retirement token is read from the core. A memory wait holds the MEM/WB packet, so an expression derived from valid_W alone reports a new retirement on every cycle of the wait. The pipeline probe therefore reads the core's own token, and the checker keeps an independent repeated-retirement guard. The historical expression is kept as a negative control and must be rejected. This was a testbench contract error that re-created the bug upstream issue #16 fixed in the RTL; no RTL was changed to obtain a pass.

Each run checks the retirement order and payload against the reference, the operand values of the executed instructions, the CSR write order and value, and the memory effects. A run must also reach its completion checkpoint, and the environment fails the run if a user hook does not report completion, so a quiet log is never treated as a pass.

Negative controls

A checker that cannot fail proves nothing. Fifteen runs inject a fault and must be rejected: twelve mutate one output bit of the hazard unit, one restore the historical retirement probe, one inject a checker observation and one corrupt a retired value. All fifteen were rejected as expected. They are 15 of the 44 self-proof candidates; the rest are not built.

Interrupt during a busy MDU: characterized, policy open

The interrupt case is characterization, not a checked requirement, because the expected policy is not decided. Measured behavior: the MDU holds the pipeline for 34 cycles with the EX stage empty, the interrupt request stays pending, and it is accepted in EX only after the MDU releases. The RTL carries an abort path, div_abort_internal = wb_redirect_i | (irq_accept_E & stallMUL) at execute_cycle.v:299, but irq_accept_E requires valid_E and a busy MDU leaves EX empty, so that term is not reachable in this configuration. The run reports irq_accepted_while_busy=0 and abort_while_busy=0 and stays open. Upstream issue #26 asks for the same defer-versus-abort decision.

Open defect HZ-F001: a squashed store reaches memory

Contract. An instruction squashed by a trap must have no architectural side effect. Data memory is architectural state.

As coded. A store younger than a taken ECALL is offered to the memory interface although the instruction never retires. At a memory wait of zero, the write becomes visible in data memory.

Mechanism

The ECALL exception is generated in decode (decode_cycle.v:418) and is carried through EX and MEM; the trap commits in WB (wb_trap_mret_commit_controller.v:64). Two transfers are not gated by the flush that should remove the younger instruction.

  1. FlushD is applied in the fetch stage only. decode_cycle.v has no FlushD input and latches valid_E_r <= valid_D; at line 367 in its normal branch, so the store in D advances into EX.
  2. FlushE clears the whole ID/EX register at decode_cycle.v:276, but execute_cycle.v latches valid_M_r <= valid_E1; at line 467 in its normal branch. The EX/MEM transfer is gated by FlushM and StallM only, so the store reaches MEM and issues its request.

The store is never retired: the reference retirement sequence contains no 0x8000_001c, and the trap's FlushW clears the MEM/WB packet. The trap itself is correct; retirement order, retired values, trap cause and handler resume all match the reference for all 14 instructions.

Scope, and what the fix must not break

  • The vulnerable window is a store that is in MEM in the cycle the trap commits in WB. A store still in EX at that moment is already killed by FlushM.
  • Traps detected inside memory_cycle.v, such as a misaligned access, are raised there and are not visible to the hazard unit's exc_inflight_M. They are not covered by the flushes above and need a separate gate. This path was read but not reproduced.
  • Gating the EX/MEM transfer on FlushE is unsafe: FlushE is also asserted by the load-use and CSR stalls, by PCSrcE and by stallMUL, so clearing EX/MEM on it would drop the load of a load-use stall, the link write of a taken branch, CSR results and the MDU instruction.
  • A trap-specific squash signal, plus a MEM-side gate on the request, is the direction the upstream issue records.
Disposition: open. Tracked upstream as issue #30, label bug, with a correction comment recording an independent review. The review confirmed the defect and corrected several statements in the first version of the issue: the exception is generated in D rather than detected in EX; FlushE clears the whole ID/EX register; the two detections are checks in one checker, not independent sources; the write is suppressed by the memory model at a non-zero wait while the core still offers the request; and raw FlushE is not a safe gate. The issue body and its addendum hold the corrected record. No RTL was changed.

Limits

  
The campaign runs on a development simulator. It does not claim sign-off, does not close the proposed pipeline candidate matrix, and does not close the interrupt and MDU policy item. The pipeline bench observes the core through a hierarchy probe; it does not prove the behaviour of a specific bus protocol or of a memory that commits on write-enable. The defect was found by this bench and not fixed; the RTL at the cited source identity is unchanged. The bench files are local to this workspace and are not part of the upstream repository, so the reproducer is not yet runnable from a fresh clone.

Learning checkpoint

  
Before the fix, predict the checker. What does the checker report at MEM_WAIT=5 if the EX/MEM transfer is gated on a trap-specific signal? The offer should disappear, ghosts should fall to zero, and effects should fall from 2 to 1, because the checkpoint write at 0x8000_13fc is the only remaining memory effect. If the offer still appears, the D-to-E transfer is also carrying the store and the second gate is needed as well. That distinction is what separates a complete fix from a partial one.
