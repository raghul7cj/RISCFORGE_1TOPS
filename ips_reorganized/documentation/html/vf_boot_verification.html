Boot Verification

How Rev B section 12 plans to verify the path from flash to the first fetched instruction: every loader state, every failure branch, the handoff to the core, and the cost of a boot. The loader design itself is on the bootloader page; this page covers only what is checked.

1. The asymmetry that shapes the plan

The loader can run from reset and nothing else can. Until it reaches S_CLEAN_RELEASE the SPI master is the only peripheral out of reset; I2C, both timers, UART and GPIO are held by periph_rst_n. So at the moment a load fails there is no LED, UART or GPIO signature available, and any externally observable failure behaviour needs an RTL change. That is why Rev B specifies a failure signature (BOOT-S4) rather than observing one. The release order is on the reset page.

3. Image source and transport

The only image source is SPI NOR flash; the loader is the sole reader and the core is held in reset for the whole load. Transport has two halves. Control is APB through slot 4: the loader sits between the bridge and the SPI master and answers its own slave port with ready, zero data and no error because the core is in reset. During the load the direction of the path scoreboard is therefore bridge-to-loader, not bridge-to-peripheral, and Rev B asks the architecture owner to tell the scoreboard which is live. Data is AXI-Lite on crossbar SLV1, write-only, every write privileged so it can pass the ISRAM privilege gate that rejects the core's own writes.

The image length is a build parameter, 64 instruction words and 0 data words as deployed (soc:242-243 in the current file). The generator writes one little-endian stream with no header, so nothing in the medium can be checked. A second transport, a hardware image-load port for a backdoor, is specified only (ASSUMED(D-028)).

Three structural properties each need a check because no waveform at one moment proves them:

  • BOOT-17: spi_rst_n is high in every load state and low only before S_RESET exits and inside the clean-slate window.
  • BOOT-19: no state has a failure exit; every advance is conditional on presence, never quality.
  • BOOT-18: two states (S_CLEAR_SRAM, S_WRITE_SRAM) wait forever on b_valid and the loader's port is excluded from the AXI timeout monitor. This is recorded as a known hole; BOOT-S5 adds the bound.

The default arm is unreachable (16 members on 4 bits) and must not be described as an abort path.

5. Integrity checking

There is none. An exhaustive search of the loader for crc, checksum, magic, verify and integrity finds only elaboration-time parameter assertions. A garbled, short or absent image therefore produces the same observable outcome as a good one: the counter reaches its target and the core is released. Rev B specifies the minimum that makes failure detectable and visible (ASSUMED(D-029)); a signature scheme is out of scope.

Six RTL changes. BOOT-S4 is the only one with a fabric-visible effect, because releasing periph_rst_n early changes the release order, so it must be raised as a change to that order. A failure path without BOOT-S4 is one no test can observe.

6. Failure paths

Rev B Table 12.3 is exhaustive over the six causes in the finding it answers, plus three the RTL makes reachable. Figure 2 shows where each ends up; Figure 3 shows what today's RTL does and what each needs. A row whose today and required behaviour agree passes now; any other row is a directed negative test that must fail until the change lands, then be re-baselined.

BOOT-N5 inverts the usual expectation. The SPI slot's 65536-cycle timeout monitor answers a stuck read with ready, an error and the value 0xDEAD_BEEF; the loader ignores the error and writes that word into ISRAM as an instruction. The monitor then latches the slot as blocked, so the rest of the image is deposited in a few cycles and the boot completes normally. The monitor must not be cited as boot protection.

BOOT-N9 is a silent hang, not a fault. mtvec resets to 0, the BootROM base; the handler runs off the 16-word ROM into an address in neither fetch range, where there is no grant, no data and no error. It is distinct from the range-coverage check PATH-0002, which catches the same defect class at the demux; triage must keep them apart.

7. Handoff to the core

Release. The loader releases the core in S_CLEAN_RELEASE; boot_done_o rises one cycle later. For exactly one cycle the core is running and the ISRAM lockout is not yet closed; that window is BOOT-14.

What the core sees. mstatus and mtvec are at reset value 0, so MIE is 0 and an interrupt asserted during or after the load is pending but not taken until firmware enables it. The trap vector is the BootROM base, so firmware must write mtvec before any instruction that can trap; that obligation belongs in the firmware specification.

Where it starts. Reset PC is 0 (soc:1245), the BootROM's first word is available without a bubble, lui sp places the stack at the top of DSRAM, and jal enters the ISRAM base. PATH-0001 to PATH-0003 score the fetch path and PATH-0009 and PATH-0010 the lockout; this page consumes them and does not redefine them. Interrupt behaviour after handoff is on the interrupt page.

Correction owed. The dedicated ISRAM write-protection test describes writing a pattern through the core's data port. That is not executable: the core cannot write ISRAM by any route, because its accesses reach the ISRAM interface unprivileged and are rejected. The check is sound; its stimulus is not, and the fix belongs to the owner of the SRAM-path scoreboard.

8. SPI release versus image source

The architecture diagram places the SPI release after the boot image source. Because the image comes from SPI flash, that order would deadlock on the first fetch. The required order is: spi_rst_n released, and the SPI master clocking, before the first APB access (S_INIT_CLKDIV); in state terms, released on leaving S_RESET. The RTL does this (bootloader.sv:720-726), BOOT-17 keeps it so, and the correct overall order is: sys_rst_n, then spi_rst_n, then core_rst_n and periph_rst_n together. A second reason decides it if argued: the SPI master is the only peripheral available during the load, so any failure signature must come from it or from a dedicated output, and the cheapest route is an early periph_rst_n release (BOOT-S4).

9. Cycle budget and the fast-boot backdoor

This section owns the boot cost; the soak campaign cites it. The budget below is a derived estimate and must be replaced by a directed measurement from reset release to the first retired instruction at address 0 for the deployed image. Until then no phase plan may cite a boot duration as evidence.

The RTL comment of about 121k cycles carries the same divisor error and is not independent corroboration.

Backdoor equivalence. A backdoor that deposits the image and releases the core is close to mandatory for any campaign of hundreds of tests, and is also the easiest way to pass everything while proving nothing about start-up. Equivalence therefore means all of the following match:

What must matchOracle

Eligibility rule. Every BOOT-01 to BOOT-20 check, every failure-path row and every FSM state is backdoor-ineligible. A regression green from backdoor runs only has executed none of them and must be reported untested. The manifest carries a per-test boot mode, and an unhit boot check counts as absent stimulus, not as closed.

10. Memory initialisation

Three memories are initialised three ways, two of them in simulation only; a testbench that relies on power-on content relies on something the design does not provide.

MemoryInitialisationHardware power-on content
BootROM, 64 BInitial block fills NOP then overlays the hex image by relative path; a missing file leaves a NOP sled silently, so the first two words must be compared at run timeDesigned (ROM)
ISRAM, 32 KBSimulation only: NOP fill and $readmemh under ifndef SYNTHESISUndefined; S_CLEAR_SRAM is the only thing that defines it
DSRAM, 32 KBNone: no reset, initial block or readmem; X from elaborationUndefined; deployed image has no data words, so the zeroing pass alone defines it

Not initialised, as a list: BootROM words 2 to 15 are NOP by design; ISRAM is NOP in simulation and undefined in hardware; DSRAM is undefined in both. A few peripheral identity registers reset non-zero (GPIO info, UART line status and divisor, SPI status). The loader's own state, including its three reset outputs, resets to a defined low value (bootloader.sv:589-591). Firmware that assumes a zeroed data section relies on the loader, and the firmware contract should say so.
