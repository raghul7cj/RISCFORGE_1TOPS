Coverage Plan: Closure, Not Reporting

How Rev B turns coverage into a closure mechanism: one tool of record, one merged database per candidate, four families that partition obligations, a loop that classifies every unhit bin before work starts, and five closure rules that gate G4 consumes. For engineers who will build the coverage model and for reviewers who must decide whether a bin is really closed.

1. Position of this plan, and current status

Rev B declares four coverage families: functional, structural, code and assertion. The central property is that they partition obligations. Every obligation belongs to exactly one family, and no family may discharge another's. Consequently no combined coverage score exists in the plan, and a proposal to produce one is a defect (CR-5).

An unhit bin has exactly three possible causes: the bin is unreachable, the stimulus is absent, or the mechanism that could report is absent. Only the second is cured by writing a test. Classifying before working is what keeps a coverage campaign from becoming an unbounded test-writing exercise.

Current status. SPECIFIED Everything in Rev B section 10 is a plan. Verification/status/PHASE_STATUS.md (snapshot 2026-10-31) shows P0 Bring-up IN PROGRESS and P4.1 Coverage model, P4.2 Checker viability and P4.4 Candidate-scale regression all NOT STARTED, with gates G2, G4 and G6 evaluated at the P4 exit. ACT-006, deciding the simulator of record and coverage tool (DEC-A), is still open there. No merged coverage database, waiver ledger or exclusion register was found in the repository. Coverage evidence is never a percentage of requirements; it is a statement for a stated boundary.

3. The XSim constraint on cover property

XSim, the interactive simulator used today, cannot evaluate cover property. This is a measured fact in the repository, not an inference:

  • EXISTS The retained Step 4 self-proof README (Verification/artifacts/component_first/20261019_run02/monitor/step4_selfproof/README.md) states that XSim reports unsupported cover property statements in the SVA files, and that the run therefore verifies the procedural checker and fault matrix, not functional coverage closure.
  • EXISTS Verification/step4_checkers carries a cover property next to each assertion in step4_axi_sva.sv and step4_apb_sva.sv (11 and 12 occurrences by text search). Step 4's exit criterion 2, "every assertion has a cover", is recorded as done in STEP4_SPEC section 13, but those covers cannot be hit-counted in XSim. STEP4_SPEC section 10 records that its listed XSim tool constraints do not affect VCS or Xcelium.
  • EXISTS run_step4.ps1 -Coverage invokes XSim's own coverage and xcrg report. Rev B calls XSim a bring-up tool that produces no counting artefact, so that output is useful for debugging and does not feed G4.

Consequences for the plan: assertion-family bins (check evaluated, antecedent_satisfied_count >= 1) can only be closed in the tool of record. Until a VCS or Xcelium run exists, the Step 4 covers prove nothing about stimulus, and a covered assertion in an XSim log must not be cited as a hit. Rev B does not list this as a decision; it is a current constraint recorded here.

4. Code coverage

Rev A declared three families and no code coverage. Rev B adds it as a fourth, reported family with four metrics and an explicit scope. The in-scope set is every module reachable from riscforge_soc_subsystem in the generated filelist, not soc_subsystem.f, which is known to be incomplete (the UART pulls in OBI modules the file says were removed, decision D-15). A module in the generated set but missing from soc_subsystem.f is in scope and is also reported as a harness defect; scope is never narrowed to hide a filelist defect.

Why toggle is deferred. Toggle density is a property of a campaign, not of a run, so a per-run threshold would be unreachable or vacuous. The rule is binding and the number is set per net class after the first full-campaign merge; until then the merged figure is reported with no gate input.

Reset dominance is a rule, not an exclusion. The core is held in reset until the bootloader releases it (reset hold of 4 cycles, flash power-up wait of 30,000 cycles), so no core flop toggles for that whole interval. Core toggle is therefore merged over the campaign and evaluated at G4, never per run. Excluding the core because it is in reset for most of the run is exactly how a dead core would produce a green run.

Four precedence rules settle overlaps: (1) a code hole is never waived by pointing at a functional bin, because a bin records an architectural combination and a line records an executed instruction; (2) a functional bin that coincides with a single RTL branch may carry a link, which closes nothing but re-opens the bin for review when the branch changes; (3) evaluated is not non-vacuous: a check sampled all campaign against a fault never injected is invisible to every percentage; (4) the sign-off predicate is a conjunction of four separately reported predicates, never a weighted total, because each fails for a different reason and names a different owner.

8. Closure rules CR-1 to CR-5

RuleMeaning in practice
CR-1A bin closes only when its owning family has recorded a hit; for the assertion family the check must also be non-vacuous (Table 6.2). Evaluated alone never closes an assertion bin. One declared exception: the unmetered-bootloader-port check, which closes on zero attributable timeouts over the campaign.
CR-2A waiver records that a bin is unreachable and why. It never replaces hitting a bin, and a code item cannot be waived by pointing at a functional bin.
CR-3Every waiver has an owner, a justification and a review date; the requester is not the approver. A toggle exclusion is a waiver and must name the net.
CR-4Code and functional coverage are reported per run and merged per candidate at one RTL identity. A regression in any bin or in-scope code item between candidates is a failure against Table 6.1 and is not offset by a gain elsewhere.
CR-5"Coverage is high" is not a closure criterion. No combined score exists, and none may be built by weighting or summing the four families.

9. How gate G4 consumes bins, waivers and exclusions

G4 ("Coverage closed") is a per-candidate gate. Its published predicate is bins_declared - bins_hit - bins_waived - bins_excluded == 0, over the merged coverage database, the waiver ledger and the exclusion register, owned by the closure owner (Regression and gates). Each way a bin can leave the "open" state has a different evidence requirement:

Bin stateEvidence G4 requiresRule
HitHit count at least 1 in the owning family; for assertion bins, antecedent_satisfied_count >= 1 and not classified vacuously true by the toolCR-1
WaivedOwner, reason and review date; requester is not the approverCR-2, CR-3
ExcludedUNREACHABLE-BY-DESIGN four-field record (rule, RTL locator, owning agent, review date) per D-054; used for sources that reach no mip bit and for CFG-F-only checks that cannot be stimulated in CFG-SSection 10.5, D-054

The boundary with G2 is hard. G2 asks whether a checker can report, using fault-injection or self-test evidence; G4 asks whether the behaviour was observed, using bin counts. A check can pass G4 and fail G2 (evaluated all campaign, never injected), or pass G2 and fail G4 (proved capable once, behaviour never reached). A bin that corresponds to a check ID contributes to G4 only; it never discharges G2. Code coverage items feed G4 through the same predicate, and core toggle is evaluated there on the campaign merge, not per run. G2, G4 and G6 are evaluated on the merged week and never stamped per run. An untestable gate is reported untested, and untested is not a pass.

No G4 evaluation exists yet: the status snapshot lists P4.1 Coverage model as NOT STARTED, and the declared-bin count is not published anywhere I found. The nine timeout and twenty-one negative-proof bins above are therefore the only bin counts Rev B states directly.
