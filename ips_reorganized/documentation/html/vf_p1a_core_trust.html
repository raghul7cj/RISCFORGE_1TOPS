Phase P1a: Core trust

P1a establishes that the RV32IM_Zicsr core itself can be trusted, before any SoC, peripheral or firmware result is built on it. It produces five pieces of evidence, CT-1 to CT-5, that later phases take as entry conditions. This page explains each one, what exists today, and a proposed order of execution.

1. Objective

Every firmware-observable result in the plan is produced by software running on the core: the compliance suite is core-only, the six APB device suites are bare-metal programs, and the attestation oracle is firmware writing a word to DSRAM. A core defect would shift all of them in the same direction, and no peripheral checker could notice, because each compares the DUT against models that also run on that core (Rev B 21.2). P1a makes the core's trustworthiness measurable first. The core is a five-stage pipeline (IF, ID, EX, MEM, WB) with traps, a two-deep shadow stack and a class-based interrupt arbiter.

The stage brief gives a reduced execution milestone: it asks for an honest baseline and says explicitly that a smoke test is not core sign-off, and that CT-2, CT-4 and CT-5 must not be silently marked complete.

4. Exit and what it unblocks

P1a exits when CT-1 to CT-5 all hold at one recorded RTL identity. The tracker lists G0 and G1 for the P1 exit; Rev B Table 20.1 does not split P1 and lists G0, G1 and G3 on the MMIO-path partition for the combined phase (a known erratum, DEF-011). Compliance is produced as an input artefact and no gate is stamped for it at this point.

The exit evidence is the entry condition of P1b and, with P1b, of P2, P3, P4, track F (core goals) and P6. CT-1 to CT-5 are re-satisfied at the candidate identity before P5. Any later Class A (core) change re-opens CT-1 to CT-3 in full (Rev B Table 21.12).

  • Tool constraint: the pinned local simulator is XSim 2022.2; it cannot evaluate cover property. The coverage tool is undecided (DEC-A).

6. Open question: CT-4 and track F

OPEN Circularity in Rev B. Track F is entered at the exit of P1a (Table 21.5, edge P1a to F). CT-4 requires core critical formal goals to be closed, and CT-1 to CT-5 are the entry condition of P1b (Table 21.4). Read literally, the proofs cannot start until P1a exits, yet P1a cannot exit until the proofs are closed. Rev B also calls track F exit "the leg of CT-4 that must close early", and requires it only before P5.

Rev B does not say how the two statements reconcile. A reading consistent with both is that at P1a exit each core critical goal must be registered and either proved, waived, or converted to a directed test, while proofs that need the engine run in track F and must close before P5. That reading is a proposal, not a Rev B statement, and it should go into the Rev C errata (DEF-011). The stage 2 brief's instruction not to mark CT-4 complete silently remains the safe default.

7. Proposal: how to execute P1a

SPECIFIED as a proposal. The order puts cheap, decisive items first and keeps each result attributable to one identity.

  1. Freeze the identity. Close P0 (run package, DC-1). Record H_rtl for the tree; every P1a artefact carries it. Do ACT-007 now: hash hazard_unit.v and note whether the stage 3 pass used the current file.
  2. Lock the DEF-001 fix with a test. Write the directed regression (an MMIO access followed by a DSRAM load-use) and show it fails on the old line and passes on the fixed one (ACT-010). A different person closes it, as separation of duty requires.
  3. CT-1. Re-run RISCOF on the final identity and publish the four counts. Investigate every failure to a minimal reproducer and a suspected layer (core RTL, testbench, tool, specification) before touching an expectation.
  4. CT-5 in parallel. Add a cold-boot scenario beside the existing warm one in the P0 run package and record both verdicts.
  5. CT-3. Bind the first two or three checks with deliberate negative cases. Settle DEC-A so that antecedent counts can be collected.
  6. CT-2. Identify an available ISS. If present, compare a short trace first, then the applicable image set. If not, record PENDING with the blocker; do not build a new ISS.
  7. CT-4. Write the core property register with covers (Track F milestone FAB-1) for the critical groups; prove, waive or convert each (see section 6).
  8. Bundle and record. One report at the recorded H_rtl states each CT as met, not met or untested, with the artefact path. Check that no check bound in P1a has its author as grader (authorship_conflicts == 0), then declare P1a exit.

This page claims no result. It does not assert that the core passes compliance, and no percentage of requirements is implied.
