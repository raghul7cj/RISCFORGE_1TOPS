Verification phases overview

How Rev B section 21 organises the SoC verification effort: two kinds of obligation, the core-trust condition, the phase register P0 to P6, the parallel formal track F, the dependency graph with its critical path, the decision cutoffs and the RTL freeze policy. Read this page first; the stage pages elaborate each phase.

1. Two obligation classes

Rev A used one word for two different things. Rev B separates them (Rev B 21.1). A gate verdict is stamped against one candidate RTL identity and is defined only in the gate register, Table 6.1. A phase-entry condition is a predicate over evidence that must hold before a named phase may start. It is never stamped, never appears in a gate verdict, and has one effect: it blocks entry.

The split exists because decision D-23 forbids any per-run gate from depending on formal or compliance. Core trust has to precede many phases, so it is expressed as an entry condition, not as a gate.

2. Core trust CT-1 to CT-5

Every firmware-observable result runs on the core, and every peripheral checker compares the DUT with models that also execute on that core. A core defect would therefore corrupt all results in the same direction without any checker noticing. Rev B makes core trust a precondition of the later phases instead of a deliverable of one (Rev B 21.2). Details and execution proposals are on P1a Core trust.

IDComponentMeasurable predicate (summary)Owner role

CT-3Core structural assertionsEvery bound core check ID has negative_case_pass or vacuity_proved, and antecedent_satisfied_count >= 1Block checker owner (core)

CT-5Boot entryOne cold-boot and one warm-boot scenario each reach S_DONE with attestation words and AXI beats greater than zeroPartition owner (boot)

CT-1 to CT-5 are the exit evidence of P1a and the entry condition of P2, P3.1 to P3.4, P4.1 to P4.5, track F and P6 (Rev B 21.2). They are not stamped as G5; G5 is stamped once, in P6. The stated cost is that core work comes first, so peripheral teams wait longer in exchange for no peripheral result being invalidated by a late core defect.

3. Phase register

P0 to P6 keep their identifiers. P1 splits into P1a and P1b; P3 and P4 decompose into four and five sub-phases. A sub-phase identifier is never written without its parent, and a parent's gate is the conjunction of its sub-phase exits (Rev B 21.3). Track F is deliberately outside the P0 to P6 scale: numbering it as a phase would give it a predecessor and a successor, which is the defect Rev B removes.

4. Dependency graph and critical path

Figure 1 draws Rev B Table 21.7. Each numbered edge carries the evidence that justifies it; the numbers match the edge table at the end of this section. Heavy blue edges are the critical path Rev B names; thin edges are the others. Track F is a swimlane above the spine because it is not a phase.

Critical path, as Rev B states it

  • The longest chain runs through the register model P2, not the architectural checks: P3.1 to P3.3 rejoin at P4.1, so shortening one does not shorten the plan. P2 is also the widest phase (25 to 45 ED).
  • Track F is on the critical path for exactly one edge, F exit to P5. Entering F at P1a gives it slack equal to all of P1b, P2, P3 and P4; entering later removes that slack.
  • P6 has no alternative predecessor. P5 can only be compressed by running more campaign partitions in parallel, a capacity decision.

Observation, OPEN. Rev B's text names P4.2 to P4.4 directly, but edge 16 also lists P4.3 as a predecessor of P4.4 and edge 15 puts P4.3 after P4.2. The chain through P4.3 is therefore at least as long as the direct one. Figure 1 follows Rev B's wording; the discrepancy does not change the conclusions above.

8. Effort derivation and uncertainty

The binding rule (Rev B Table 21.8) is E(phase) = N_check x tau_check + N_scen x tau_scen + E_fixed. The throughput constants tau_check and tau_scen are TBD(D-GR01): the repository holds no measured verification throughput. The ranges in the phase register are therefore planning values built from three bases, in descending reliability: a direct count of checks, a ratio to a neighbouring phase, or an analogy.

BasisUncertainty bandNote
Direct countplus or minus 40%Phase checks enumerated in a section the plan owns
Ratioplus or minus 55%Scaled from a neighbouring phase's count
Analogyplus or minus 70%Order of magnitude only; also used where volume depends on TBD(D-25)
  • Phase band and volume band are united, not multiplied.
  • tau_scen becomes a measurement at P0 exit (P0 runs and times scenarios); tau_check at P1a exit. Table 21.3 is then reissued. Tracker item P0-X2 is NOT MET today.
  • Elapsed time equals the critical path length, which is TBD(D-GR02) pending a start date and a team size (TBD(D-GR03)). The only scheduling statement that needs no unknown is the sum rule: concurrent commitment never exceeds team size, checked by the project lead at each phase entry.

9. RTL freeze point F and re-run policy

The freeze point F is declared at the exit of P1b (D-GR09). After F, RTL still changes, but every edit carries a change note naming files, change classes and the phases the re-run touches, and no gate verdict transfers across an identity change. There is no judgement about "significant" changes, which is what makes the rule enforceable. The identity is a SHA-256 over a manifest built from the non-comment entries of RTL_SOC/soc_subsystem.f (Table 21.10), because no git history exists to cite; the recipe and its use are on P0 Bring-up.

Three precedence rules resolve overlaps: any change to core_rst_n release timing, to the fast_irq_i or fast_intr_core widths, or to mip_w is Class A whatever file carries it; Class X is additive; and the class map is generated from the traceability matrix once that exists (Rev B Table 21.12, D-GR10). A per-run gate is re-run whenever its run is re-run, a per-candidate gate is re-derived whenever the manifest changes, and G5 is re-stamped only in P6 (Rev B Table 21.13). See regression and gates.
