Phase P0: Bring-up

P0 proves that the harness can build the intended SoC, push stimulus through it, and keep enough evidence to repeat the run. It claims nothing about functional correctness. This page covers the phase definition, the run package, the two gates it stamps, and where the project stands against the exit criteria.

1. Objective

Produce one reproducible end-to-end SoC run and record its identity (Rev B 21.3, goals/P0_bringup.md). The run starts at bootloader and SRAM load, releases the core, executes firmware that checks an expected outcome, and ends in a recorded verdict. P0 is the only phase with no predecessor, and every other phase depends on it: no gate can be evaluated before one run exists, because G1 is decided from a run's own artefacts.

The goal labels P0-G1, P0-G2 and P0-G3 are phase-local. P0-G1 evidences Rev B G0, P0-G2 evidences Rev B G1, and P0-G3 evidences the run identity. They are not Rev B gate identifiers; Rev B's own G3 is the checkers-pass gate.

3. What P0 verifies, and what it does not

  • Verifies: the harness builds the golden filelist with no unresolved and no extra modules; the simulator version is pinned; artefacts can be written; stimulus reaches the DUT (instructions retire, AXI-Lite and APB transfers occur, firmware writes an attestation word); the run is repeatable from its recorded identity; a deliberate negative case fails visibly (stage brief step 5).
  • Does not verify: core correctness, register behaviour, interrupts, coverage, formal results or compliance. The stage brief explicitly excludes a UVM port, generic agents, scoreboards, ISS lock-step, coverage closure and dashboards.

4. Activities

  1. Inspect the repository for the SoC top, resolved filelist, simulator command, firmware build, boot setup and result mechanism; record gaps (brief scope 1).
  2. Compute the tree identity: H_rtl, H_filelist, ID-1, ID-2, ID-3 (Table 21.10, Table 21.11).
  3. Build and elaborate; compare compiled modules with the golden module set (G0).
  4. Run one boot scenario with self-checking firmware; read the counters (G1).
  5. Run one harmless negative case, for example a wrong expected firmware signature, and confirm FAIL.
  6. Package identity, logs, filelist diff, counters and verdict together.
  7. Close out: record DC-1 (default is out of scope), time the scenario to obtain tau_scen, reissue Table 21.3.

8. Use of the identity recipe

P0 is where the Rev B Table 21.10 recipe is first applied. The recipe pins the RTL by hashing, because the plan treats a cited commit id as worse than none. In outline: fix the file set from the non-comment entries of RTL_SOC/soc_subsystem.f; resolve every entry (any failure means no hash and an untested run); relativise paths (absolute paths are an error); SHA-256 the raw bytes of each file with no normalisation; build a sorted manifest of <sha256> <path> lines; hash the manifest to get H_rtl; hash the relativised filelist for H_filelist; compute ID-1, ID-2 and ID-3 in the same step; stamp all eight identity fields (H_rtl, H_filelist, ID-1, ID-2, ID-3, tool version, seed, plusargs) into every artefact header.

The DEF-001 story

The Oct 24 stage 3 README traces the earlier counter shortfall (reads 12 instead of 14, a corrupted write counter) to a core defect. During an MMIO access mem_stall_i freezes the pipeline. A DSRAM load in EX followed by a dependent instruction raised lwstall, which flushed EX in FlushE because the flush was not gated by the stall, so the waiting load turned into a NOP and left a stale register value. The fix gates the load-use term with ~mem_stall_i; the current riscv_core/rtl/hazard_unit.v:192 contains it. The tracker records the defect as DEF-001, C-DUT, S2 proposed, FIXED-UNVERIFIED: there is no directed regression that fails without the fix (ACT-010), and no independent closer.

The fix is a Class A (core) change under Rev B Table 21.12, so any earlier core evidence is void and compliance and lock-step must be produced at the final identity. Also open: hazard_unit.v was modified after the stage 3 run timestamp; the file must be hashed against the proof (ACT-007). The Oct 18 failure is therefore explained by the core defect only by inference from the later pass, not by a retained before-and-after pair on the same identity.

10. Proposal: the run-package script

SPECIFIED proposal, not built. ACT-002 asks for one script; this section suggests its shape so that it closes P0-G1.4, G1.5, G2.4, G2.5 and G3.* together.

  1. Preflight. Run p0_identity.py (EXISTS). Refuse to continue, and write verdict UNTESTED, if ID-1, ID-2 or ID-3 is non-zero. Do the artefact write test (empty file write, read back, delete).
  2. Create the folder named by date, scenario and a short H_rtl prefix. Copy in the manifest, the relativised filelist and the contract reference.
  3. Build. Execute compile and elaborate with the pinned XSim 2022.2; tee the logs into the folder; record the commands as run, not as intended.
  4. G0 diff. Extract the elaborated module list and compare it with the golden module set (ACT-003): write unresolved_modules and extra_modules counts and the diff report.
  5. Run the stage 3 scenario with the recorded plusargs and seed none, with a timeout. Time it for tau_scen.
  6. Parse counters from the testbench summary into the verdict record: instructions retired, AXI reads and writes, APB transfers, PSLVERR count, attestation words written and value. Fail on any zero or on a timeout.
  7. Negative control. Re-run with a corrupted expectation and require the verdict FAIL; restore the correct expectation and re-check the file hash.
  8. Seal. Write a single record with all eight identity fields, the G0 and G1 verdicts (PASS, FAIL or UNTESTED), and file hashes of every part in the folder.

Order matters for honesty: identity before any run; verdicts derived only from retained files; nothing in the verdict that cannot be recomputed from the folder. A first success criterion is simple: running the script twice at an unchanged identity yields the same counters and the same verdict.
