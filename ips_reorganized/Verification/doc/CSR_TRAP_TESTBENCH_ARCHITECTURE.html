01 / Goal

Establish checked coverage of the difficult interactions.

Verification goal

Verify that exceptions and interrupts produce the correct trap state and redirect, preserve instruction order, suppress forbidden side effects, and return or replay correctly when CSR dependencies, memory waits and multi-cycle operations overlap.

The current deliverable provides the connected skeleton. The reference model, coverage bins and stimulus must be supplied and reviewed before this goal can be demonstrated.
Target behavior

Exception metadata and priority; older versus younger effects; CSR read/write dependencies; gating-CSR updates; IRQ arrival during memory or M operations; MRET state and replay.

Scope allocation

Ordinary CSR instruction semantics are assigned to RISCOF in the plan. This environment targets corner cases and hazards. Existing IRQ arbitration and gateway coverage remains with its unit bench.

RISCOF is an evidence dependency: its current qualifying result was not established by this skeleton task. The proposed suite supports G2.9 review and relevant core verification; it does not itself close a signoff gate.

02 / Architecture

Two new tops, with one shared core harness.

The CSR fixture uses module-based SystemVerilog. The core harness uses lightweight OOP SystemVerilog for shared configuration, scheduling and observation plumbing. UVM is not introduced in this skeleton; the separate SoC UVM/VIP requirement remains an independent obligation.

03 / Observation flow

One snapshot, two independent recipients.

Pipeline activity and settled CSR state are sampled at separate phases. Each record is copied into separate queues, so the scheduler and scoreboard do not compete for a single mailbox entry.

Reset-held behavior: the current lifecycle keeps reset asserted. The event publishers are gated by reset release, so they emit no functional records in the skeleton-only run. Starting the consumers and stopping them with sentinels establishes source plumbing; it does not exercise the functional event path.

04 / Lifecycle

A bounded incomplete run, ready for extension.

  1. Initialize deterministic inputs.Assert active-low reset and keep IRQ pins low. Construct the configuration and environment.
  2. Start the empty test hook and passive consumers.corner_env.run() calls configuration, then forks the scheduler, scoreboard consumer and selected test hook.
  3. Keep reset asserted for three clock cycles.The memory shells remain placeholders. No program or architectural scenario runs.
  4. Stop both mailbox consumers.stop() sends a null sentinel to each queue and waits for both consumers to finish.
  5. Report SKELETON/INCOMPLETE.No reference checks or coverage results exist. This lifecycle is described from code; simulation has not established its execution.

Expected results still need decisions: interrupt handling during busy MUL/DIV; gating-CSR writes versus IRQ acceptance; invalid CSR/encoding behavior; mtval policy; direct versus vectored mode; software/external IRQ scope; instruction access faults; and per-register port priority, especially MSIP. The skeleton chooses none of these policies.
