2. The 3-Tier Verification Boundary Hierarchy

A rigorous classification methodology segregating targets by their exact Design Under Test (DUT) boundary.

Tier 1: IP Unit Level Unit Focus

Isolates individual IP blocks from the system. Uses direct Bus Functional Models (BFMs), pin stubs, or synthesizable wrappers to exercise boundary state spaces exhaustively.

  • DUT Boundary: Standalone block interface (APB, AXI4-Lite, or custom signals).
  • Stimulus Mechanism: Dedicated SystemVerilog tasks, randomized BFMs, directed cycle vectors.
  • Observation Points: Pin protocol assertions, internal FIFO pointers, local coverage bins.
  • Scope Intent: Exhaustive functional verification of registers, state transitions, and edge cases.
Tier 2: Subsystem Fabric Level Fabric & Routing

Verifies bus interconnects, memory-mapped aperture decoders, and structural protocol bridges using synthetic responders or isolated traffic controllers.

  • DUT Boundary: Interconnect matrix + bridge + aperture decoder (peripherals replaced with stubs).
  • Stimulus Mechanism: Synthetic master transactions injecting contiguous and out-of-range addresses.
  • Observation Points: Select-line routing, wait-state propagation, PSLVERR abort injection.
  • Scope Intent: Proof of address space isolation, routing correctness, and fabric deadlock immunity.
Tier 3: SoC Integration Level Closed-Loop SoC

Complete closed-loop system simulation combining the RISC-V core, bus fabric, integrated peripherals, and dual memory banks executing real compiled firmware.

  • DUT Boundary: Complete RISCFORGE chip boundary (including clock, reset, external pins).
  • Stimulus Mechanism: Preloaded bare-metal C/assembly firmware programs.
  • Observation Points: Instruction retirement counters, passive bus monitors, firmware attestations.
  • Scope Intent: End-to-end confirmation of pipeline execution, interrupt handling, and peripheral control.
Methodological Rule: Tier Follows the DUT Boundary, Not Module Function
Under this framework, tier classification is dictated strictly by the physical boundary instantiated in the testbench. A standalone crossbar testbench is classified as Tier 1 IP Unit because it tests the isolated crossbar against synthetic master/slave BFMs. Conversely, tests exercising bus apertures through the SoC bridge are classified as Tier 2 Subsystem, while complete core-driven firmware executions represent Tier 3 SoC Integration.

3. Golden Baseline Freezing & RTL Identity Governance

Cryptographic provenance, filelist decoupling, and Rev B identity predicates safeguarding baseline integrity.

Cryptographic Identity Stamping

To prevent unverified changes from corrupting golden sign-off baselines, the repository enforces dual-layer SHA-256 cryptographic freezing stamped into version-controlled manifests:

  • Filelist Identity: Master list hash computed across all registered source files.
  • RTL Identity: Cumulative hash computed over the raw byte content of all golden RTL and header files.
  • Git Provenance Stamping: Git commit hash and dirty status recorded in every execution record.
  • Immutability Guarantee: Development edits occur in forwarding filelists, keeping baseline hashes unchanged.
The Three Rev B Identity Predicates

Specific architectural hygiene rules enforced across all filelists and component directories:

  • ID-1 (Duplicate Module Convergence): Prohibits divergent copies of the same Verilog module in reachable directories (both timer copies converged to identical content).
  • ID-2 (Zero Unresolvable Paths): All source files and include directories declared in filelists must physically exist on disk.
  • ID-3 (Absolute Path Ban): Filelists must never contain absolute host paths; all references must be strictly relative to the repository root.

4. Execution Infrastructure & Sandboxed Regression Engine

Zero-footprint simulation orchestration ensuring isolated execution, bounded deadlines, and leak-free artifact containment.

Sandboxed Execution Model

Simulators generate intermediate databases, wave logs, and journal files that pollute source trees if unmanaged. The established execution model guarantees complete containment:

  • Isolated Execution CWD: Compiler, elaborator, and simulator tools execute strictly with cwd = sandbox_dir.
  • Absolute Path Normalization: Filelist relative paths are dynamically translated to absolute paths at invocation time.
  • Zero Repository Footprint: All simulation artifacts (xsim.dir, waveforms .wdb, snapshots, compiler databases) remain confined within the unique run folder.
  • Deterministic Retention: Only the final run log (run.log) and structured verdict (verdict.json) are permanently archived.
Multi-Process Tree Termination Architecture

EDA tools spawn nested worker processes (e.g. xsimk.exe) that easily orphan when parent wrappers die. The regression runner implements bounded, verified process reclamation:

  • Process-Tree Killing: Windows invocation of taskkill /F /T /PID targeting the parent and all child nodes.
  • Return Code Distinction: Explicitly audits return code 0 (terminated) vs code 128 (already reaped), flagging unrecognized failures.
  • Bounded Pipe Drain: Subprocess stdout/stderr pipes are drained under a strict 5-second deadline.
  • Explicit Failure Reporting: Failure to kill or drain immediately marks the run log with explicit diagnostic warnings.

The established regression entry point is run_regression.py; its autorun harness stages each target in an ephemeral sandbox and owns cleanup of the simulator process tree.

Stage 1

Identity Verification & Sandbox Creation

Extracts git commit and stamps P0 manifest hash. Generates isolated timestamped run directory under artifacts/runs/.

Stage 2

Path Normalization & Static Compilation

Converts relative filelist references to absolute paths. Invokes xvlog inside the sandbox with strict error-code capture.

Stage 3

Elaboration & Snapshot Generation

Invokes xelab with timescale 1ns/1ps. For design-only targets, halts after clean elaboration; for testbenches, produces simulation snapshot.

Stage 4

Simulation Execution with Bounded Deadlines

Executes xsim in batch mode under a wall-clock timeout. On timeout, triggers hierarchical process tree kill and bounded pipe drain.

Stage 5

Strict Evidence Classification & Atomic Publishing

Scans log for non-zero activity counters, vacuity violations, and forbidden errors. Emits immutable JSON verdict record atomically via temporary-rename protocol.

5. Strict Evidence Classification & Anti-Vacuity Policy

A multi-clause verification grading engine enforcing active stimulus accounting and prohibiting synthetic passes.

Quantified Positive Counters

A passing simulation must actively demonstrate functional work. Banners lacking non-zero numeric counters are strictly prohibited.

  • Requires regex pattern [1-9]\d* in pass banners.
  • Enforces minimum check, transfer, or snapshot counts.
  • Generic fallbacks (e.g. bare "PASSED") are completely disabled.
Autonomous Vacuity Trapping

Testbenches that exit cleanly without exercising any logic are caught and failed by an active anti-vacuity monitor.

  • Traps patterns like checks=0, pass=0, 0 PASSED.
  • Flags vacuity_detected = True in verdict records.
  • Forces overall verdict to FAILED despite exit code 0.
Multistage Signature Auditing

Error detection operates across all three execution phases: compilation, static elaboration, and runtime simulation.

  • Scans for tool error codes (ERROR: [XSIM, *E,).
  • Traps SystemVerilog fatal calls ($fatal, Assertion failed).
  • Emits complete failure diagnostics into verdict.json.
Classification Verdict Precedence Engine
The classifier evaluates execution results through strict deterministic priority: (1) Pre-execution failure (missing filelist) ➔ BLOCKED; (2) Compiler exit non-zero (syntax/type error) ➔ FAILED; (3) Elaboration exit non-zero (unresolved module/port mismatch) ➔ FAILED; (4) Simulator exit non-zero or wall timeout ➔ FAILED; (5) Vacuity violation detected (zero checks/transfers) ➔ FAILED; (6) Forbidden fatal or assertion token detected in log ➔ FAILED; (7) Missing mandatory positive count regex signature ➔ FAILED; (8) Design-only target with clean elaboration ➔ PASSED (Design-Only); (9) Clean exit 0 with validated positive activity counter and zero forbidden tokens ➔ PASSED.

6. Bare-Metal Reference Firmware Architecture & Hardware Abstraction

A unified firmware Board Support Package (BSP) decoupling software test payloads from physical bus topologies.

Authoritative Hardware Memory Map

Derived from the golden RTL definitions (riscforge_soc_subsystem.sv and boot_rom.sv) and implemented in soc_regs.h:

  • BootROM: 0x00000000 (64 Bytes = 16 words startup jump stub).
  • Instruction SRAM (ISRAM): 0x00010000 (32 KiB executable instruction window).
  • Data SRAM (DSRAM): 0x00020000 (32 KiB data, rodata, stack, and heap window).
  • APB Peripheral Base: 0x40000000 (Contiguous 4 KiB apertures per integrated peripheral).
Peripheral Aperture Register Mapping

Standardized base addresses for all integrated peripheral controllers:

  • APB[0] I2C Master: 0x40000000 (Prescaler, Control, RX, Status, TX, Command).
  • APB[1] Timer 0: 0x40001000 (Control, Limit, Prescaler, Counter Value).
  • APB[2] UART 16550: 0x40002000 (RBR/THR/DLL, IER/DLM, IIR/FCR, LCR, MCR, LSR).
  • APB[3] GPIO 32-bit: 0x40003000 (Input, Output, Direction, Interrupt Enable/Status).
  • APB[4] SPI Master: 0x40004000 (Control, Status, Clock Divider, CS, TX/RX Data).
  • APB[5] Timer 1: 0x40005000 (Secondary system timer registers).
CRT0 Startup & Trap Dispatch

Low-level processor initialization ensuring predictable hardware execution prior to payload entry:

  • Reset Vector Hook: Initializes global pointer (gp) and aligns stack pointer (sp) at top of DSRAM.
  • BSS Zeroing & Data Copy: Clears uninitialized memory and copies initialized data segments.
  • Trap Vector Vectoring: Installs default synchronous exception and asynchronous interrupt handlers.
  • Trap-Frame Preservation: Saves caller-saved registers upon trap entry, preserving hardware state for blame analysis.
Linker Memory Segmentation

GNU linker architecture enforcing memory boundaries at compile-time:

  • Preload Execution Model: Maps .text directly to ISRAM (0x00010000) and data to DSRAM (0x00020000).
  • Mandatory Entry Offset: Enforces _start symbol placement strictly at 0x00010000.
  • Linker Overflow Assertions: Strict linker scripts abort compilation if segments exceed 32 KiB physical memory limits.
  • Standardized Drivers: Production C drivers sharing unified initialization, transfer, and status interfaces.

8. Ledger Governance & Dynamic Verification Tracking

Automated, version-controlled metadata engines generating dynamic reporting dashboards without manual bookkeeping.

Master Verification Matrix

The primary source of truth across all components and integrations, version-controlled as a 26-row schema-validated CSV:

  • Assigns unique permanent Evidence IDs (e.g. APB-02, FAB-03).
  • Tracks component scope (Unit, Subsystem, System, Harness).
  • Maps every row directly to master plan chapters and sections.
  • Records live retained run directory pointers and exact pass metrics.
Unified Defect Register

A formal lifecycle tracking ledger categorizing all design and verification anomalies:

  • Defect Classes: C-DUT (Silicon bug), C-HARNESS (TB flaw), C-SPEC (Doc ambiguity).
  • Severity Levels: S1 (Blocker) to S4 (Cosmetic enhancement).
  • Verification Status: Requires second-person closer and designated regression test before marking FIXED-VERIFIED.
Dynamic Metric Engine

A Python build script (build_tracker.py) transforming CSV ledgers into analytical outputs:

  • Generates RISCFORGE_Verification_Tracker.xlsx with native dynamic Excel formulas (COUNTIF, INDEX/MATCH).
  • Emits executive markdown snapshot PHASE_STATUS.md.
  • Eliminates human error and manual transcription drift.
Relational Traceability Model
The established tracking architecture enforces strict relational data integrity: Master Verification Plan Clauses ➔ Verification Matrix Evidence IDs (26 Rows) ➔ Crosswalk Target Catalog (17 Targets) ➔ Isolated Run Directory Sandboxes ➔ Structured Machine Verdicts (verdict.json) ➔ Defect Lifecycle Register (defects.csv) ➔ Dynamic Excel Dashboard & Phase Status Snapshots.

9. Verification Automation Tooling & Script Inventory

Architectural rationale, lifecycle boundaries, and categorization of the Python automation toolchain.

Why Python is Required in EDA Verification

Hardware description languages execute strictly within simulator memory and lack operating-system-level execution authority. Python serves as the essential control and governance plane:

  • Cleanroom Sandbox Isolation: Spawns ephemeral scratch execution run directories, isolating temporary simulator locks (xsim.dir) from golden repository sources.
  • Bounded Process-Tree Lifecycle: Enforces wall-clock execution deadlines and issues recursive process-tree termination (taskkill /F /T /PID), distinguishing exit code 0 (terminated) from 128 (already reaped).
  • Strict Evidence Classification: Scans raw stdout/stderr streams to mandate [1-9]\d* positive transaction counters and autonomously traps vacuous passes (e.g., checks=0).
  • Cryptographic Baseline Integrity: Computes byte-exact SHA-256 digests across 90 source files ($H_{filelist}$, $H_{rtl}$) and enforces multi-directory module convergence ($ID_1, ID_2, ID_3$).
  • Automated Formulaic Ledger Building: Reads version-controlled CSV matrices to emit multi-sheet analytical workbooks with live Excel formulas (COUNTIF, INDEX/MATCH), eliminating human data entry error.
Toolchain Structure: 3 Daily Engines vs. Auxiliary Staging

While ~25 Python scripts exist across the verification folder, only three scripts constitute the active daily execution runtime:

  • Primary Regression Engine: run_regression.py (443 lines) — The single entry point for all testbench execution, timeout monitoring, and evidence classification.
  • Baseline Identity Stamping: p0_identity.py (235 lines) — Frozen manifest and cryptographic hash generator.
  • Governance & Dashboard Engine: build_tracker.py (803 lines) — Dynamic spreadsheet and status report builder.
  • Firmware Hex Translators: Bridging GNU GCC ELF outputs to 32-bit hex word arrays for Verilog $readmemh.
  • Immutable Audit Snapshots: 11 scripts under artifacts/P0/ are preserved historical run logs, never executed in regular regression.
