02 Verification Architecture & Progression

The verification methodology adopts an incremental, fail-fast progression where each stage provides the prerequisite foundation for subsequent stages. Rather than relying on monolithic testbenches or complex UVM VIPs, the infrastructure uses lightweight SystemVerilog passive monitors connected directly to internal signals, paired with bare-metal firmware that acts as deterministic stimulus.

Read the result at the right level
A test case is a scenario, such as deliberate noncompletion. A transaction is one load, store, or bus operation within it. An activity threshold rejects too little stimulus. An acceptance criterion decides whether the scenario proved its purpose. The earlier Stage 3 failure was an accounting discrepancy, not too few test cases. These implementation stages do not replace Rev B's broader release gates.

The Four-Stage Verification Progression

  1. Stage 1 (Boot & Communication Baseline): Validates toolchain assembly, crt0.s C runtime initialization, DSRAM .mailbox protocol, and basic APB read/write round-trips. Provides directed evidence that firmware can run, publish results, and request a testbench verdict.
  2. Stage 2 (Failure Detection & Blame Engine): Demonstrates the watchdog timeout mechanism through an inverted negative test. Proves that when software hangs, the testbench catches the expiration, attributes failure to LAYER_FIRMWARE with the exact PC, and freezes cyclic history buffers for post-mortem triage.
  3. Stage 3 (Quantitative Bus Observability): Targets exact transaction accounting across the observation points. The firmware counts accesses issued while testbench monitors independently count AXI-Lite and APB beats. Exact agreement is the objective. Current acceptance enforces activity minimums; equality of printed totals is an audit observation, not yet an automated stage-specific assertion.
  4. Stage 4+ (Protocol Formalisms & Advanced Integration): Extends monitoring with SVA protocol assertions, bus timeout fault injection, register reset sweeps, pin-level peripheral BFMs, and machine-mode trap preemption.

Runtime System Architecture & Datapath Partitioning

A crucial architectural concept in the RISCFORGE SoC is the distinction between Direct SRAM Access and MMIO Bus Access. The CPU core communicates with memory through hybrid_mem_interface.sv, which decodes the upper address bits to direct transactions down two physically separate paths:

  • Direct DSRAM Path (0x0002_0000 – 0x0002_7FFF): Mapped directly to port 0 of the dual-port SRAM arbiter (sram_mux.sv). The interface uses a synchronous SRAM response; interface latency is not a promise that every CPU load completes in one clock. Crucially, direct DSRAM accesses bypass the AXI4-Lite crossbar and APB bridge completely, producing zero AXI and zero APB bus activity.
  • MMIO Peripheral Aperture (0x4000_0000 – 0x4FFF_FFFF): Forwarded to the 2x3 AXI4-Lite crossbar (axi_lite_xbar.sv), across the AXI-to-APB synchronous bridge (axi_lite_to_apb.sv), and into the 6-slot APB3 peripheral subsystem. The CPU core pipeline is frozen (mem_stall_i = 1) throughout the multi-cycle handshake until BVALID or RVALID commits.

03 Stage 1 Deep Dive: Boot, Console & Bus Liveness

Purpose: Prove that the RISC-V GCC toolchain produces structurally valid RV32IM machine code, that crt0.s executes from ISRAM, that the DSRAM mailbox accurately streams ASCII console messages to the testbench, and that the CPU can execute read-modify-write operations across the APB bus without wedging the interconnect.

Execution Sequence

  1. C Runtime Initialization (crt0.s): Disables interrupts via csrci mstatus, 0x8, sets stack pointer sp = 0x0002_8000, sets gp = __global_pointer$, clears the other writable GPRs while preserving initialized sp and gp, zeroes .bss without touching .mailbox, and jumps to main().
  2. Section 1 (Canary & Memory Layout Verification): Firmware reads bss_canary (verifying 0), data_canary (verifying 0xC0FFEE11), and rodata_guard (verifying 0x5A5A1234). Then writes bss_canary = 0x1234ABCD and confirms write persistence.
  3. Section 2 (Mailbox Console Streaming): Calls mailbox_puts() to stream character packets through MAILBOX->char_out (DSRAM offset +0x14). Each character carries a sequence tag; the testbench notices a new nonzero tag and prints the character. This is a DSRAM side channel, not UART pin traffic.
  4. Section 3 (DSRAM Data-Path Signature): Executes proof_dsram_signature(0xA11CE01), which writes a deterministic 16-word seed-derived pattern, checks every returned word, and folds the words using an FNV-style multiply/XOR checksum. It repeats with seed 0x0B0B0CA5 and checks that the signatures differ: 32 verified DSRAM reads are attempted. The log reports final signature 0x953C6BAC; independent agreement with the source algorithm is not established (see Section 8).
  5. Section 4 (APB Bus Liveness): Executes proof_mmio_ping() against two separate peripheral apertures: I2C Prescaler Lo (0x4000_0000) and Timer 0 Compare Register (0x4000_1008). Performs read-modify-write and verifies physical restoration.
  6. Vacuity & Pass Gate: Firmware asserts TEST_REQUIRE_ACTIVITY(8, 6, 2, 0x1000), publishes activity to MAILBOX->cycle_cnt, writes MAILBOX_CMD_PASS (0xC0DE_C0DE), and executes wfi.

Boot assumptions and what the canaries establish

The retained run uses warm preload: the harness synchronizes reset, loads ISRAM/DSRAM images, then releases the core through the BootROM trampoline to 0x00010000. This does not exercise SPI-flash cold boot. The linker reserves 0x00020000–0x0002003F for the mailbox; data sections follow. The stack starts at 0x00028000 and grows downward. Startup clears BSS, sets mtvec, and calls main; initialized data comes from preload.

The BSS canary checks zero and later write/read persistence. If memory was already zero, that alone cannot prove the clearing loop ran. Also, rodata_guard is a nonvolatile C constant: the compiler may substitute it into comparisons. Check the binary for an actual load before claiming a physical rodata-read test. The normal suites use mailbox helpers; startup's fallback return-from-main path uses different command values and is not validated by these passes.

04 Stage 2 Deep Dive: Watchdog, Freeze & Blame Attribution

Purpose: Validate the testbench safety watchdog, monitor freezing logic, and diagnostic blame attribution engine. This stage implements an Inverted Negative Proof: because the intended outcome is a hard simulation timeout, a test that terminates with CMD_PASS is considered broken, whereas an intentional timeout attributed correctly to LAYER_FIRMWARE constitutes success.

Firmware & Testbench Inversion Protocol

  1. Pre-Hang Evidence Generation: Firmware first executes proof_dsram_signature(0x5EED0002) and two APB pings, publishing activity word 0x00040006 to the mailbox. This provides evidence for the specific memory and peripheral accesses exercised before the hang.
  2. Deliberate Spin Loop: Firmware enters an infinite loop (while(1)) that increments volatile counter spin_iterations and continuously polls csr_read_mcycle(). The loop is designed to continue executing; its presence and a cumulative retirement count do not assert recent retirement at the timeout boundary.
  3. Watchdog Expiration: Testbench watchdog timer expires at exactly 50,000 cycles (configured via -testplusarg TIMEOUT=50000).
  4. Blame Engine & History Dump: Testbench calls failure_reporter.report_failure(LAYER_FIRMWARE, “WATCHDOG_TIMEOUT”, ...), freezing all cyclic ring buffers and dumping the last 10 retired instructions, LSU transactions, AXI handshakes, and APB transfers.
  5. Inverted Verdict Evaluation: Testbench checks that test ID is 0x0002, retired instructions >= 1 (MIN_RETIRED_INSTR), exactly 1 failure finding exists, blame layer is LAYER_FIRMWARE (6), failure check ID is WATCHDOG_TIMEOUT, and pre-hang bus activity was recorded. If these checks pass, it prints [STAGE2 PASS] and calls $finish(0).

Resolution of the Stage 2 Architectural Gap
In the historical archived testbench implementation, when the watchdog expired for Stage 2, the code executed if (mb_test_id == STAGE2_TEST_ID) $finish(0); before calling report_failure() or dumping the freeze buffers. Consequently, while the timeout threshold was verified, the blame engine and post-mortem dumps were never actually exercised under simulation! In the revised testbench (soc_tb_top.sv lines 667–732), the watchdog handler unconditionally fires report_failure(), dumps all four ring buffers, and then evaluates the 5-point Stage 2 acceptance criteria. The new log in artifacts/stage_proofs/20261024_stage2_watchdog/logs/ shows execution of the reporter and four dump routines. Source drives a common freeze signal; post-freeze pointer and content stability is not separately asserted.

How to interpret an expected fatal finding

Normal tests require zero reporter findings. Stage 2 intentionally creates one WATCHDOG_TIMEOUT finding and accepts it only for test ID 2 with the expected layer and prior activity. The layer is supplied by the caller; it is not an independent inference that any timeout has a firmware root cause.

The watchdog starts after boot/preload setup, not at time zero. At 10 ns per clock, 50,000 cycles are 500,000 ns; setup and the final 500 ns grace period explain termination at 500,765 ns. The reporter's approximate cycle number uses absolute simulation time and a different origin. AXI/APB dumps preserve pre-hang pings, while retirement and LSU records continue during the spin. Dump execution does not itself prove chronological accuracy or post-freeze stability.

Regression Runner Bifurcation Logic

Because Stage 2 deliberately causes failure_reporter.sv to log a failure report, standard regression parsers would interpret the string “FAILURE REPORT” as a test failure. In ips/Verification/regression/run_regression.ps1 (lines 321–326), the verdict logic is explicitly bifurcated:

if ($t -eq "stage2_watchdog") {
    $hasFail = ($log -match "\[STAGE2 FAIL\]") -or ($log -match "\[FATAL TIMEOUT\]") -or ($log -match "\[MAILBOX FAIL\]")
} else {
    $hasFail = ($log -match "\[MAILBOX FAIL\]") -or ($log -match "\[FATAL TIMEOUT\]") -or
               ($log -match "\[MAILBOX HALT\]") -or ($log -match "FAILURE REPORT")
}

05 Stage 3 Deep Dive: Exact Bus Transaction Proof

Purpose: Exercise known memory and peripheral sequences and compare firmware evidence with independently sampled bus activity. The latest run matches planned MMIO totals. Matching every LSU event to every bus completion, including dropped or duplicated operations, remains a closure objective rather than an implemented end-to-end guarantee.

Firmware Phase Architecture

  1. Phase 1 (Pure DSRAM Array Sweep): Writes 20 distinct patterned words to scratch_array[20] using seed 0x3C0DE0. Followed immediately by a full forward read-back sweep (20 loads) and an inverse reverse sweep (20 loads). Expected bus activity: 0 AXI transfers, 0 APB transfers.
  2. Phase 2 (Array Mutation & Signature): Computes seed-dependent signature proof_dsram_signature(0x3A6E0003), then separately flips a bit in scratch_array[7], checks the changed word, restores it, and checks restoration. The helper hashes proof_dscratch[], not this array; no signature is recomputed after mutation. Checksum sensitivity to scratch_array[] is not tested.
  3. Phase 3 (APB Path Liveness Across 2 Apertures): Executes proof_mmio_ping() against Slot 0 (I2C PRER_LO, 0x4000_0000) and Slot 1 (Timer 0 CMP, 0x4000_1008).
  4. Phase 4 (Sustained MMIO Read Burst): Issues 8 sequential, blocking 32-bit reads against Timer 1 Control Register (0x4000_5004, Slot 5), asserting that each reads back 0x0000_0000.
  5. Phase 5 (Vacuity Gate & Completion): Asserts TEST_REQUIRE_ACTIVITY(16, 14, 3, 0x3000) requiring >=16 DSRAM reads, >=14 MMIO reads, >=3 distinct APB apertures, writes attestation word 0x0004000E, and writes MAILBOX_CMD_PASS.

What the counters mean

A successful ping reads a baseline, writes a toggled bit, checks it, restores the baseline, and checks restoration: 3 reads + 2 writes. The checks cover the selected bit, not necessarily every register bit. Firmware counters are software bookkeeping; AXI/APB monitors observe handshakes. They are separate measurement points, but either can be wrong.

TEST_REQUIRE_ACTIVITY(16, 14, 3, 0x3000) sets minimum DSRAM reads, minimum MMIO reads, and minimum distinct slots. It does not require exactly 14 reads or four writes. 0x0004000E = (4 << 16) | 14 packs writes and reads; 0x23 = (1 << 0) | (1 << 1) | (1 << 5) records slots 0, 1, and 5.

The testbench requires nonzero retirement, AXI/APB activity and attestation with no unexpected reporter finding; it prints totals without enforcing exact equality. The path scoreboard checks completed APB slot selection from the address. Its LSU inputs are connected but unused by the matching logic. Without expected records and a completion drain, that checker cannot detect an expected transfer that never appears.

For the first array phase, count accepted stores in the array address range: expected 20 stores and 40 sweep reads, with zero AXI/APB delta in the same window. Later mutation adds two array stores and more reads. BSS initialization, stack, mailbox and counter accesses add other LSU events. Whole-run LSU totals therefore cannot simply equal 20.

06 Pipeline Hazard Record and Evidence Limits

The Stage 3 failure separates peripheral work completing from correct execution of instructions around that work. The current hazard-unit change addresses a plausible instruction-loss mechanism and a later directed run passes. A cycle trace linking the first incorrect update to that mechanism is not retained in this report.

F-CORE-001 — Data-hazard bubble while Execute must be held
Symptom: reads 12 instead of 14; writes 0x00010001 instead of 4, despite observed peripheral totals of 14 reads and 4 writes.
Implementation: three data-hazard contributions to FlushE are gated with ~mem_stall_i in hazard_unit.v:192.
Status: change present; passing directed rerun retained; historical mechanism reported and structurally supported, with trace confirmation and broader regression still open.

1. Why a bubble is normally useful

For lw a5, offset(a3) followed by addi a5, a5, 1, the add needs a value the load has not produced. With the load in Execute and the add in Decode, lwstall holds Fetch/Decode and inserts a bubble into ID/EX. In an advancing pipeline the load moves toward Memory while its consumer waits. The bubble is safe because the producer can advance.

2. Why the same action is unsafe during an older memory stall

An older MMIO operation may occupy Memory and assert mem_stall_i. The following counter load is then held in Execute; the dependent add waits in Decode. The load cannot advance. ID/EX must retain it until Memory becomes available. In decode_cycle.v:273–305, the FlushE branch precedes StallE. If both are high, clearing the control state wins over holding it. This is a synchronous control-priority conflict, not a simulator scheduling race.

Conceptual intervalMemory stageExecute / DecodeRequired decision
Before MMIO completesOlder peripheral operation waitsCounter load held / dependent add waitsHold ID/EX; no data-hazard bubble
Ungated hazard termStill stalledLoad control bits cleared by FlushEProducer may be lost
Memory stall releasesCan accept next operationLoad must advance before add consumes itResume normal hazard handling

This table explains the mechanism; it is not a measured waveform. A stale Timer 0 probe value 0x00010000 incremented by one would explain 0x00010001. Matching that arithmetic is supporting evidence; the actual stale-register path and first lost read-count update need a retained trace.

3. Ruling out a missing increment

The historical archived disassembly contains the counter updates, including the restore-read increment. This rules out an omitted increment in that binary. It does not independently rule out bad load data, overwrites, source/snapshot mismatch or another execution defect. Do not jump directly from “instruction exists” to “instruction was flushed.”

4. What the correction changes

// Current hazard_unit.v:192, reformatted only
assign FlushE = (lwstall & ~mem_stall_i) |
                (csr_gpr_stall & ~mem_stall_i) |
                PCSrcE | (csr_stall & ~mem_stall_i) |
                exc_inflight_M | wb_redirect |
                flush_pipeline_onehot[1] | stallMUL;

Only data-hazard bubble terms are suppressed during the memory stall. Branch redirects, exceptions, explicit flushes and multiply-related control remain separate causes. The change does not globally forbid FlushE during all stalls. Decode priority remains unchanged in inspected source.

5. Decisive experiment and regression still needed

Capture a counter load in EX, its dependent add in ID, and an older MMIO operation stalled in M. Observe mem_stall_i, lwstall, StallE, FlushE, valid bits, destination register, and counter load/store data. The distinguishing result is that the producer survives the stall and its loaded value reaches the add. Retain pre-change failure and post-change success with identical stimulus and source/snapshot hashes. Repeat for CSR hazards and permitted redirects. This review proposes that experiment; it does not execute it.

6. Assertion scope

The previous proposal mem_stall_i |-> !(lwstall && FlushE) could reject a legitimate redirect when lwstall is also true. Exclude all other permitted flush causes. For the inspected expression, a narrow candidate is:

// Proposed only: bind signals and verify reset polarity before use.
assert property (@(posedge clk) disable iff (!rst_n)
  (mem_stall_i && !PCSrcE && !exc_inflight_M &&
   !wb_redirect && !flush_pipeline_onehot[1] && !stallMUL)
  |-> !FlushE);

This combinational check is close to the implementation and cannot prove instruction preservation alone. Pair it with a temporal property that ID/EX data and control remain stable across a stalled edge without a permitted kill, and that the held instruction resumes. Formal property verification is distinct from lint; no formal proof is claimed here.

08 Engineering Study Notes & Theory

This section provides pedagogical explanations and reference code listings designed for junior engineers and design verification trainees.

Open evidence issues

F-DOC-001 — Mislabelled DSRAM count: proof_report() sets v = proof_dsram_sig and prints it for both dsram_rds and sig. Thus dsram_rds=A459670A is not a read count. The current source label is wrong; only the report is corrected here.

F-EVID-002 — Source/log checksum discrepancy: An independent unsigned 32-bit evaluation of the inspected helper gives 0x785C69AA for seed 0x3A6E0003; Stage 3 prints 0xA459670A. Stage 1's second seed 0x0B0B0CA5 gives 0x0F7193AC, while its final log prints 0x953C6BAC. This is not yet a diagnosed hardware fault. Plain-Language Walkthroughs

Stage 1 walkthrough: The CPU needs a reporting channel before UART itself has been verified. A fixed DSRAM mailbox supplies it. Startup prepares the C environment, firmware writes tagged characters and status, and the testbench observes memory directly. A banner plus successful canary and peripheral checks is useful bring-up evidence; it does not prove UART operation, cold boot or every memory location.

Stage 2 walkthrough: Deliberate noncompletion exercises the timeout path. This watchdog belongs to simulation infrastructure, not an integrated hardware watchdog peripheral. The newer run reaches the deadline, records the expected timeout, freezes module histories, dumps them and reports inverted success. Glossary of Technical Terms

mem_stall_i
Active-high stall signal asserted by LSU when awaiting an AXI/SRAM response, freezing the core pipeline.
FlushE
Control signal clearing the ID/EX pipeline register to insert a NOP bubble into Execute.
StallE
Control signal freezing the ID/EX register to hold an instruction in Execute across stall cycles.
lwstall
Load-use data hazard signal asserting when an instruction in Decode depends on a load in Execute.
Mailbox
Fixed 64-byte DSRAM communication structure (0x0002_0000) for firmware status and console streaming.
Attestation Word
Packed 32-bit value at mailbox +0x1C containing [31:16]=mmio_writes and [15:0]=mmio_reads.
Freeze Buffer
Circular history ring buffer (64 entries) that stops sampling on fatal error to preserve trace history.
APB Slot
One of six slot selections spaced 4 KB apart; register offsets and aliasing require separate checks.
LAYER_FIRMWARE
Caller-selected category 6 for firmware assertions/timeouts; it does not prove root cause or rule out hardware execution defects.
Vacuity Violation
A pseudo-pass condition where a test completes successfully only because stimulus was skipped.
AXI4-Lite
Subset of AXI4 protocol with single-beat transactions, fixed data width, and no burst support.
FNV-1a
Fowler-Noll-Vo non-cryptographic hash function used in firmware to fold DSRAM reads into a signature.

Common Architectural Misunderstandings

  • Misunderstanding 1: “DSRAM stores generate AXI-Lite traffic.” Direct DSRAM accesses (0x0002_0000..0x7FFF) route directly to sram_mux.sv. They never touch the AXI4-Lite crossbar. In these warm suites MMIO generates the observed core AXI traffic. Other SoC masters and AXI SRAM routes exist; this is not a universal fabric restriction.
  • Misunderstanding 2: “Stage 2 passed because the core halted.” Stage 2 passes because the testbench watchdog killed the simulation, not because the core stopped. The dump supports spin-loop execution; a recent-retirement assertion is still needed for automated boundary-liveness checking.
  • Misunderstanding 3: “StallE automatically overrides FlushE.” In the original decode_cycle.v RTL, FlushE took precedence over StallE in an if-else ladder, which permits the instruction-loss mechanism discussed in Section 6 when an ungated data-hazard bubble coincides with a memory hold.
  • Misunderstanding 4: “A simulator exit code of 0 proves verification success.” Do not assume the argument to $finish is a portable process exit-status contract. Check the process result and explicit verdict records. If the testbench calls $finish(0) erroneously, the test passes silently. Verification relies on log string matching and mailbox status.
  • Misunderstanding 5: “Sub-word writes are supported across all peripherals.” Legacy APB3 slaves (UART, Timers, I2C, SPI) lack byte enable (PSTRB) inputs. All MMIO accesses must be strict 32-bit aligned transactions.

Engineering Review Questions

  1. Q: Why does Stage 3 use Timer 1 for the sustained read burst instead of Timer 0?
    A: Timer 0 was already modified during the ping phase. Timer 1 CTRL is reset-initialized and not written by this stage, so zero is expected. CTRL is not the live counter; elapsed time alone should not change it.
  2. Q: Why must FlushE be gated with ~mem_stall_i in hazard_unit.v?
    A: During a memory stall, the instruction in Execute cannot advance. A held load in Execute and its dependent consumer in Decode can keep lwstall high. Suppress that bubble while the load cannot advance; preserve legitimate redirects and exception kills.
  3. Q: What prevents a test from falsely passing if it skips all peripheral accesses?
    A: The vacuity gate TEST_REQUIRE_ACTIVITY() rejects the run if MMIO reads < 14 or distinct slots < 3. The testbench requires nonzero monitor activity and attestation. An exact equality comparator is missing; the retained totals are compared during review.
  4. Q: How does the testbench distinguish between an unexpected crash and an intentional Stage 2 watchdog pass?
    A: The testbench inspects the mailbox test_id. If test_id == 0x0002, it requires that exactly 1 failure finding exists, that the layer is LAYER_FIRMWARE, and that check ID is WATCHDOG_TIMEOUT.
  5. Q: Why is the mailbox located at 0x0002_0000 instead of 0x0001_0000?
    A: 0x0001_0000 is Instruction SRAM (ISRAM), which is read-only from the CPU data port. DSRAM is read-write data memory, allowing bidirectional message passing between core and testbench.
