RISCFORGE SoC Architecture

A microcontroller-class system-on-chip built around a 5-stage RV32IM_Zicsr RISC-V core. This page explains what each block does, why a RISC-V system needs it, and how we built it: the privileged-architecture blocks (CSRs, exceptions, trap/MRET, interrupts), the load/store and hazard logic, and the AXI-Lite/APB peripheral subsystem.

1Goal of the SoC

RISCFORGE is meant to be a complete, self-contained computer on one die. The core runs ordinary RISC-V programs compiled with the standard GNU toolchain. Code and data live in on-chip SRAM. The core responds to hardware events through interrupts and talks to the outside world through serial, timer and GPIO peripherals on standard AMBA buses.

One rule drives the architecture: keep the common case fast and simple, and put the slow parts behind a bus. Instruction fetch and data access go straight to SRAM. Peripheral registers are accessed rarely and can tolerate latency, so they sit behind AXI-Lite and APB, where their extra cycles can't slow down ordinary code.

Designed in this project

The processor core: pipeline, CSR file, trap/MRET commit controller, interrupt arbiter, hazard unit, load/store unit, and the hybrid memory interface. Also the SoC integration: fetch demux, AXI-to-SRAM adapters, SRAM port muxes and the address map.

Integrated open-source IP

AXI-Lite crossbar, AXI-Lite→APB bridge, GPIO and timers from the PULP platform (ETH Zürich / University of Bologna), plus open-source 16550 UART and I2C master cores. Each was adapted to the SoC's bus types and address map.

2System architecture

The diagram shows every path a request can take out of the core. There are three kinds of traffic, and each takes a different route.

Three kinds of traffic

  • Instruction fetch goes to the fetch demux, which picks BootROM or ISRAM by address. It is a single-cycle SRAM read with no bus and no handshake.
  • Loads and stores to DSRAM go through the hybrid memory interface straight to the SRAM. There is no arbitration, and a read costs one wait cycle.
  • Loads and stores to 0x4000_0000–0x4FFF_FFFF are the only accesses that become AXI-Lite transactions. They cross the crossbar, then the APB bridge, then reach the peripheral register.

Why split it this way

A bus access costs several cycles of valid/ready handshaking. If every load and store went over AXI, memory instructions would be the slowest thing the core does, and they are among the most frequent. Peripheral registers are touched rarely and don't care about a few extra cycles, so only they pay the bus cost.

Each SRAM has one physical port shared by a 2:1 mux. The core's direct port has fixed priority, and the bus port waits for it. ISRAM accepts bus writes only when they are marked privileged. The core's own bus accesses are unprivileged, so running software can't overwrite its own code through the bus.

3CSR file (Zicsr)

What it is

The Zicsr extension adds a second register space of up to 4096 control and status registers. They hold the processor's own state rather than program data. Zicsr also adds six instructions that read a CSR and write, set bits in, or clear bits in it, all in one atomic step.

Why RISC-V needs it

Firmware has to control the core itself. It needs to say where traps go, which interrupts are allowed, why the last trap happened and where to return afterwards, and it needs to count cycles for profiling. This state can't live in the 32 general registers, because programs use those freely. It can't live in memory either, because the hardware needs it every cycle. The read-and-set and read-and-clear forms matter because an interrupt arriving between a separate read and write could otherwise lose an update.

How we built it

  • Read in EX, write at WB. A combinational read port gives a CSR instruction its old value in the execute stage. The new value is written only at write-back, once the instruction is certain to commit. A CSR instruction later cancelled by a branch or trap therefore never changes anything.
  • Three write sources with a fixed priority:
    1. Trap entry: mepc, mcause, mtval and mstatus are updated together in one cycle.
    2. MRET: the trap controller restores mstatus through its own port.
    3. CSR instructions: normal writes, filtered through each register's writable-bit mask.
    If a trap and a CSR write arrive in the same cycle, the trap wins and the instruction's write is dropped.
  • Hardware-driven bits. mip is assembled from the peripheral interrupt wires every cycle. mcycle increments on every clock and minstret on every retired instruction.
  • Hazards. Because writes happen late, a CSR read that follows a pending write to the same CSR must wait. The hazard unit handles this (§8).

4Exceptions

What they are

Exceptions are synchronous traps. The instruction itself causes them, at the same point every time the program runs. Examples are an unknown opcode, a misaligned load, or a store to an address with nothing behind it.

Why RISC-V needs them

A processor must never quietly carry on after something it can't do correctly. It must hand control to a handler that can report the error, emulate the operation or recover. ECALL and EBREAK use the same mechanism on purpose: they are how software makes system calls and how a debugger sets breakpoints.

In a pipeline, exceptions must also be precise. With five instructions in flight, the handler must see every older instruction finished, no younger instruction started, and mepc pointing at exactly the instruction that faulted. Otherwise, returning from the handler would repeat or skip work.

How we built it

  • Tag, don't act. The detecting stage attaches a tag to the instruction, and the tag travels in the pipeline registers. If an instruction already carries a tag from an earlier stage, the earlier tag is kept, because that fault happened first.
  • No side effects. A tagged or misaligned load/store never sends its memory request. A branch with a misaligned target does not redirect fetch.
  • Clear the path behind it. While a tagged instruction moves down the pipeline, the younger instructions behind it are flushed.
  • Wrong-path safety. If a taken branch flushes a tagged instruction before it reaches WB, the exception simply disappears. It was never on the real program path.

5Trap controller & MRET

What it is

A small combinational controller at the write-back stage, which is the point where instructions retire. It turns a tagged instruction into a trap, and an MRET instruction into a return from the handler.

Why RISC-V needs it

The privileged specification requires trap entry to be atomic. Saving the return PC, recording the cause, disabling interrupts and jumping to the handler all happen as one step. If software had to do this, an interrupt could arrive halfway through and overwrite the saved state. MRET is the exact inverse, so the interrupted program resumes as if nothing had happened.

How we built it

  • Commit decision. A trap commits when a valid, tagged instruction reaches WB. An MRET commits when a valid MRET reaches WB with no tag.
  • Target address. Traps go to the mtvec base. In vectored mode an interrupt goes to base + 4 × cause, so each source has its own entry and no software dispatch is needed. Exceptions always use the base. MRET goes to mepc.
  • Flush and redirect in one cycle. All four pipeline registers are flushed. The redirect overrides every stall, so fetch starts at the new PC on the next cycle.
  • CSR updates. The controller drives the highest-priority trap-entry write into the CSR file, and a separate port for the MRET update of mstatus.
  • Why only at WB. One redirect point means two stages can never issue conflicting redirects. At WB every older instruction has already finished, so the state the handler sees is exact.

Where mepc points. For an exception, mepc is the faulting instruction, so an ECALL handler adds 4 before returning to skip it. For an interrupt, mepc is the instruction that was interrupted. That instruction never completed and runs again after MRET.

6Interrupts

What they are

Interrupts are asynchronous requests from hardware outside the instruction stream: a byte arrived on the UART, a timer expired, a GPIO pin changed.

Why RISC-V needs them

Without interrupts, firmware has to poll status registers in a loop. That wastes cycles and power, and the response comes late whenever the loop is busy elsewhere. With interrupts, the core does useful work, or idles, and reacts within a few cycles of the event.

How we built it

  • Four gates must be open. The peripheral's own interrupt-enable register (for example UART IER or I2C IEN), the source's mie bit, a priority above the mintprio threshold, and the global mstatus.MIE.
  • Fixed priority. When several sources are pending, the highest cause number wins: the fast local lines (UART, SPI, I2C, GPIO in that order), then external, timer, software.
  • Priority threshold (mintprio, 0x7C0). An interrupt is taken only if its cause number is above the threshold. A handler can raise the threshold so that only more urgent sources can preempt it. This gives CLIC-style priority levels without the area of a full CLIC. The repository includes a complete CLIC IP, but in the integrated SoC its APB slot went to a second timer and prioritisation happens inside the core.
  • Injected at EX. An accepted interrupt converts the instruction in EX into an interrupt trap (mcause bit 31 = 1), and the fetch and decode stages are flushed. EX is the right place because that instruction has not yet touched memory (MEM) or registers (WB), while the older instructions ahead of it finish normally. The interrupt is therefore precise.
  • When it waits. An instruction that already carries an exception is not converted, so synchronous faults are handled first. A multiply or divide in progress is allowed to finish before the interrupt is taken, which keeps the extra delay bounded.
  • Level-sensitive. mip mirrors the wire, so a handler must clear the request at the peripheral (for example GPIO write-1-to-clear status or I2C IACK) before MRET. Otherwise it re-enters immediately.

7Load/store unit & memory router

What it is

The LSU turns RISC-V byte, halfword and word loads and stores into 32-bit memory transactions. Behind it, the hybrid memory interface sends each transaction to DSRAM or to the AXI-Lite bus, depending on the address.

Why RISC-V needs it

RISC-V is a load/store architecture: loads and stores are the only instructions that touch memory. Memory is byte-addressed, but the SRAMs and buses are 32 bits wide. Something has to put a byte into the right lane on a store, pull it out and sign- or zero-extend it on a load, and refuse accesses the hardware can't do in one transfer.

StoreAddress bits [1:0]Byte enables (lane 3 → 0)Matching loads
SB (byte)00 · 01 · 10 · 110001 · 0010 · 0100 · 1000LB sign-extends the byte, LBU zero-extends it
SH (halfword)00 · 100011 · 1100LH sign-extends, LHU zero-extends
SW (word)001111LW passes the word unchanged

Other alignments are caught in the MEM stage before any request goes out, and raise exception 4 (load) or 6 (store). The RISC-V specification allows this, and it keeps the LSU from having to split one access into two.

How we built it

  • DSRAM reads cost exactly one stall cycle. The SRAM has a registered output, so data arrives the cycle after the address. One cycle is the minimum for a synchronous SRAM. Writes return nothing, so they don't stall at all.
  • AXI write FSM. It presents address and data together. The crossbar may accept them in different cycles, so the FSM tracks each channel separately before waiting for the write response. The read FSM sends the address, then waits for data.
  • Same-cycle stall. The stall comes combinationally from the FSM state. The pipeline freezes in the very cycle a bus request appears, and the address and data it drives stay stable for the whole transaction.
  • Errors become exceptions. An unmapped address, or a SLVERR/DECERR bus response, is reported as an access fault on the completing cycle.

Found in SoC-level simulation. An early version registered the stall, so a peripheral load retired before its bus transaction had even started. Another version waited on the wrong ready signal and deadlocked on the first peripheral write, because the crossbar accepts the address a cycle before the data. Both were fixed and are why the handshake is now combinational and tracked per channel.

8Hazard unit

What it is

The hazard unit is the pipeline's traffic controller. Every cycle it decides, for each stage, whether to let the instruction advance, hold it, or flush it into a bubble, and whether an operand should be taken from a later stage instead of the register file.

Why a pipeline needs it

Pipelining overlaps up to five instructions, which creates three kinds of conflict:

  • Data hazards: an instruction needs a result that an older instruction hasn't written back yet.
  • Control hazards: a branch is resolved in EX, after two younger instructions were already fetched from the wrong path.
  • Latency hazards: an operation takes more than one cycle, such as multiply/divide or a memory access.

Without the hazard unit the core would compute with stale values and execute instructions that should never have run.

How we built it

  • Forwarding first. When an older instruction in MEM or WB is writing a register that EX needs, the value is bypassed. MEM has priority because it holds the newer value. Register x0 is never forwarded, since it is always zero.
  • Loads can't be forwarded in time. Load data arrives at the end of MEM, one cycle too late for the next instruction's EX, so the core inserts one bubble.
  • CSR results take a different path. CSR results come from the CSR file rather than the ALU result path, and CSR writes happen only at WB (§3). A dependent instruction therefore waits instead of forwarding.
  • Redirects win. A trap or MRET redirect at WB cancels every stall and flushes the whole pipeline, so the handler starts on the next cycle.

9AXI-Lite interconnect

What it is

AXI4-Lite is the simple subset of ARM's AMBA AXI4 bus. It has five independent channels: write address, write data, write response, read address and read data. Each channel uses a valid/ready handshake, and each transaction moves one 32-bit word, with no bursts and no transaction IDs.

Why the SoC needs it

  • Standard interface. Any AXI-Lite master can reach any AXI-Lite target. Existing IP drops in without custom glue, and bus verification components can be reused.
  • Safe backpressure. Valid/ready lets a slow target hold off the master for as long as it needs, without losing data.
  • More than one master. The core and the bootloader both need to reach memory and peripherals. A crossbar shares the targets between them instead of wiring every pair point-to-point.

How we built it

  • 2 × 3 crossbar. Two master-side ports (the core's MMIO path and the bootloader) and three target-side ports (ISRAM, DSRAM, APB bridge). A rule table decodes each address to one target. An unmapped address gets a decode error, which the core sees as an access fault.
  • Register slices on the address channels. The crossbar cuts every address channel with a spill register. This breaks long combinational paths for timing closure, at the cost of one cycle, and only peripheral accesses pay it.
  • AXI-to-SRAM adapters. These let the bus reach ISRAM and DSRAM through the low-priority side of each SRAM's 2:1 mux. The ISRAM adapter accepts only writes marked privileged by the AXI protection bits and answers everything else with SLVERR. This protects the program image once it is loaded.

Naming. In AXI crossbar terms, the ports that face masters are called slave ports, and the ports that face targets are called master ports. The crossbar is a target to the core and a master to the memories.

10AXI-Lite → APB bridge

What it is

A protocol converter. It takes each AXI-Lite read or write from the crossbar and performs it as an APB4 transfer on one of six peripherals, each owning a 4 KB window.

Why APB, and why a bridge

APB is the AMBA bus designed for peripheral registers. A transfer has two phases: SETUP, where the peripheral's select line rises with a valid address, and ACCESS, where the enable line rises and the transfer holds until the peripheral asserts ready. There is only one transfer at a time and no pipelining. An APB slave interface is a few flip-flops and a read mux, so it is small, low-power and easy to close timing on. Peripherals are accessed rarely and one word at a time, so they don't need more.

Putting the AXI logic in one bridge, instead of in all six peripherals, is what keeps the peripherals cheap.

How we built it

  • Decodes the AXI address against six rules and drives the matching select line.
  • Takes write data and byte strobes from the AXI write-data channel, and returns read data on the AXI read channel.
  • Converts the peripheral's error signal (PSLVERR) into an AXI SLVERR response. An address outside the six windows gets DECERR, and no APB transfer is made.

11APB peripherals

Each peripheral is a block of memory-mapped registers. Firmware configures and uses it with ordinary loads and stores to its 4 KB window, and it can raise an interrupt when something needs attention.

I2C master

0x4000_0000 · slot 0

Function. Drives a two-wire bus (SCL clock, SDA data) shared by sensors, EEPROMs, real-time clocks and power-management chips. Many devices share just two pins.

  • Firmware writes a byte plus a command (START, WRITE, READ, STOP, ACK). The hardware generates the bus conditions, shifts bits, samples the acknowledge and detects lost arbitration.
  • Clock speed is programmable: SCL = PCLK / (5 × (PRE + 1)).
  • Open-drain pads, driven through output-enable signals.
IRQ mip[17] · byte donePRE · CTR · TXR/RXR · CR/SR

Timer 0

0x4000_1000 · slot 1

Function. Two independent 32-bit counters, each with an enable, a 3-bit prescaler and a compare register. When a counter reaches its compare value it resets and raises an interrupt, which gives a steady periodic tick.

  • The compare-match output drives the core's machine timer interrupt. The SoC has no separate CLINT, so this timer is the system tick used for scheduling, timeouts and delays.
  • An overflow interrupt is also available for each counter.
IRQ mip[7] · MTIPVAL · CTRL · CMP

UART (16550)

0x4000_2000 · slot 2

Function. Asynchronous serial port with TX/RX and modem-control lines. It is the console and host link: text output, command input, data logging.

  • Programmable baud-rate divisor, 5–8 data bits, parity, 1–2 stop bits, FIFOs, and line/modem status.
  • Being 16550-compatible means standard, well-known drivers work unchanged.
  • It has the highest interrupt priority, which suits a device whose receive FIFO overflows if it is serviced late.
IRQ mip[19] · RX / TX / statusRBR/THR · IER · LCR · LSR

GPIO × 32

0x4000_3000 · slot 3

Function. General-purpose pins for buttons, LEDs, chip selects and simple handshakes with other chips.

  • Per-pin direction and mode. Inputs are synchronised to the clock to guard against metastability.
  • SET / CLEAR / TOGGLE registers change the chosen pins in a single write, with no read-modify-write. This stays safe even if an interrupt handler is driving other pins at the same moment.
  • Per-pin interrupt on rising edge, falling edge, high level or low level, with write-1-to-clear status.

Timer 1

  • Occupies the APB slot originally planned for the CLIC.
  • Its interrupt outputs leave the SoC as pins and are not routed into the core.
