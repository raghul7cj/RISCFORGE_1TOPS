1. Sign-off is a conjunction

Rev B 20 defines sign-off as the conjunction of the release-level gate set, evaluated once per release on the frozen candidate manifest. G5 requires the per-candidate gates (G2, G4, G6) and each of those requires every run in the manifest to have satisfied the per-run gates (G0, G1, G3). There is no partial sign-off: a design satisfying six of seven gates has six satisfied and one unknown, and an untested gate is reported untested. SPECIFIED

Section 20 restates no gate condition. Predicates, tiers and evidence live only in Table 6.1 (see the gates page). Rev B singles out G1 as carrying the most weight: without it, an unresponsive design yields a run with zero findings and every downstream check trivially satisfied.

4. The RTL identity recipe

There is no .git in the repository or any parent (D-22), so the identity is a hash recipe (Table 21.10, decision D-GR07). Evidence is valid only for the identity that produced it. Figure 2 shows the eight steps; the failure branch matters as much as the flow, because a hash over a partly resolved file set looks authoritative and is not.

Measured values Rev B reports for this repository (SPECIFIED as plan text; to be re-measured, not trusted): the file set is 105 entries and RTL_SOC/soc_subsystem.f has none unresolved, while across all 40 filelists in rtl/ips, 15 carry an unresolvable source entry and 9 contain absolute paths. The anchor hashes are published in facts.yaml:meta.file_sha256. Step 8 combines the existing run-identity tuple (tool version, seed, plusargs) with five new fields: H_rtl, H_filelist, ID-1, ID-2, ID-3.

5. The three identity checks

Table 21.11 defines the checks computed in the same step as the hash. A run carrying a non-zero duplicate_divergent_reachable or unresolved_entries is untested, never pass (D-GR08).

CheckPredicateWhat it catches
ID-1 module-name uniquenessduplicate_divergent_reachable == 0. Group every module declaration in the tree by name; a group whose members differ in content is DIVERGENT, and REACHABLE if some filelist names a member together with a testbenchTwo bodies for one module name where a live flow can compile either
ID-2 resolutionunresolved_entries == 0 over every in-scope filelist, evaluated per flowA filelist that cannot elaborate, or elaborates a subset of what it names
ID-3 portabilityabsolute_path_entries == 0 in every in-scope filelistA flow that only works on the machine that generated its filelist

The motivating case is the duplicate timer.sv: a green result is attributable to neither copy until one body is deleted or the two are byte-identical, and selecting the "right" copy does not escape the check. Rev B treats this as a defect class, not an incident (ID-1 is a precondition of core trust CT-1, and it is an S1 by predicate; see defects).

6. Freeze point F and the re-run matrix

The freeze point F is declared at the exit of P1b. After F, RTL keeps changing; the rules are that no edit is forbidden, no edit is unrecorded (each change note names files, classes from Table 21.12 and phases touched), and no gate verdict transfers across an identity change. Because the last rule needs no judgement of "significance", it is enforceable; the matrix only bounds how much must be re-run, because the bare rule would be unaffordable.

Three precedence rules resolve overlap: a broader trigger beats the narrower class (a change to core_rst_n release timing, to the fast_irq_i or fast_intr_core widths, or to mip_w is Class A wherever it sits); Class X is additive and never removes an obligation; and the class map is generated from the design-element column of the traceability matrix, maintained as a reviewed list until that matrix exists.

Table 21.13 turns the matrix into a cost per gate. Every cell follows from the tiers: a per-run gate is re-run when the run is re-run, a per-candidate gate is re-derived when the manifest changes, and G5 is stamped once on the frozen manifest and so is re-stamped only in P6.
