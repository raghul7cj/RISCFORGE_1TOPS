2. The stall investigation

2.1 Symptom

In component-first run 02 (2026-10-19, XSim 2022.2) the UART bench compiled and elaborated, passed the reset checks of TC1, then stopped advancing at 60 ns, at the first register read, when PSEL rises. The retained notes record memory climbing to 8.5 GB before a kernel fatal. The matrix classified the row INCOMPLETE. One caveat: the roadmap notes that the retained uart/debug/sim_adapter.log ends at ADAPTER before PSEL 60000, so the fatal and memory figures are not corroborated by that file. OPEN

2.3 Mechanism

The adapter converts APB to OBI. In its original form one always_comb block both drives obi_req_o.req and reads obi_rsp_i.gnt (apb_to_obi.sv:111-134 before the fix):

always_comb begin : obi_fsm
  obi_req_o.req    = 1'b0;            // line 112, default
  ...
  ADDR: begin
    obi_req_o.req = apb_req_i.psel;   // line 119
    if (obi_req_o.req && obi_rsp_i.gnt) obi_phase_d = RESP;   // line 121 reads gnt
  end

The UART register file answers with obi_rsp_o.gnt = obi_req_i.req (obi_uart_register.sv:51), a combinational feed-through. Reading gnt makes the block sensitive to it. Per the isolation README, when the block re-runs, the default assignment on line 112 produces a 1 to 0 event on req in XSim even though line 119 sets it back to 1; the responder sees the glitch, updates gnt, and the block is triggered again, without end and without simulation time advancing. A slave raising gnt combinationally from req is allowed by OBI; req must not depend on gnt, and here it does through the sensitivity. Figures 1 and 2 show the loop.

2.4 Why Xcelium did not stall

The isolation README says Cadence Xcelium finishes the same design because it collapses the intermediate procedural write in always_comb and only schedules downstream processes at steady state. I did not find a retained second-simulator experiment that tests this explanation, so treat it as the investigators' account. OPEN Related evidence is mixed: the README cites apb_uart-main/xrun_thorough_1.log as a complete Xcelium run, but that file (dated 2026-09-28) ends 59 PASSED / 10 FAILED, with all ten failures being read-data mismatches (RBR, loopback, FIFO burst bytes reading 0). The current bench comments describe a BFM bug in which an extra clock before the ready check triggered a second OBI read that cleared RHR; the failures look like that, but I did not verify it. The run 02 README separately declines to accept an earlier "Xcelium 69/69" claim because no source identity was captured.

3. The fix and the zero-timing-change argument

The fix moves the request out of the procedural block into a continuous assignment, and the block no longer drives req:

assign obi_req_o.req = (obi_phase_q == ADDR) ? apb_req_i.psel : 1'b0;   // line 111
...
ADDR: if (apb_req_i.psel && obi_rsp_i.gnt) obi_phase_d = RESP;

Why timing is unchanged. In the original, req is psel in state ADDR and 0 in every other state (RESP and the default arm both leave the line 112 default). The new assignment gives exactly the same function of phase_q and psel. The next-state condition req && gnt in ADDR becomes psel && gnt, which is equal because req = psel there. So every cycle-level output (req, pready, next phase) is the same Boolean function, and the cone is the same two-input logic. This is my reading of the code and the README's argument. EXISTS No formal equivalence run or gate-level comparison is retained, and the 69/69 run is the dynamic evidence. OPEN

5. The 30 test cases

The bench apb_uart-main/rtl/tb_apb_uart_thorough.sv is directed, self-checking and non-UVM. It drives apb_uart through an APB BFM, uses masked === comparisons, sticky flags for single-cycle events, concurrent APB protocol assertions, and a 20 ms global watchdog. Check counts per test case below are counted from the retained xsim.log of the 2026-10-31 run (they sum to 69).

6. Rev B 15.7 scenarios and mapping status

Rev B 15.7.3 defines 29 SoC-level checks, DEV-0401 to DEV-0429. All are CFG-S only (full SoC), invalid in the core-only and fabric-only configurations, and none needs a UART VIP because MCR[4] closes the loop internally (the plan's own prose is inconsistent about "nine" pad-level checks; the roadmap flags it). 8. What this page does not claim

  • It does not claim the UART is verified at SoC level, or that any Rev B 15.7 check is closed.
  • It does not claim XSim is wrong or Xcelium is right; the code pattern is the cause of the loop in XSim, and the Xcelium explanation is unverified.
  • The overlap column in section 6 is my reading, not a traceability record.
  • The delta diagram is illustrative; no retained trace gives the exact event order.
