1. Layered approach

Rev B draws one scope line for all peripherals (Rev B 15.1). At SoC level the plan verifies two things only: connectivity (decode to the right instance, protocol conformance from the load/store unit to the register file, well-formed response, interrupt line reaching the intended mip bit, reset release) and end-to-end flows (a transaction started through the fabric produces the architectural side effect). Device internals, such as framing, command decoding and bit timing, are inherited from each IP's own bench, and an inherited claim is only valid when a named artefact and IP source hash back it (Rev B 15.1, mechanisms M-A, M-B, M-C; falsifiers FALS-1 to FALS-4). SPECIFIED

Closure is tracked in five layers, which is also how the tracker sheet Peripheral_Closure is organised. Figure 1 lists them; the first is the "component bench" column and the other four are SoC-level.

2. Verification environment

Figure 2 shows the target environment that Rev B 15 describes for a SoC-level peripheral check: firmware on the real core, the fabric, one APB slot, the device, and the verification components around them. The device VIP is a pin-level model of whatever sits on the pads (I2C EEPROM, SPI flash, serial peer); for UART the internal loopback (MCR[4]) removes the need for one (Rev B 15.7.3). The environment as a whole is SPECIFIED. Pieces that EXIST in the repository are the passive monitors and checker self-proof (matrix rows MON-01, CHK-01), the I2C EEPROM and SPI flash models (MEM-SLV), and stage proofs that ran firmware through the real fabric (STG-02, STG-03); a per-device register model and scoreboard is not retained as a run.

4. Full-window offset sweep and error policy

Rev B 15.3 requires one word read and one word write at every word offset of the APB decode space (0x4000_0000 to 0x4000_5FFF), 6144 offsets, each recorded for response code, read data and register-model state change. The outcome must reconcile: 3603 offsets resolve to a register, 2029 are unimplemented inside decoded windows and 512 fall in the GPIO hole (3603 + 2029 + 512 = 6144). SPECIFIED The key point is that four of six instances receive only part of PADDR, so offsets above their decode range alias onto real registers rather than reading zero.

Reserved and unimplemented bits are checked, never masked (decision D-90); each register descriptor carries three masks and the read-back comparison uses all three. The error policy (Rev B 15.4, Table 15.5) replaces a rule set that contradicted the RTL. Rows that matter for planning:

  • X3 byte-lane write: non-conforming on all six instances, by four distinct mechanisms. None has a working PSTRB path.
  • X4 write to a read-only register must give PSLVERR: conforming on the UART only.
  • X5 write to an unimplemented offset must give PSLVERR: conforming on GPIO only; vacuous on UART (no unimplemented offset).
  • X8 zero-lane write to a decode hole returns OKAY in the bridge instead of DECERR (one edit, axi_lite_to_apb.sv:319 per Rev B).
  • X13 concerns the AON watchdog only, so the executable minimum on the integrated instances is 11 of 13 rows (PC-3).

Rev B predicts today's response for these and records it as a defect, so a green X3, X4, X5 or X8 is a recorded defect, not a pass. These are plan statements; no retained run executes the sweep or the policy rows (matrix mapping is NOT MAPPED throughout). OPEN

5. Timing oracle for timed devices

A pin oracle is not applicable to a timer: the timer has no status latch, only combinational levels qualified by TIMER_CTRL.EN. Rev B 15.5 therefore replaces it with a cycle-accurate counter-and-compare reference model built from only the predicted register values and the count of clk_i rising edges, never reading a DUT net. SPECIFIED

  • Tick period is 1 cycle when TIMER_CTRL[5:3] is 0 and that value plus 1 otherwise, so periods 1 to 8 cycles; all eight are exercised.
  • Tolerance is 0 cycles. A one-cycle disagreement is a finding (PATH-0301 to PATH-0305).
  • Overflow is reached by a directed write of 0xFFFF_FFFF to TIMER_VAL followed by one tick, because counting to it takes 2^32 ticks.
  • A write to TIMER_CMP clears TIMER_VAL on the next cycle; compare or overflow clears it on the following cycle.
  • PATH-0307 mutates the model's tick period by one cycle and requires PATH-0301 to report; the model is mutated, never the DUT.

All obligations are in clk_i cycles; the clock frequency in hertz is TBD (D-92). The retained Timer 0 and Timer 1 results (9/9, 52/52) are functional checks, not this oracle. OPEN

7. Evidence versus requirement

The verification README states the rule: a PASS in a component record does not automatically close a Rev B check ID; the check-to-test mapping and the SoC-level scope must also be established. Figure 3 applies that rule. Each retained result on the left supports only part of the obligations on the right; the dashed boxes have no retained evidence at all.

Figure 4 reproduces the layer statuses from the PERIPHERALS list in Verification/status/build_tracker.py, which generates the Peripheral_Closure sheet (I read the same values from the workbook with openpyxl). 9. What this page does not claim

  • No percentage of requirements is closed. Evidence is "PASS for a stated boundary".
  • Rev B scenario counts are plan content (SPECIFIED); none is mapped to a retained check, and the plan itself leaves some counts TBD (D-87, D-93).
  • Counts of GPIO and Timer 0 rows are my row counts, not totals stated by the plan.
  • Fabric-side verification (bridge, crossbar, timeout monitor) is on fabric verification and the fabric-to-peripheral view; device design is on SoC peripherals and SoC fabric. Start from the index.
