Core Verification Overview

What verification of the RV32IM_Zicsr five-stage core exists in the repository today, what Rev B requires before the core can be trusted, and the one core defect (DEF-001) found so far. Written for engineers who need to know which core claims have evidence behind them.

1. Summary of the position

  • The only core-level evidence with a result attached is a RISCOF report of 47 entries (46 Passed, 1 Failed). It carries no RTL identity, and the DUT directory its plugin names does not exist in the tree (section 2).
  • No lock-step comparison, no core assertions and no formal goals exist. Rev B specifies all three (Rev B 16, 21.2).
  • No dedicated hazard-unit test exists. The Stage 3 firmware proof exercises the DEF-001 sequence indirectly.
  • Phase P1a (core trust) is NOT STARTED and its entry criteria are not met (Verification/status/PHASE_STATUS.md, phase table).
Verification evidence in this project is "PASS for a stated boundary". Nothing on this page is a percentage of requirements verified.

4. Core-trust condition CT-1..CT-5

Rev B 21.2 makes core trust a set of phase-entry conditions, not a gate. Every firmware-observable result in the plan runs on the core, so a core defect would corrupt all of them in the same direction. Figure 2 shows the five conditions and where each stands; the table gives the predicates.

5. DEF-001: the core defect found by the Stage 3 proof

DEF-001 is the only core (C-DUT) defect in Verification/status/defects.csv. Its status is FIXED-UNVERIFIED: the fix is in the current riscv_core/rtl/hazard_unit.v but no regression test exists.

  1. Symptom. In the Stage 3 firmware run, proof_mmio_reads reached 12 instead of 14 and proof_mmio_writes held a corrupted 0x00010001 instead of 4 (Stage 3 README, section 4).
  2. Cause. An MMIO access held the pipeline with mem_stall_i. A DSRAM load in EX whose result the next instruction needed raised lwstall. FlushE included lwstall ungated, and in decode_cycle.v the flush has priority over the stall, so the held load was turned into a bubble and never executed. The failing sequence appears in stage3.dis at 0x109c4 to 0x109cc: lw a7,0(a0), lw a5,736(a2), addi a5,a5,1.
  3. Fix. hazard_unit.v:192 now masks lwstall, csr_gpr_stall and csr_stall with ~mem_stall_i inside FlushE.
  4. Owed. A directed regression that fails on the old RTL and passes on the fixed one (ACT-010), a second-person closer, and a CT-1/2/3 re-run because the change is Class A under Rev B Table 21.12. ACT-007 asks that the Stage 3 proof be tied to the current file by hash.

The regression design, with expected and failing behaviour, is on Hazard unit verification.

6. What this page does not claim

  • It does not say the core is correct or incorrect. It says which checks exist.
  • The 46-of-47 figure is a count from one retained report, not a compliance percentage, and it is not tied to current RTL.
