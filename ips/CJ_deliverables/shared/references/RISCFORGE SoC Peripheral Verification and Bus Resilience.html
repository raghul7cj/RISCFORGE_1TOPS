1Executive Summary

In a microcontroller-class SoC, peripherals and interconnects are the primary source of unpredictable timing, bus hangs, and deadlock risks. The RISCFORGE SoC combines high-throughput native SRAM paths with an AXI-Lite and APB peripheral fabric. To guarantee rock-solid runtime execution, the subsystem incorporates three layers of verification and resilience:

1. Active Fault Containment

Independent APB Timeout Monitors sit on each of the 6 APB slots, and an AXI-Lite Timeout Monitor sits at the CPU master port. If any slave permanently deasserts its ready signal or deadlocks, the monitors abort the stalled transaction with a precise bus error (SLVERR) and cleanly drain orphan downstream transactions without violating AXI/APB bus protocols.

2. System Recovery & Register Proof

An OpenTitan-derived Always-On Watchdog Timer (AON Timer) provides non-maskable bark interrupts and bite system resets. The full peripheral register suite (57 mapped registers across 6 APB peripherals) is tested end-to-end with bare-metal RISC-V firmware (regtest.c) executing after a genuine SPI-flash cold boot.

2Always-On Watchdog Timer (AON Timer / WDT)

The RISCFORGE SoC integrates the OpenTitan Always-On (AON) Timer IP (ips/aon_timer/rtl/aon_timer.sv), which runs continuously in the always-on power and clock domain (clk_aon_i). It provides two independent hardware timing facilities:

  • 64-bit Always-On Wakeup Timer: Driven by a 12-bit programmable prescaler (WKUP_CTRL.PRESCALER) and compared against a 64-bit threshold (WKUP_THOLD_HI/LO). Generates a wakeup request (wkup_req_o) and interrupt (intr_wkup_timer_expired_o).
  • 32-bit Watchdog Timer with 2-Stage Escalation: Increments continuously while enabled. Generates a first-stage warning Bark Interrupt (intr_wdog_timer_bark_o / nmi_wdog_timer_bark_o) when reaching WDOG_BARK_THOLD, followed by an uncatchable Bite System Reset Request (aon_timer_rst_req_o) when reaching WDOG_BITE_THOLD.

Watchdog IP Operational Architecture

Dual Clock & Reset Domains: The register interface and SECDED integrity checks operate on the high-speed system bus clock (clk_i, rst_ni). The actual timing counters and comparator logic run continuously in the isolated always-on domain (clk_aon_i, rst_aon_ni), surviving system core resets and low-power sleep modes.

Asynchronous CDC & Write-Once Protection: Register programming is synchronized across domains via OpenTitan's prim_reg_cdc synchronizer. Once locked by writing 0 to WDOG_REGWEN, hardware locks WDOG_CTRL and threshold registers against any subsequent modification until the next full system reset.

When Does the Watchdog Kick In? — Operational Failure Scenarios

The watchdog timer evaluates hardware conditions on every cycle of clk_aon_i. It is engineered to detect and contain the following concrete failure modes:

Scenario 1: Firmware Spinlock & Infinite Polling Loops

When software enters an un-terminated polling loop (e.g. waiting on a non-responsive peripheral ready flag), the main scheduler fails to execute the watchdog service routine (petting). The counter reaches WDOG_BARK_THOLD to interrupt the core, and subsequently WDOG_BITE_THOLD to enforce a hardware system reset.

Scenario 2: Interrupt Flooding & Task Starvation

If a peripheral asserts a continuous spurious interrupt storm that starves background tasks or lower-priority threads from executing, the watchdog pet interval is breached. The Bark NMI preempts all standard IRQs, giving firmware a dedicated non-maskable vector to quarantine the offending peripheral.

Scenario 3: Dynamic Threshold Jump Condition

Comparators evaluate count >= threshold rather than equality (==). If software dynamically reduces WDOG_BARK_THOLD or WDOG_BITE_THOLD below the active counter value, the trigger condition evaluates true immediately on the next clock edge, avoiding a 232-cycle rollover dead-zone.

Scenario 4: Security Life-Cycle Escalation Override

When the hardware security controller asserts lc_escalate_en_i[0] = 1, the watchdog timer bypasses all software disable bits and WDOG_REGWEN locks, forcing the watchdog counter to run continuously to ensure tamper-resistant system reset escalation.

Hardware Bark vs. Bite Escalation Mechanics

The core counter increment and trigger evaluation logic in aon_timer_core.sv enforce deterministic mathematical escalation:

  • Stage 1 — Bark NMI Warning: When wdog_count >= WDOG_BARK_THOLD, hardware asserts intr_wdog_timer_bark_o and nmi_wdog_timer_bark_o, latching INTR_STATE.wdog_timer_bark = 1. Software is provided a deterministic grace window:
    ΔTgrace = (WDOG_BITE_THOLD − WDOG_BARK_THOLD) / fAON
    During this window, the CPU can capture diagnostic crash logs, flush buffers to non-volatile storage, or perform an emergency recovery reset.
  • Stage 2 — Bite Hard System Reset: If the counter increments to wdog_count >= WDOG_BITE_THOLD without being serviced, hardware triggers aon_timer_rst_req_o = 1. This drives an internal sticky reset latch (rst_req_d = wdog_reset_req_o || rst_req_q) that holds the system in hard reset until an external power-on reset pulse (rst_aon_ni = 0) is applied.
  • Petting Window Protocol: To prevent triggers, software must periodically write 0x0000_0000 to WDOG_COUNT within interval Tpet < WDOG_BARK_THOLD / fAON. Notably, WDOG_COUNT is exempt from the REGWEN lock, allowing normal petting even when configuration registers are permanently locked.
  • Sleep Mode Gating: If WDOG_CTRL.pause_in_sleep = 1 and the SoC power manager asserts sleep_mode_i = 1, watchdog counting pauses during legitimate deep-sleep states and resumes seamlessly upon wakeup.

3Peripheral Register Access Test (RegTest)

The peripheral register access testbench (soc_regtest.f / soc_regtest_tb.sv) executes bare-metal firmware (regtest.c) running directly on the 5-stage RV32IM core. Unlike unit-level IP tests, every register access traverses the full physical datapath:

Core Fetch → Execute LSU → hybrid_mem_interface → axi_lite_xbar → axi_lite_to_apb Bridge → APB Slave Registers

Hardware Cold Boot Sequence & Trampoline Redirection

The SoC executes a deterministic hardware boot state machine in bootloader.sv before code execution starts:

1. Memory Zeroing & Flash Power-Up

S_CLEAR_SRAM: Post-reset hardware zeroing of 16,384 words (64 KB total across ISRAM and DSRAM) to clear residual uninitialized memory state.
S_FLASH_CMD: Configures internal SPI master (CLKDIV=4) and enforces a 30,000-cycle power-up hold delay (tPU) for external flash analog settling.

2. DMA Preload & Core Release

S_READ_FIFO: Executes burst DMA reads from external SPI flash into ISRAM (0x0001_0000) and DSRAM (0x0002_0000).
S_RELEASE_CORE: Deasserts core_rst_n = 1. CPU fetches from BootROM (0x0000_0000), executing a 1-instruction trampoline (jal x0, 0x00010000) into _start.

Root Cause Analysis (RCA) of Discovered Hardware Bugs

Hardware RTL Bugs Identified & Isolated: Simulation of soc_regtest_tb with Cadence Xcelium 24.09 uncovered two critical integration bugs:

  • Timer Comparator Readback Inversion Bug: In ips/apb_timer/apb_timer/timer.sv, the comparator logic clears the comparator register match state unconditionally when CTRL.EN == 0. As a result, Phase 3 bit-bash and Phase 5 checks failed because T_CMP could not retain programmed values while disabled. Fix: Decouple configuration register storage from counter enable gating.
  • Spurious Uninitialized Timer IRQ Flooding (2,311 Traps vs 15 Expected): During cold reset and pattern writes, timer.sv continuously asserted its IRQ line while CTRL.EN = 0. With global interrupts enabled, the core was flooded with 2,296 spurious interrupts. Fix: Gate interrupt output with CTRL.EN & CTRL.IRQ_EN.

4Bus Timeout Monitors & Fault Resilience

In a standard bus fabric without timeouts, a slave peripheral that hangs or leaves PREADY permanently low freezes the entire SoC pipeline, deadlocking the CPU in an unrecoverable wait state. RISCFORGE implements a comprehensive two-tier timeout monitor architecture (ips/bus_monitors/):

When Do the Bus Monitors Kick In? — Failure Taxonomy

The bus monitors continuously track transaction durations across the interconnect. They actively trigger under four distinct failure conditions:

Case A: Defective Slave Permanent Stalls (PREADY Stuck Low)

In APB4, a transaction enters the ACCESS phase with PSEL=1, PENABLE=1 and remains locked until PREADY=1. If a peripheral's internal FSM deadlocks, its clock gate fails, or its power rail drops, the APB monitor fires after TimeoutCycles (16 cycles for I2C/TMR/UART/GPIO). It injects PREADY=1, PSLVERR=1, PRDATA=0xDEAD_BEEF, unblocking the bridge immediately.

Case B: SPI FIFO Boundary Stalls & Passive Sniffing Protection

The PULP SPI Master deasserts PREADY when reading an empty RXFIFO or writing a full TXFIFO. In the SPI RTL, FIFO pop logic is driven by spi_data_rx_ready = rxfifo_rd_access & PREADY. The APB monitor passively sniffs apb_req_i without overriding the peripheral's internal lines. On timeout, only the bridge is answered; when PSEL drops, the slave sees an aborted transfer, preserving all unread FIFO contents without data loss.

Case C: AXI Crossbar Arbitration & Bridge Routing Lockups

If the 2SLV → 3MST AXI-Lite crossbar encounters an unrecoverable routing conflict or an unmapped aperture freeze, the CPU-side AXI-Lite monitor fires (64 cycles for SRAM, 131,072 cycles for APB). It injects RESP_SLVERR (2'b10) and RDATA=0xDEAD_DEAD back to the CPU master, preventing core LSU pipeline deadlock.

Case D: Fast-Fail on Broken Slaves & Auto-Recovery (blocked_q)

To prevent repeated timeout delays when firmware retries a broken peripheral, the APB monitor latches blocked_q = 1 upon firing. Subsequent accesses to the dead slot fail immediately in cycle 0. The latch automatically clears only when the peripheral recovers and presents PREADY=1 during an unselected, idle cycle (!PSEL && PREADY).

Timeout budgets are strictly nested to ensure localized fault containment and prevent false triggers:

AXI-Lite 3-State Protocol Invariant Cleanup FSM

Under AMBA AXI specifications, a master cannot withdraw VALID once asserted until READY responds. Naively aborting an access by dropping VALID causes permanent crossbar deadlocks. The AXI timeout monitor resolves this through a 3-state cleanup FSM (StPass → StInject → StDrain):

Blocked State Fast-Fail & Auto-Recovery (blocked_q)

To prevent software retry loops from incurring repeated full timeout delays on a permanently stuck slave, the APB monitor latches blocked_q = 1 upon firing. Subsequent accesses to the dead slot fail immediately in cycle 0 of the ACCESS phase. The latch automatically clears only when the peripheral recovers and shows PREADY=1 during an idle, unselected bus cycle.

Firmware Bus Error Recovery & Trap Decoding

When an APB or AXI monitor injects SLVERR, the RV32IM core executes a precise trap. The firmware trap vector decodes the faulting MMIO address and skips the instruction to resume execution:

// Bare-metal RISC-V MMIO Exception Handler (montest.c / crt0.S)
void trap_handler(void) {
    uint32_t mcause, mepc, mtval;
    __asm__ volatile("csrr %0, mcause" : "=r"(mcause));
    __asm__ volatile("csrr %0, mepc"   : "=r"(mepc));
    __asm__ volatile("csrr %0, mtval"  : "=r"(mtval));

    if (mcause == 5 || mcause == 7) {
        // Load (5) or Store (7) Access Fault generated by Bus Monitor SLVERR
        // mtval contains the exact 32-bit faulting MMIO register address
        log_bus_fault(mcause, mtval, mepc);

        // Advance mepc past the 4-byte faulting instruction to safely continue
        __asm__ volatile("csrw mepc, %0" :: "r"(mepc + 4));
    }
}

5Cadence Xcelium Simulation & Test Flow

All verification suites are compiled and simulated using Cadence Xcelium 24.09-s001 on CentOS. Both SoC-level testbenches (soc_regtest_tb and soc_montest_tb) automatically dump complete hierarchical simulation databases (*.shm) during execution without requiring additional command-line probe switches.

1. Always-On Watchdog Timer Verification (AON WDT)

The standalone directed testbench exercises all 14 registers, TL-UL bus integrity, alert channels, bark/bite thresholds, and CDC crossings under both synchronous and integer-divided clock frequencies:

# Navigate to AON Timer IP verification directory
cd ips/aon_timer

# Run standard synchronous test (clk_aon_i = clk_i)
xrun -f tb_watchdog_full.f

# Run asynchronous CDC test with 4x clock divider on clk_aon_i
xrun -f tb_watchdog_full.f +define+WDT_AON_DIV=4

2. Peripheral Register Access Testbench (RegTest)

The register test runs bare-metal C firmware (regtest.c) compiled with the GNU RISC-V toolchain (riscv64-unknown-elf-gcc), linked to ISRAM and DSRAM images, and converted into flash memory files (regtest_flash.mem). The testbench simulates a cold hardware boot from the Infineon S25FS512S SPI flash model before releasing the CPU:

# Step 1: Build firmware binary, header parameters, and SPI flash image
cd ips/mem_files/regtest
python3 build.py

# Step 2: Execute cold boot and register verification from RTL_SOC
cd ../../RTL_SOC
xrun -f rtl/soc_regtest.f              # standard run, writes soc_regtest_tb.shm
xrun -f rtl/soc_regtest.f +VERBOSE     # verbose mode: log all PASS events

3. Bus Timeout Monitor Verification (MonTest)

The bus monitor test compiles directed firmware (montest.c) that coordinates with soc_montest_tb.sv via the DSRAM mailbox (0x0002_0000). The testbench applies hardware forces to peripheral PREADY signals and bridge response logic to verify timeout aborts, fast-fail states, and orphan cleanup:

# Step 1: Build monitor test firmware and flash memory image
cd ips/mem_files/montest
python3 build.py

# Step 2: Execute bus timeout monitor verification from RTL_SOC
cd ../../RTL_SOC
xrun -f rtl/soc_montest.f              # standard run, writes soc_montest_tb.shm
xrun -f rtl/soc_montest.f +VERBOSE     # verbose mode: log individual monitor fires
