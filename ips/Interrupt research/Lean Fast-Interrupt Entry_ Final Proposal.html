Lean Fast-Interrupt Entry for an In-Order RV32IM Core: Interrupt-Transparent Multi-Cycle Units and a Bank-less Background Context Save

Final proposal (Option A of three, see Options at the end) · two milestones, each a separate paper · M1 ≈ end Nov 2026 · M2 ≈ end Mar 2027

Introduction

Hard real-time firmware depends on how fast and how predictably a core reaches the first instruction of an interrupt handler. We study the 5-stage RV32IM_Zicsr core of the RISCFORGE SoC and propose two scoped microarchitectural changes, each judged by cycles or area: M1 makes the multi-cycle divider and multiplier interrupt-transparent, so entry latency no longer depends on the interrupted instruction or its operands; M2 saves interrupt context in the background without a shadow register bank.

Motivation

  • Software context save costs about 33 cycles on baseline CLINT/CLIC cores; CV32RT's fastirq reaches 6 cycles [1].
  • That result needs a second register bank (about +36% register-file area, +21% ID-stage area [1]) and was measured on uncontended zero-wait memory.
  • Our core injects interrupts at EX and blocks acceptance while the divider runs, so latency depends on the interrupted instruction. Open cores show the same effect: Ibex documents divide stalls of up to 37 cycles [5].

Literature

  • CV32RT / fastirq [1]: CLIC + register banking + background stacking; the reference point. It states the hardware cannot know which caller-saved registers matter, so it saves all.
  • CLIC spec [2], Mao et al. [7], Balas & Benini [6]: levels, thresholds, vectoring, automatic stacking on RISC-V.
  • Interruptible divide [4]: Arm Cortex-M3 reportedly abandons and restarts DIV on interrupt (verify in the TRM). It is known practice, so M1 differentiates on formal proofs and a progress condition, not on the idea.
  • Nemesis [3]: interrupt latency leaks the timing of the interrupted instruction; a side benefit of M1.
  • Gap: no open, small-core design that gets bank-less hardware context saving with a formally checked bound. Run a one-week literature sweep before claiming this.

Background

Machine-mode only core; interrupts are accepted in EX (valid_E & irq_pending & ~exc & ~stallMUL), tagged, and committed at WB, which flushes the pipeline and redirects to mtvec (vectored: base + 4·cause). mepc holds the interrupted PC, so the instruction re-executes after mret. mintprio (0x7C0) gates by cause number. DSRAM has one physical port behind a 2:1 mux where the core has fixed priority; peripherals sit behind AXI-Lite/APB with a frozen pipeline during MMIO.

Problem

  1. M1: a divide in flight delays interrupt acceptance by up to a full divide time, making entry latency data-dependent.
  2. M2: entering a handler costs about 30 cycles of software stacking; banked hardware fixes it but costs registers and area that a tape-out-oriented small core may not afford.

Hypothesis

  • H1 (M1): abort-and-replay makes worst-case entry with a divide or multiply in flight equal to the no-op case plus a small constant, at a cost of a few hundred gates.
  • H1b (M1): entry latency becomes statistically indistinguishable across operand classes for which the baseline's latency differs (the channel of [3]).
  • H2 (M1): if interrupt inter-arrival time Tmin exceeds ISR time plus one divide time, every divide completes (progress lemma).
  • H3 (M2): a background save engine with write-interlock reaches entry near the 12-cycle Cortex-M4 reference in [1], from about 33 software cycles.
  • H4 (M2): its added state is a fraction of a 16×32-bit bank (512 flops), before the optional mask table.

All are targets to falsify; none has been measured yet.

Framework

One thesis, two steps: bounded and cheap interrupt entry. M1 removes the pipeline-side variability; M2 removes the software-side cost. M2 reuses M1's abortable divider so its bound can be proven.

Methodology

M1. (1) Read the divider and multiplier FSMs and record their real latencies. (2) Add one shared abort interface: on accept, drop the operation without writing rd. (3) Prove replay gives the same result as an uninterrupted run. (4) State the progress condition. (5) Show baseline entry latency differs by operand class, then that it no longer does.

M2. (1) Software baseline B0 on the current core. (2) Add the save engine that reads registers in a fixed order and stacks them. (3) Add the write interlock and LSU stack-range check. (4) Add SRAM arbitration with a starvation bound. (5) Stretch: mask table and post-link analyzer. Skip a full banked reimplementation; use [1]'s published numbers as the reference.

Implementation

  • M1: shared abort port on the divider and multiplier, irq_accept_E no longer gated by stallMUL, optional retry-limit CSR.
  • M2: ctx_save_engine.sv, register-file snapshot port, interlock in the hazard unit, stack-range compare in the LSU, arbiter tweak, vector stub jal isr_c; mret so handlers are plain C.
  • Tools: Verilator, SymbiYosys [8], Yosys, Spike, RISCOF, riscv-dv, PYNQ-Z2 for FPGA.

Experimental

RTL simulation for cycle counts, formal runs for proofs, Yosys synthesis for gate counts, and an FPGA run to confirm behavior on hardware. Baselines are the current core (B0) and, for M2, the published numbers from [1]. Profiling is a means of validation, not a result.

Benchmarks

  • M1: divide/multiply-heavy loop with a periodic timer interrupt at varied periods (one below the progress condition), plus two operand classes with different baseline divide times for the leakage test.
  • M2: short ISRs (GPIO toggle, UART RX, timer tick, I2C byte), a load-heavy ISR to stress SRAM contention, and back-to-back interrupts.
  • Regression: CoreMark and a few Embench-IoT kernels, RISCOF.

Validation

  • Formal: M1 replay equals uninterrupted result, no double write-back, and entry latency identical for two runs differing only in operands (bounded two-copy check); M2 each stacked word equals the register's value at trap entry, interlock never lets an unsaved register be overwritten, and IRQ-taken implies first handler fetch within K cycles under stated bus assumptions. The baseline is expected to yield a counterexample; the new design a proof.
  • Co-simulation: random programs and ISRs (riscv-dv) against Spike; RISCOF still passes.
  • Assertion quality: add cover properties and mutation-test the assertions so proofs cannot pass vacuously.

Results

No results yet. Acceptance criteria:

  • M1: worst-case entry with a divide or multiply in flight within a small constant of the no-op case; operand classes indistinguishable (|t| < 4.5) where the baseline is distinguishable; formal proofs close; area cost stays small.
  • M2: entry at or near 12 cycles versus roughly 33 for software; added state well under a 512-flop bank; formal bounds close.
  • If the stretch mask table is not reached, the paper stands on the bank-less engine alone.

Contributions

  1. M1: a uniform abort-and-replay interface for multi-cycle units with a progress condition, a formal replay-correctness proof, and operand-independent interrupt latency (closing the channel of [3] for these units), with measured cycle and area cost.
  2. M2: a bank-less background context-save engine with write-interlock and contention-aware arbitration, with formal bounds and an area-versus-cycles comparison against published figures.
  3. Open RTL, assertions and scripts for both.

Significance

Small tape-out-oriented cores cannot always afford banked register files. A proven, cheap route to fast, predictable interrupts widens the set of real-time systems a minimal RISC-V core can serve. M1 also closes, for the divider and multiplier, the interrupt-timing channel described in [3].

Conclusion

The plan replaces "recreate and beat" with two small, checkable changes to one core, each with a metric, a proof obligation and a fallback. M1 delivers a short paper by late November; M2 builds on it for a fuller paper by late March.

Options considered

Option A (recommended): interrupt-transparent units + bank-less save.
  • M1: shared abort/replay for divider and multiplier, progress lemma, leakage closure. M2: bank-less background context save with write interlock.
  • Metrics: cycles and area. Proofs: replay correctness, snapshot correctness, bounded entry.
  • Venues: TCAS-II, then TVLSI. Risk: medium; M1 novelty rests on the leakage hook.
Option B: bounded interrupt arbitration + mask-guided stacking.
  • M1: hybrid priority/round-robin arbiter on your CSR-based interface, with a formal per-source wait bound and area-per-source scaling (the CLIC in [1] spends about 176 GE per source on configuration registers). M2: bank-less save with the clobber mask promoted to a core contribution.
  • Lowest microarchitecture risk and continues your existing interrupt work. Novelty moderate; M2 needs a post-link analyzer.
  • Venues: TCAS-II, then TVLSI.
Option C: constant-latency interrupts as a timing-channel defense.
  • M1: leak-free divider/multiplier with a noninterference proof and a Nemesis-style demonstration [3]. M2: extend to bus and SRAM contention and quantify the price of constant time against worst-case latency.
  • Strongest hook and highest risk: it needs a threat model, and the win is security rather than fewer cycles, so it only partly fits your cycles/area rule.
  • Venues: security- or architecture-oriented journals; check scope first.
