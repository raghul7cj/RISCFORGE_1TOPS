In-Core Zicsr Interrupt Subsystem: Architecture & Proposal

A Tightly-Coupled, Interconnect-Isolated Interrupt Subsystem for the RISCFORGE 5-Stage RV32IM_Zicsr Core
Target Venues: IEEE Embedded Systems Letters (ESL) & IEEE TCAS-II Express Briefs · Prepared for Silicon Sign-off & Academic Publication

1 · Executive Summary & Research Motivation

In resource-constrained edge computing SoCs where an in-order RISC-V processor is co-located with high-throughput streaming accelerators (e.g., a 1TOPS neural processing unit or hardware cryptographic engine), interrupt servicing determinism is a critical figure of merit. Modern RISC-V systems universally adopt one of two standardized interrupt controllers: In resource-constrained edge computing SoCs where an in-order RISC-V processor is co-located with high-throughput streaming accelerators (e.g., a Simple Accelerator DMA Master / cryptographic engine), interrupt servicing determinism is a critical figure of merit. Modern RISC-V systems universally adopt one of two standardized interrupt controllers:

  • The Bus-Mapped Platform-Level Interrupt Controller (PLIC): Standardized for application processors, but forces the core to execute memory-mapped (MMIO) claim and completion load/store transactions across shared system crossbars (AXI4-Lite / APB). This introduces 27–43 bus cycles of latency and injects arbitration stalls into concurrent accelerator DMA bursts.
  • The Core-Local Interrupt Controller (CLIC / Smclic): Reduces hardware entry latency to 6–8 cycles, but requires ~6.8 kGE (~320 flip-flops), introduces non-standard compiler calling conventions (__attribute__((interrupt("CLIC")))), and uses a memory-mapped trap vector table (mtvt) that breaks standard upstream GCC/LLVM toolchains.

This research proposes an alternative: an In-Core, Tightly-Coupled Zicsr Interrupt Subsystem for the 5-stage RV32IM RISC-V core. By consolidating pulse-to-level capture (irq_gateway.v), 4-level preemption, and priority evaluation (irq_arbiter.v) directly within the core's native Machine-mode CSR space (0x7C0–0x7C2), the design achieves:

  • Zero Interconnect Bus Contention: 100% of claim, auto-clear, and threshold operations occur across internal pipeline sidebands. Zero bus transactions are issued for interrupt servicing.
  • Deterministic 6-Cycle Hardware Entry: Standard vectored dispatch via mtvec with zero-cycle hardware auto-clearing at Writeback commit.
  • 100% Upstream Toolchain Compatibility: Fully compliant with standard RISC-V Privileged Architecture v1.12. Compiles out of the box with vanilla riscv32-unknown-elf-gcc.
  • Ultra-Low Silicon Footprint: Budgeted at ~1.29 kGE (~110 flip-flops), delivering a 4.4× reduction over PLIC and 5.3× reduction over CLIC.

3 · Baseline Architecture & RTL Defect Audit

In the baseline RISCFORGE design, interrupt qualification occurs combinationally in the Execute (EX) stage according to the following boolean qualification logic:

Execute-Stage Interrupt Qualification:
irq_accept_E = valid_E & irq_pending & ~new_exc_valid_E & ~exc_valid_E & ~stallMUL

When qualified, the pipeline flushes the IF and ID stages. State is committed atomically at the Writeback (WB) boundary by wb_trap_mret_commit_controller.v, writing mepc ← PC_E, setting mcause, clearing mstatus.MIE, and redirecting the program counter to mtvec.

Audited Defects in the Baseline RTL

  • Defect 1 — Transient Pulse Loss (Critical): Peripherals (SPI, GPIO banks, DMA done strobes) emit single-cycle pulses. In the baseline RTL, peripheral lines connect directly to the mip wire. If a pulse arrives while interrupts are globally disabled (mstatus.MIE = 0 during an active ISR), the pulse deasserts in 1 cycle and is permanently dropped.
  • Defect 2 — Fixed Priority Starvation of MTIP: The hardwired priority encoder in top.v evaluates: UART (19) > SPI (18) > I2C (17) > GPIO (16) > MEIP (11) > MTIP (7) > MSIP (3). Because the Machine Timer (MTIP, cause 7) is ranked below all peripherals, continuous UART or SPI traffic completely starves the system tick counter, breaking RTOS preemption.
  • Defect 3 — Inverted Priority Comparator: The hardware threshold comparator in execute_cycle.v evaluates (irq_cause_enc > mintprio[4:0]). It compares arbitrary cause IDs rather than true priority weights, improperly ranking cause 19 above cause 11 and cause 7 above cause 3, in direct violation of the RISC-V Privileged Architecture hierarchy.

6 · Deep-Dive Technical Inquiries

A. Is 4-Level Runtime Priority Feasible for 16 Sources?

Yes, it is mathematically and physically optimal.

  • Register Packaging: 16 sources × 2 bits per level = exactly 32 bits. This packs perfectly into a single standard RISC-V 32-bit CSR (mintlvl). Firmware can reassign the entire SoC's priority map with a single csrw instruction.
  • Timing & Delay: The decoding logic forms 4 parallel 16-bit masks. Finding the winning level requires four 16-input OR reductions followed by a 4-to-1 priority multiplexer. In a commercial 40nm or 130nm standard-cell library, total combinational propagation delay is < 0.4 ns (less than 3% of a 50 MHz clock period), introducing zero timing closure risk.

B. Contention Resolution: What Happens When 2+ Sources Share the Same Priority?

When two or more peripherals contend within the winning priority level, arbitration is resolved through one of two area-conscious strategies:

  • Option 1 — Static Hardwired Sub-Priority (Baseline: 0 Flip-Flops): Within each level, a fixed priority encoder selects the lowest source index. Area cost is 0 flip-flops and ~30 combinational gates. If UART (bit 0) and SPI (bit 1) both reside at Level 2, UART wins contention. Because priorities are runtime-configurable via CSR, firmware can elevate critical peripherals to distinct levels if starvation threatens.
  • Option 2 — Rotating Token Round-Robin (Anti-Starvation Extension: 4 Flip-Flops): A 4-bit token pointer (rr_ptr[3:0]) remembers the last serviced source. Ties within a level are resolved relative to rr_ptr. Upon acceptance, rr_ptr ← (winner + 1) mod 16. This formally guarantees that for N contending sources at level L, maximum waiting time is bounded:
    Maximum Waiting Time Bound:
    T_wait(i) ≤ (N_lvl − 1) × (T_ISR + T_overhead)
    Silicon cost is exactly 4 flip-flops (~22 GE in SkyWater 130nm) and ~120 GE of combinational mask logic.

C. The CLIC Problem: Why Does CLIC Break Toolchains While Ours Does Not?

The RISC-V Smclic draft specification incurs major toolchain and linker liabilities:

  1. Compiler Calling Conventions: CLIC introduces Selective Hardware Vectoring (SHV) and tail-chaining (mnxti), mandating non-standard function attributes like __attribute__((interrupt("CLIC"))). Upstream GCC and LLVM do not support this natively; developers must use vendor-specific compiler forks (Nuclei, Andes, or PULP GCC).
  2. Vector Table Architecture (mtvec vs mtvt): Standard RISC-V uses mtvec pointing to an array of executable jump instructions (j isr_handler). CLIC replaces this with mtvt, which requires a table of 32-bit memory addresses loaded across the data port, requiring custom linker scripts (.ld) that break standard RTOS BSPs.
  3. Core Bus Contention: CLIC's control arrays are memory-mapped to a core-local port, competing with the core's Load-Store Unit (LSU) for data memory cycles.

Why the Proposed Architecture is 100% Upstream Compatible: Our design retains the canonical vectored mtvec jump table and standard Machine-mode trap semantics. Interrupt handlers are written in standard ANSI C using vanilla __attribute__((interrupt)). Hardware auto-clear and preemption stack popping execute transparently on standard Writeback commit and mret execution. Custom CSRs (0x7C0–0x7C2) reside in the official user-definable range and compile in stock GCC via standard inline assembly.
