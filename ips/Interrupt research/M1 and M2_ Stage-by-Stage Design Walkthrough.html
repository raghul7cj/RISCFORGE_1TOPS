M1 and M2: Stage-by-Stage Design Walkthrough

RISCFORGE 5-stage RV32IM_Zicsr core · Stage 1 = what we have · Stage 2 = M1 optimization · Stage 3 = M2 optimization. Values marked "target" are goals to confirm by measurement, not results.

Stage 1 · Baseline: the trap and interrupt mechanism we have

Approach after corner-case analysis

  • Gate in hardware, accept at an instruction boundary: pending ∧ enabled, priority above mintprio, then global MIE; only then does EX consider it.
  • Detect early, act late: EX converts the instruction into a trap tag; only WB turns tags into traps, so there is one redirect point.
  • Precise by construction: older instructions retire, younger ones are flushed, and mepc = PCE so the interrupted instruction re-executes after mret.
  • Synchronous exceptions win over interrupts; the earlier tag is kept.

Stage 2 · Optimization 1 (M1): interrupt-transparent multi-cycle units

Approach after corner-case analysis

  • Abort, then replay: one strobe drops the operation without writing rd; mepc already points at it, so mret re-executes it. No checkpoint register to keep consistent.
  • One interface for divider and multiplier, so the bound covers every multi-cycle unit.
  • Progress condition: if interrupt inter-arrival time exceeds ISR time plus one divide, every divide completes; an optional retry-limit CSR covers storm cases.
  • Constant-time abort: the abort path takes the same cycles regardless of step counter or operands, which removes the latency channel described in [3].

Quantifiable outcome (targets, to confirm):
  • Worst-case entry with a divide or multiply in flight: L0 + up to Tdiv → L0 + a small constant c.
  • Latency distinguishability across operand classes: |t| < 4.5 where the baseline exceeds it.
  • Area: a few hundred gate equivalents (estimate). Replay cost: at most Tdiv per interrupted operation.
  • Proofs: replay equals uninterrupted result; latency identical for runs differing only in operands (bounded two-copy check).

Stage 3 · Optimization 2 (M2): bank-less background context save

Approach after corner-case analysis

  • Snapshot at commit, not at accept: at EX-accept, older instructions are still in flight; at WB commit they have all retired, so the register file is architecturally exact.
  • No second bank: the engine reads the register file in the background and stalls the handler only on real hazards (a write to an unsaved register, or an access to an unwritten stack slot).
  • Bounded by construction: the LSU keeps fixed priority, and a starvation counter forces a save slot every N cycles, so save completion has a proven bound.
  • Plain C handlers: vector stub is jal isr_c, software restore, mret. v1 keeps exit cost unchanged and reports it separately; hardware unstacking is a stretch.

Quantifiable outcome (targets, to confirm):
  • Entry to first C-callable instruction: L0 + S (about 33 cycles for a software-save baseline in [1]) → about 12 cycles or better, the Cortex-M4 reference in [1].
  • Added state: tens of flops (estimate) against a 512-flop 16-register bank; SRAM writes unchanged at 16 per entry.
  • Hazard stall cycles per ISR reported for five ISR types, including a load-heavy one.
  • Proofs: each stacked word equals the register at trap entry; interlock never lets an unsaved register be overwritten; entry and save completion within a stated bound.
