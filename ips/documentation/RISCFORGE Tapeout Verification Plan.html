Executive summary

The design under test is the RISCFORGE SoC subsystem: a 5-stage RV32IM_Zicsr core with direct ISRAM and DSRAM paths, a 2×3 AXI-Lite crossbar shared with the SPI-flash bootloader, an AXI-Lite→APB bridge and six APB peripherals (I2C, Timer 0, UART, GPIO, SPI, Timer 1). The plan layers nine methodologies so that every class of bug has one owner level and one golden reference. SV OOP unit benches cover micro-architecture. UVM covers the protocol-heavy blocks and the SoC fabric. RISCOF and riscv-dv with Spike cover the ISA. Bare-metal C, directed and random, covers the integrated datapaths. FPGA emulation covers long software runs, and equivalence checking, GLS, CDC/RDC and DFT cover the netlist.

One finding changes the order of work. The interrupt path is not yet ready for riscv-dv and Spike. Three of the five connected interrupt sources are single-cycle pulses feeding an mip that does not latch, the priority order is the reverse of Spike's, and several mandatory CSRs are missing. Six small RTL changes, R1–R6 in §10, should land before the co-simulation is built. That way the verification environment is built once, against the final architecture.

Item 10 in one paragraph

The current interrupt architecture works for directed tests of the level-type sources (UART, I2C). It does not yet work reliably for peripheral interrupts in general, or for riscv-dv + Spike. Timer 0 compare, SPI events and GPIO (in its reset-default edge mode) produce 1-cycle pulses. A pulse that arrives while EX holds a bubble, while the divider stalls, or while mstatus.MIE = 0 is lost. Spike also orders simultaneous interrupts differently, cannot enable mie[31:16] without a patch, and does not know CSR 0x7C0. The main integration reference is lowRISC Ibex's riscv-dv + Spike lockstep co-simulation, because Ibex uses the same fast-interrupt layout at mip[16+].

Core under test

  • RV32IM + Zicsr, M-mode only, in-order 5-stage with forwarding and hazard unit
  • Precise traps: accepted in EX, committed at WB (wb_trap_mret_commit_controller)
  • 16 fast local interrupts at mip[31:16] plus MTIP/MEIP/MSIP; custom threshold CSR mintprio (0x7C0)
  • Multi-cycle MUL/DIV stalls EX; mtvec direct mode only

Fabric & peripherals

  • Direct ISRAM fetch and DSRAM load/store; only MMIO crosses AXI (hybrid_mem_interface)
  • 2×3 AXI-Lite crossbar shared with the bootloader (privilege-gated ISRAM writes)
  • AXI-Lite→APB bridge, six slots; SPI muxed between bootloader and CPU
  • Cold boot (SRAM clear + flash load) and warm boot (soft_rst_ni, SRAM retained)

1SV OOP unit benches

This is the fastest tier. It runs on every change (xsim, Verilator or VCS) and builds on the existing class-based work: the module plan in modules_verificaction_implementation_plan.md and the commit_* classes in tb_sv_oop_csr_exc. Every bench has the same shape: transaction → driver → monitor → scoreboard with a reference function → covergroup. Each bench ships three sequence flavours: directed, constrained-random and corner.

2UVM block & SoC environments

UVM has two jobs. At block level it verifies the protocol-heavy IP in the configuration you actually instantiate. Third-party PULP, lowRISC and OpenCores IP counts as unverified until it has been checked in that configuration. At SoC level it is the shell that hosts the pin agents, bus monitors, IRQ monitor and the co-simulation scoreboard. Run UVM on VCS or Xcelium; keep xsim for smoke runs.

Register model (RAL): one source, three outputs

Describe every register once and generate the UVM RAL, the C header used by firmware, and the register documentation from it. GPIO already has lowRISC reggen output (gpio_reg_pkg, gpio_reg_top), so its description stays the source. For UART, SPI, I2C, the timers and the bootloader, write SystemRDL and generate with PeakRDL. Run uvm_reg_hw_reset_seq, uvm_reg_bit_bash_seq and uvm_reg_access_seq on each block. Registers whose reads have side effects must be excluded with NO_REG_TEST: UART RBR/IIR/LSR, SPI RXFIFO/INTSTA and GPIO W1C status.

Block environments

Build one environment each for apb_uart, apb_spi_master + flash, apb_i2c + EEPROM, gpio_apb_wrap, apb_timer, axi_lite_xbar (including both masters hitting the same slave), axi_lite_to_apb (six slots plus holes) and bootloader (flash images, reset modes, bad images). The existing directed benches (tb_axi_lite_xbar.sv, tb_axi_lite_to_apb.sv, i2c_thorough_tb.sv, tb_apb_uart_thorough.sv, tb_gpio.sv, bootloader_tb_all_testcases.sv, apb_timer-master/tb) become the directed seed set. UVM adds randomisation, RAL and coverage on top.

SoC environment

At SoC level the firmware is the stimulus. UVM virtual sequences play the outside world: they respond on pins, inject UART bytes, toggle GPIOs and synchronise with firmware through the mailbox described in §6. Scoreboards chain end to end. An AXI transaction from the core LSU must appear as the APB transaction on the decoded slot, which checks address decode. That APB transaction must then appear as activity on the pins, which checks the data.

Protocol assertions everywhere

Bind AXI-Lite and APB SVA checkers on every fabric interface. Use the same properties in simulation and in JasperGold (ABVIP). The core rules: VALID holds until READY; no X on VALID/READY after reset; PENABLE follows PSEL by one cycle; PADDR/PWDATA stay stable through the access phase.

Exit: every block environment reaches 100% RAL coverage and hits all protocol covers, with 0 SVA failures and block code coverage per §9.

3RISC-DV random instruction streams

riscv-dv generates random, self-consistent assembly programs. Its value here is in the core's interactions: hazard mixes, trap entry and exit, and interrupt timing against the pipeline. Run it in two stages. 3a uses trace compare without interrupts and can start as soon as the RVFI port exists. 3b uses lockstep co-simulation with a random IRQ agent (§10). Run 3b at core level first, with top.v and a flat simulation memory, then at SoC level.

  1. Custom target riscforge. Copy target/rv32imc and edit riscv_core_setting.sv as shown below.
  2. Custom program generator. Extend riscv_asm_program_gen into riscforge_asm_program_gen. Replace the default interrupt handler's csrrc mip, which cannot clear hardware-driven bits, with a signature write (HANDLING_IRQ). The testbench IRQ agent drops the line when it sees that write. This is the Ibex pattern.
  3. Memory. At core level, use the 4 MB simulation memories (Instruction_Memory.v / Data_Memory.v outside SYNTHESIS). riscv-dv's default data regions and stacks do not fit a 32 KB DSRAM. SoC-level runs therefore need either a simulation-only enlarged SRAM parameter or reduced +instr_cnt, stack and region sizes.
  4. End of test. Pass +require_signature_addr=1 +signature_addr=<mailbox>. The testbench ends on TEST_RESULT; Spike ends on tohost.
  5. Trace. Convert the RVFI stream to riscv-dv's CSV format with a short script, then compare with instr_trace_compare.py against spike_log_to_trace_csv.py output (stage 3a only).
  6. Coverage. Run riscv-dv cov.py over the DUT traces to collect instruction × operand × hazard bins.

4RISCOF architectural compliance

RISCOF is the architectural sign-off against the Sail model. The flow already exists (verification/riscof, the riscforge plugin, Icarus). For tapeout it needs four changes.

  • One RTL source. Point the DUT plugin at the tapeout tree (ips/riscv_core/rtl) through a single filelist. Either retire the flat copy in rv32im_zicsr_5stage_exc_nointr or regenerate it from the same source by script, with a hash check. Signing off RISCOF on a drifted copy signs off the wrong design.
  • Exact WARL description. After R4/R5, the ISA and platform YAML must state the real behaviour: M-mode only, direct mtvec, misaligned accesses trap, the misa value, and SIE/MPP hardwired.
  • Coverage. Run RISCOF in coverage mode (ISAC with the CGF files) to see which architectural cover points the suites hit. Feed any holes to riscv-dv directed streams.
  • Second reference. Run the suites once with Spike as the reference as well as Sail. If the two model configurations disagree, fix that before building the co-simulation.

Suites: rv32i_m/I, M, Zicsr and privilege (misalign-*, ecall, ebreak, mtvec). Run them on every RTL change (< 30 min), and once on the synthesised netlist in zero-delay GLS. Exit: 100% pass with zero waivers against both references.

5FPGA emulation

Run the exact tapeout RTL at 25–50 MHz to reach cycle counts that simulation never will. FPGA emulation also rehearses silicon bring-up. It complements GLS; it does not replace it.

Build rules

  • Only the wrapper differs: fpga_top.sv with MMCM clock, reset synchroniser and button, IOBUFs (open-drain for I2C). sram_sp infers BRAM unchanged.
  • Core, fabric and peripheral files are byte-identical to the ASIC filelist. Record a hash list in every build log.
  • FPGA-only code stays under `ifdef FPGA. Close timing at the target clock in XDC.
  • Any Artix-7-class board fits: 64 KB of SRAM is a small fraction of its BRAM. Map UART to USB-UART, SPI to on-board QSPI or a flash PMOD, I2C to an EEPROM PMOD, GPIO to LEDs and switches.

Content & debug

  • Same ELFs as the §6 catalogue, with results reported over UART.
  • Random C (§7): 100k+ seeds from a host script, with checksums compared against Spike on the host.
  • Soak: 24 h of CoreMark + UART echo + GPIO interrupt storm + timer tick.
  • Boot robustness: 1000 reset cycles, alternating cold and warm.
  • ILA on the RVFI port, mip/mie, irq_accept_E and the AXI MMIO channel. Keep a 1K-entry retire ring buffer, readable over UART after a hang.

Exit: the whole directed catalogue passes on the board; 24 h soak with no hang and no checksum mismatch; 1000/1000 boots. FPGA does not prove ASIC timing, SRAM macro behaviour, X/reset behaviour or DFT.

6Bare-metal C directed tests

Every SoC-level test is a C (or assembly) program built by one toolchain. The same ELF runs on the RTL, on Spike and on the FPGA.

crt0.S disables interrupts, sets gp/sp, zeroes .bss, clears x1–x31, installs the direct-mode mtvec and calls main(). link.ld places .text in ISRAM and .rodata/.data/.bss, the stack and a 64-byte .tohost mailbox in DSRAM. elf_to_hex.py writes word-addressed little-endian $readmemh images; gen_flash_image.py packs the same content for the SPI flash model.

Mailbox convention

The .tohost section holds STATUS, TEST_ID, ARG and PUTC words. The testbench reads the address from the ELF symbol table, passes it as +MAILBOX_ADDR, and monitors writes to it. Spike terminates on the same symbol. For tests that need the testbench to respond (UART RX, GPIO input), firmware writes STATUS=READY and waits for the testbench to answer through ARG.

Reference walkthrough: IRQ-01, Timer 0 tick

  1. BootROM sets sp to 0x0002_8000 (top of DSRAM) and jumps to 0x0001_0000.
  2. crt0.S builds the C runtime and points mtvec at trap_entry (direct mode).
  3. The driver writes Timer 0 CMP = N and CTRL = EN | prescaler, sets mie.MTIE (or the FLI bit after R6) and mstatus.MIE, then writes STATUS=READY.
  4. The core runs a mixed ALU, DIV and MMIO-polling loop. The IRQ monitor logs the cycle irq_o[1] rises and the cycle irq_accept_E fires.
  5. On the trap, cosim checks mcause = 0x8000_0007 and that mepc equals the PC of the instruction that was in EX. The handler acknowledges the source (R1 W1C), counts the tick and executes mret.
  6. After K ticks the firmware writes PASS. The testbench requires K accepts, 0 lost pulses, latency within bound and no spurious traps.

8Peripheral datapath verification (SV TB + C)

This is the pattern already proven on UART0, SPI0 and I2C0 in datapath_verification/, formalised and extended. Firmware drives the peripheral through the real core and fabric. SV models sit on the pins. Three checkpoints must agree:

  • Bus: the AXI and APB monitors see the right access at the right slot.
  • Register: the RAL predictor mirrors every write and checks every read.
  • Pin: the protocol monitor decodes the wire traffic, and the scoreboard compares it with what firmware sent or expected.

10RISC-DV + Spike integration & interrupt verdict

Main integration reference

lowRISC Ibex: dv/uvm/core_ibex (riscv-dv integration, IRQ agent, signature handshake) and dv/cosim (Spike lockstep over DPI), built on lowRISC's riscv-isa-sim fork. Ibex is the closest match to RISCFORGE: an in-order RV32 core with machine-mode traps and 15 fast local interrupts at mip[30:16], the same layout RISCFORGE uses at mip[31:16]. The riscv-dv target/ and user_extension/ hooks, the RVFI specification and OpenHW's core-v-verif are secondary references.

Integration steps

  1. RTL: RVFI retire port (R2). Behind `ifdef RVFI, carry PC and instruction to WB and expose rvfi_valid, order, insn, trap, intr, pc_rdata/pc_wdata, rd_addr/rd_wdata, mem_addr, mem_rmask/wmask, mem_rdata/wdata and CSR mip/mcause/mepc. The same port serves trace compare, lockstep cosim, coverage, the FPGA ILA and, optionally, riscv-formal.
  2. Spike. Start from lowRISC's fork, which already supports a fast-interrupt mip/mie layout. Add CSR 0x7C0 and its threshold gate in take_interrupt. Configure M-mode only, the RISCFORGE misa and direct-only mtvec. On upstream Spike the mie write mask covers only the standard bits, so mie[19:16] can never be set without the same patch.
  3. Cosim library (C++ over DPI-C). Use Ibex's cosim.h / spike_cosim.cc as the template. On each retire, call step() with rd, wdata, PC and sync-trap. Before each step, call set_mip(). For each MMIO access, call notify_dside_access() so Spike uses the DUT's load data for 0x4000_xxxx. Sync mcycle from the DUT; cycle counts are not architectural. ISRAM/DSRAM load from the same ELF; the MMIO range belongs to the DUT.
  4. riscv-dv. Use the riscforge target and program generator from §3. The core-level IRQ agent asserts fast_irq_i / timer_irq_i as levels, holds them until the handler's signature write, and in a second mode fires single-cycle pulses to prove R1.
  5. SoC level. Remove the IRQ agent; the real peripherals drive the lines, stimulated by UVM pin agents. Cosim still checks the core's architectural reaction, while the pin scoreboards check the peripherals.
  6. Runner. One flow, in the style of riscv-dv's run.py: generate → compile → RTL sim with cosim → coverage → triage, with every seed recorded.

Who checks what

Spike checks the core's architectural behaviour: which interrupt it takes and when that is allowed, mepc/mcause, handler effects, and MMIO data as software sees it. Spike does not model the peripherals. Peripheral correctness belongs to the UVM pin scoreboards and the RAL. Spike MMIO plugins are useful for firmware development without RTL, not for sign-off.

Verdict: does the current interrupt architecture work for riscv-dv, Spike and peripherals?

Works today

  • mie masking and mstatus.MIE gating; mcause interrupt bit; precise EX accept and WB commit with front-end flush. This is exactly what an Ibex-style cosim expects.
  • Fast local interrupts at mip[16+]: the same layout as Ibex, so the lowRISC cosim pattern applies almost as-is.
  • UART and I2C interrupts are level-sensitive and cleared at the source, the right model for software and for Spike.
  • Direct-mode mtvec and trapping misaligned accesses match riscv-dv DIRECT mode and Spike's defaults.
