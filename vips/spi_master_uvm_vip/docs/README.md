# SPI Master UVM VIP

UVM-based verification environment for the PULP/ETH-Zurich `apb_spi_master` RTL.

The environment verifies the SPI master through its APB register interface and SPI pins using reusable APB and SPI UVM agents, constrained-random virtual sequences, a self-checking scoreboard, and functional coverage.

### APB Agent

The APB agent drives and monitors the DUT register interface.

The driver implements the APB SETUP and ACCESS phases and honors `PREADY` wait states. This allows the environment to verify DUT backpressure conditions such as:

- RXFIFO read while the FIFO is empty
- TXFIFO write while the transmit path is not ready

The APB monitor publishes register accesses to the scoreboard and coverage components.

### SPI Agent

The DUT operates as an SPI master, therefore the SPI agent behaves as a reactive SPI slave.

The SPI driver supplies response data to the DUT for read transactions and supports:

- Standard SPI transfers
- Quad SPI transfers
- Multiple chip selects
- Multiword bursts
- Command/address/dummy preamble timing

The SPI monitor reconstructs MOSI traffic generated by the DUT and sends completed transactions to the scoreboard.

## Scoreboard

The scoreboard performs end-to-end TX and RX data checking without hierarchical DUT probing.

### TX Checking

Words written through APB to `REG_TXFIFO` are queued by the scoreboard.

When the SPI monitor captures a completed MOSI transfer, the transmitted words are compared against the expected TXFIFO contents.

### RX Checking

Read sequences register the expected SPI slave response words using:

```systemverilog
spi_scoreboard::add_expected_rx_words()
```

The words later read from `REG_RXFIFO` through APB are compared against these expected values.

RX path:

```text
SPI slave response -> SPI RX logic -> RXFIFO -> APB read
```

TX path:

```text
APB write -> TXFIFO -> SPI TX logic -> MOSI
```

## Command, Address and Dummy Phases

The reactive SPI slave supports delayed response generation for transfers containing command, address and dummy phases.

The transaction contains a `preamble_symbols` field. Read sequences calculate the number of SPI symbols that must occur before response data begins.

```systemverilog
function automatic int unsigned compute_preamble_symbols(
    int unsigned cmd_bits,
    int unsigned addr_bits,
    int unsigned dummy_cycles,
    bit          quad
);
    int unsigned width = quad ? 4 : 1;
    int unsigned cmd_symbols;
    int unsigned addr_symbols;

    cmd_symbols  = (cmd_bits  + width - 1) / width;
    addr_symbols = (addr_bits + width - 1) / width;

    return cmd_symbols + addr_symbols + dummy_cycles;
endfunction
```

The SPI slave driver waits for these symbols before driving response data.

This supports flash-style transfers containing:

```text
CS assert
   |
   +-- Command
   +-- Address
   +-- Dummy cycles (when configured)
   +-- Data
   |
CS deassert
```

Both normal flash-read and fast-read transactions are included in the test suite.

## FIFO Corner-Case Verification

### Empty RXFIFO

An APB read is issued before SPI response data is available.

The test verifies that `PREADY` remains low while the RX FIFO is empty and that the APB transaction completes after received data becomes available.

### RXFIFO Full / Backpressure

The overflow test sends more words than the configured FIFO depth.

The test verifies:

1. FIFO occupancy reaches its maximum depth.
2. Receive-side backpressure occurs.
3. Existing FIFO contents can be drained.
4. Transfer resumes.
5. Remaining words are received correctly.

## Software Reset

The reset test asserts the software-reset control during an active transfer and verifies RX FIFO clearing.

The current RTL contains:

```systemverilog
input logic spi_swrst, // FIXME Not used at all
```

in the SPI controller. Therefore software reset clears the FIFO state, but controller return to `IDLE` is not currently enforced through `spi_swrst`.

This is tracked as an RTL limitation rather than a scoreboard failure.

## Constrained-Random Verification

Random transactions exercise combinations of:

- Standard read/write
- Quad read/write
- Clock divider values
- Chip-select selection
- Command length
- Address length
- Dummy cycles
- Burst lengths
- Random 32-bit data

The number of random transactions is controlled using:

```text
+NUM_TRANS=<number>
```

Simulation reproducibility is controlled through the simulator seed.

## Running

Simulation is controlled through `sim/Makefile`.

### Xcelium

```bash
cd sim
make xcelium TEST=spi_smoke_read_test
```

Flash fast-read:

```bash
make xcelium TEST=spi_flash_fast_read_test
```

Constrained-random test:

```bash
make xcelium TEST=spi_random_test NUM_TRANS=50 SEED=1
```

Complete regression:

```bash
make xcelium TEST=spi_regression_test NUM_TRANS=50 SEED=1
```

### VCS

```bash
cd sim
make vcs TEST=spi_smoke_read_test
```

Constrained-random test:

```bash
make vcs TEST=spi_random_test NUM_TRANS=50 SEED=1
```

## Coverage

Coverage collection can be enabled through the Makefile:

```bash
make xcelium TEST=spi_regression_test COV=1
```

Individual tests retain separate coverage databases, allowing the coverage contribution of each test to be inspected independently.

Coverage reports can be generated using the Makefile coverage targets.

## Current Verification Scope

The implemented environment verifies:

- APB register programming
- Standard SPI reads
- Standard SPI writes
- Quad SPI reads
- Quad SPI traffic through constrained-random testing
- Single-word and multiword transfers
- Command/address/data sequencing
- Dummy-cycle handling
- Flash read transactions
- TXFIFO-to-MOSI data integrity
- SPI-to-RXFIFO data integrity
- RX FIFO full/backpressure behavior
- Empty RXFIFO APB stalls
- Software FIFO reset
- Multiple chip selects
- Clock-divider variation
- Constrained-random traffic
- End-to-end regression checking

The following checks are not part of the current test suite:

- Directed interrupt verification (`INTCFG`, `INTSTA`, `events_o[0]`)
- Dedicated directed quad-write test
- Controller reset-to-IDLE behavior through `spi_swrst`
- APB and SPI protocol assertions
- Dedicated negative tests for illegal command/configuration combinations
- Final functional/code coverage closure

## SoC Integration

The verification environment operates at the native boundary of the SPI peripheral:

```text
APB <-> apb_spi_master <-> SPI
```

At SoC level, the SPI master may be connected behind an AXI-to-APB bridge. AXI protocol verification belongs to the interconnect/bridge verification environment rather than this SPI IP-level environment.

The APB agent can be reused in passive mode during subsystem or SoC verification to monitor transactions reaching the SPI peripheral while an AXI-side agent drives transactions through the SoC interconnect.

This keeps the SPI verification environment reusable at both IP and subsystem level without adding AXI-specific dependencies.
