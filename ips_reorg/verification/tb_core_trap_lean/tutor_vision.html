CSR & Trap Verification — Part 2

Tutor vision & progress map · RISCFORGE 1TOPS SoC · target DUT: riscv_core/rtl/riscv_core.v

1. The Big Picture — Why Part 2?

Part 1 verified the CSR register file in isolation (124/124 checks, 100% block/expression coverage). It proved the registers behave.

Part 2 verifies the whole pipeline's commitment to traps: when an exception/interrupt fires, does the core correctly squash in-flight work, record mepc/mcause, redirect PC to mtvec, clear MIE, and later resume via mret — with zero ghost stores?

This is the hardest correctness property of a CPU. It can't be checked by unit tests alone — it needs the pipeline, memory, and CSR state observed together.

2. Architecture — What We Built

flowchart LR subgraph DUT["DUT: riscv_core (top.v)"] IF[IF] --> ID[ID] --> EX[EX] --> MEM[MEM] --> WB[WB] CSR[csr_regfile] --- WB HU[hazard_unit] --- IF end IMEM[(IMEM SRAM\nresponsive model)] <--> IF DMEM[(DMEM SRAM\nresponsive model)] <--> MEM IRQ[IRQ Generator\nMSIP/MTIP/MEIP/fast] --> DUT TB[TB Driver\nprograms + scoreboard] --> IMEM TB --> IRQ SVA[SVA Library\ncore_pipeline_sva\ncore_stage_sva] -. observes .-> DUT COV[Functional Coverage\nmcause / preemption /\nvectored vs direct] -. observes .-> DUT style DUT fill:#eef,stroke:#88a

The DUT is driven by legal programs loaded into a canonical synchronous SRAM model. An independent scoreboard predicts retirement. SVA observes pipeline state — never the expected ISA results.

Lean principles

  • Max 1–2 files read per task (routing map first).
  • Shared SVA written once, reused 4× (D/E/M/W).
  • Memory model is canonical & reusable (Verification/lib/memory).
  • Scoreboard freezes predictions before reset release.
  • Legal programs support overwrites — not just NOP loops.

Key invariant

  • mepc = exact faulting/interrupted PC.
  • mtvec redirect cycle-exact (direct & vectored).
  • Pipeline flush squashes IF/ID/EX/MEM — no ghost RF/DMEM stores.
  • mret restores MIE/MPIE and resumes cleanly.

4. The Open Finding — F02-WB-01 (Tutor Explanation)

What happened: Under a 1- and 3-cycle memory wait, the core kept asserting the physical GPR write-enable every cycle while WB retirement was stalled. The written value was identical each time.

Why it matters: This is duplicate write attempts, not data corruption — but the contract is ambiguous: must RF writes be commit-qualified (only on actual retirement), or is idempotent replay acceptable?

Why we didn't "fix" it yet: It's a design-contract question, not a bug fix. Changing the RTL or relaxing the checker would hide the ambiguity. We preserved both outcomes (ordinary stream + NOP-before-store fixture) and recorded waveform evidence.

Decision needed before F1: Pick commit-qualified vs. idempotent-replay, then encode it as an SVA invariant. Everything downstream (trap squashing, ghost-store checks) depends on this answer.
