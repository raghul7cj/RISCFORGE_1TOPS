1. Scope and status

This page plans and records verification of the RV32M multiplier and divider: rv32m_unit with its rv32m_mul (Booth radix-4, Dadda tree, three registered stages) and rv32m_div (non-restoring, iterative) sub-blocks, and how the unit stalls the pipeline. Status in one sentence: EXISTS there is no dedicated unit testbench for these modules anywhere in the repository (a search outside riscv_core/rtl and the artefact folders finds no file that instantiates rv32m_*); the only retained evidence is an older RISCOF compliance report that lists the eight M-extension tests as passed, and one historical interrupt test that executes a single DIV.

Evidence boundary. The RISCOF report is dated 2026-06-03. rv32m_div.v and rv32m_unit.v were last modified on 2026-09-30, after the report. The tracker plans a RISCOF re-run at the final identity (ACT-011 in Verification/status/PHASE_STATUS.md); phase P1a (core trust) is NOT STARTED. Treat the M-extension compliance result as PASS for an earlier RTL state, not for the current files.

3. Corner-case operand matrix

Figure 1 lists the eight operand pairs that every operation must pass, with the expected result worked out by hand from the specification. It is the seed of the directed list; constrained-random vectors are added on top (RM-13). The two highlighted regions are where the result is defined by the specification and not by arithmetic, so a reference model written by copying the RTL would hide a bug there; the oracle must be written from the spec.

Two cases the matrix does not show but the plan includes (RM-14): a signed divisor of INT_MIN (its magnitude is 2^31, which the divider holds in a 32-bit register after negation), and a dividend of INT_MIN with any divisor other than -1. The RTL header comments record five divider defects that were found and fixed during development (rv32m_div.v:65-70,142,178-198); the same classes (sign handling, partial-remainder correction, op-flag snapshot) are what the random and directed sets must hit.

5. Check architecture

The unit is small enough to verify standalone with a clock and the ports of rv32m_unit (rv32m_unit.v:2-21), then re-checked inside the core by the lock-step flow. Figure 2 shows the unit-level harness. The reference model is deliberately written in a different style from the RTL: a plain SystemVerilog function using 64-bit signed and unsigned arithmetic for the multiplies and the specification rules for the divides, or a Python script that emits an expected-results file. The comparator checks the 32-bit result, rd_out and that valid_out is a single pulse. The latency monitor checks Figure 3.

6. How stalls and latency interact with the pipeline

The unit raises stall from three terms: the multiplier counter, the divider, and the accept cycle itself (rv32m_unit.v:85). In the core, stallMUL feeds StallF, StallD and FlushE in hazard_unit.v:170-171,192 but not StallE (hazard_unit.v:173, which follows only mem_stall_i). The EX stage substitutes the M result into ResultE and the destination tag into the write-back when m_valid_out is high (execute_cycle.v:293,329-331). A divide interrupted by an accepted interrupt is aborted through div_abort_o = irq_accept_E & stallMUL (execute_cycle.v:297).

Pipeline-level checks, each needing the full core and not the standalone harness:

  • No early commit. While stallMUL is high no younger instruction may retire (RM-13).
  • Exactly one start. start_M is derived from m_started, which clears when m_valid_out is high. The cycle the result arrives, the EX stage must advance and not re-issue the same instruction (RM-15). I did not find a test that observes this.
  • Flush interaction. FlushE includes stallMUL, so bubbles are inserted behind the M operation; the checks must confirm no bubble overwrites a pending write-back.
  • Interrupt abort. The interrupt path and the M unit share abort_i; rv32m_mul has no abort port, so a multiply already in its three-stage pipeline may still produce valid_out after the abort. OPEN Whether that can corrupt a register is not shown by any evidence I found; RM-17 exists to decide it. The interrupt plan Verification/MINTPRIO_INTEGRATION_AND_PREEMPTION_PLAN.md also lists MUL/DIV interruption as an unverified pipeline risk.

8. What this page does not claim

  • It does not claim the unit is correct. The latency numbers and the expected values in Figure 1 are derived from the source and the specification, not from a simulation.
  • It does not claim the RISCOF passes still hold on the present RTL.
  • It does not cover the Zba/Zbb or compressed extensions, which are not in this core.
