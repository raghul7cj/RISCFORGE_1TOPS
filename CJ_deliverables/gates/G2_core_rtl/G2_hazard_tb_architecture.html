Hazard testbench:
layered OOP architecture

A small SystemVerilog class-based framework for observing hazard decisions and pipeline behavior. It connects the current production RTL and provides clear places for the primary engineer to add tests, expected behavior, coverage and closure.

1. Two harnesses, one layering approach

Unit harness

Instantiates hazard_unit directly. It deals in settled input/output vectors and checks every current output port. It is the starting point for control combinations and forwarding selection.

Pipeline harness

Instantiates core top, its real pipeline and MDU. It supplies instruction/data-memory boundaries, IRQ/reset controls and passive stage snapshots. Temporal scoreboards are extension points.

3. Sampling without races

Combinational hazard unit

Drive a complete vector → wait the declared nonzero settle interval → capture inputs and outputs together → dispatch copies → acknowledge completion. The next vector cannot overwrite the one being checked.

Clocked pipeline

Drive boundary responses away from the consuming edge. Observe pre-edge controls and post-NBA stage state under one cycle identity. Use the implementation guide's exact sampling phases; do not treat a pre-edge sample as next-state data.

Never derive the oracle by copying DUT equations. A control signal can be asserted correctly while the pipeline loses an instruction. Future pipeline checkers must evaluate dynamic instruction identity, the actual operand value and accepted side effects.

4. Connected DUT boundaries

BoundaryContract
Unit hazard RTLCurrent stallMUL and mem_stall_i; forwarding A/B; StallF/D/E/M; FlushD/E/M/W. All declared inputs are connected.
Instruction memoryCore exports word-addressed SRAM signals. The harness must honor the synchronous address/data pairing and selected reset-PC/base mapping. Images belong to the engineer.
Data memoryCore request / write-enable / byte address / byte enables / data, with response data / stall / error. A level request is not automatically a new transaction every cycle.
Interrupts and resetConnected through owned boundary controls. No implicit choice between IRQ defer and abort/restart.
Pipeline observationRead-only stage/valid/control and WB-effect probes. Probe names are source-coupled and require review after RTL hierarchy changes.
MDUProduction MDU in the real-core harness. This skeleton supplies no MDU algorithm checks and no claimed abort or completion correctness.

An external MMIO effect can become irrevocable before architectural retirement. A future scoreboard must log request offer, acceptance/effect and instruction disposition separately. A core memory model does not establish the real bridge's cancellation behavior.

5. Ownership and honest results

Primary engineer: stimuli, bins/crosses, golden policies, functional checker content and closure decisions.
Framework: DUT wiring, data transport, timing, passive observation, lifecycle/error handling and maintainable extension APIs.

SKELETON_READY means the bounded plumbing path initialized and stopped. It does not mean hazard scenarios passed. An ordinary run with missing user functionality must terminate as incomplete/failure; a blank checker or empty sequence cannot produce a functional pass.

Counts from monitors are observations, not successful checks. A coverage subscription is an API, not implemented coverage. Keep compile/elaboration, infrastructure execution, simulation checking, coverage closure and system validation as separate evidence.

6. How to start working

  1. Read the unit guide and pipeline guide; build their filelists from the documented directory.
  2. Use the explicitly named plumbing mode to check setup. Review the validation record for what was actually compiled or executed.
  3. Implement your user sequence/scenario and checker hooks. Keep each new scenario small enough to understand from its log and waveform.
  4. Add your coverage subscriber and choose semantic sampling events. Retain reachability/exclusion decisions with the bin inventory.
  5. Run bounded tests and preserve failures. Set your own reviewed closure criteria before claiming completion.

The reviewed verification plan and parent amendments describe future scenario obligations. Their candidate bin counts are planning material; this implementation does not claim to fill them.

7. Current scope and maintenance rules

The delivered work is a connected layered skeleton. Advanced reference interpretation, pipeline token conservation, functional hazard checks, stimulus campaigns and coverage closure remain explicit user work. Policy-sensitive cases need an agreed IRQ and memory-effect contract before expected behavior is frozen.

  • Keep production RTL unchanged when extending the bench. Add source-coupled probe changes in the adapter, with a comment explaining the mapping.
  • Use one owner per driven signal; avoid hidden background drivers and normal-flow hierarchical forces.
  • Copy published class objects; never let a later transaction mutate an earlier sample.
  • Use bounded waits and name every diagnostic with a sample/cycle ID.
  • Prefer short classes with one responsibility and explanatory concurrency comments over an elaborate framework.
