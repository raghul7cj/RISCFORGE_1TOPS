Core Lock-Step and ISA Compliance

How Rev B checks the core two ways: per-instruction lock-step against an independent instruction-set simulator (section 16), and ISA compliance by signature comparison (section 17). The page explains the three named configurations, what is compared, how interrupts are replayed, and why neither mechanism substitutes for the other.

2. What each mechanism answers

  • Compliance asks whether the core implements RV32IMZicsr as specified. It compares a signature over a fixed memory region against the Sail C reference. It reports that a run diverged, never where.
  • Lock-step asks whether the core and an independent model agree instruction by instruction on the same binary. It localises the first divergence by commit ordinal.
  • A green compliance report with a lock-step failure is coherent: the core implements the ISA but mis-executes this program, which points to a timing or hazard defect. CO-12 forbids either report standing in for the other.
  • Neither covers interrupt delivery (Rev B section 13): Spike models architectural M-mode delivery, not the deployed gateway and arbiter.

5. Compare set, tolerance and trap modelling

Table 16.4 lists twelve items. Ten are compared with tolerance zero, per committed instruction in retirement order:

  1. retired PC; 2. retired instruction word; 3. register write (destination and value); 4. CSR read value; 5. CSR write address and value; 6. privilege fields (MPP, MIE, MPIE; misa once at reset); 7. trap entry (interrupt flag, cause, mepc); 8. MRET and the CSR values it installs; 9. memory access stream (address, direction, size, data, byte mask); 10. instruction-fetch stream.

Two items are removed from comparison because Spike cannot produce them: 11, shadow-stack depth and contents (the 2-deep stack is a DUT feature, so its silent drop at depth 2 must be caught by an assertion, not lock-step), and 12, cycle counts. A third category, "differs for a documented reason", is forbidden: it is a defect to raise. No field is masked and an X is a failure.

The DUT's retire stream does not exist as a port: the core exports one debug output (Rev B cites top.v:31). Each row is assembled by the testbench from hierarchical references. This is acceptable in RTL simulation (D-049) and is why ISS-14 is registered with "executable: no".

Trap normalisation: the DUT encodes the interrupt flag as bit 5 of a 6-bit internal cause, not as mcause bit 31, so both sides are reduced to a 1-bit flag and a 5-bit cause. mtval is compared only where the DUT marks it valid (never for interrupts). The faulting instruction's memory request is suppressed in the DUT and not issued by the ISS, which is why item 9 is taken on the commit log.

7. DUT-sourced interrupt timing

Binding rule ISS-B1: the interrupt schedule given to the DUT and to the ISS is the same file, and that file is the DUT's own observed behaviour, never the generator's assumption. A generator cannot know when the DUT will accept an interrupt (acceptance depends on a valid execute slot, no competing exception and the multi-cycle state), so a generator-sourced schedule would measure the generator.

  1. Record phase. Run the DUT in CFG-S with the injector driving only the arbiter inputs; collect one record per event (Table 16.6). At least one record is required (ISS-16).
  2. Reproducibility gate. Repeat at the same run identity; the file must be byte-identical and non-empty (ISS-7). If not, the flow stops.
  3. Replay phase. The same file raises each mip bit in the ISS at the recorded commit ordinal. Ordinal k is the accepting instruction, never its successor; an off-by-one is an ISS-6 failure.
  4. Run phase. The DUT runs with no file-driven forcing; the graded run's interrupt sequence must equal the file (ISS-6).
  5. Legality gate. ISS-8: mip bit in {7, 16, 17, 18, 19, 27}, class in {0, 1, 2}, ordinals strictly increasing. Any mip[20] to mip[26] is a harness defect.

The replay can only fix what Spike models. Edge capture, class arbitration, the pre-emption gate, the clear strobe, the divider abort on pre-emption and the shadow stack are scored by the interrupt-family checks (IC-n), not by ISS-n. Interrupt-bearing ISS checks are therefore valid only for the single-pending, no-pre-emption case; the plan states this instead of reporting a partial cross as an ISS pass.

8. Random instruction stream

riscv-dv (SPECIFIED; pinned commit TBD(D-051); Rev B reports it absent from the repository) supplies instructions only and never interrupt timing. Binding categories (knob names resolved against the pin):

  • Class mix uniform over six classes (ALU, memory, branch/jump, multiply, divide, Zicsr/system), because uniform over instructions would under-weight divide and CSR by about two orders of magnitude.
  • Illegal-encoding generation OFF; misaligned generation ON with addresses held inside DSRAM so misalignment is architectural, not an SoC access fault; interrupt generation OFF unconditionally.
  • Seed derived from RTL hash, filelist hash and run index; memory legality filter against the deployed map; termination on the CFG-S tohost address.
  • CFG-S boots only 64 instruction words and 0 data words (D-052), a hard bound on generated length there; longer programs run in CFG-C and the manifest records which.

Nine pipeline states (S1 bubble, S2 ALU, S3 load-use, S4 multiply, S5 divide, S6 branch taken, S7 CSR write in flight, S8 synchronous exception, S9 MMIO in flight) cross three classes (0 Background, 1 Stream, 2 Real-Time).

10. Exactly-once MMIO across an interrupt

Finding 30. Four countable side effects make "exactly once" a number: MMIO-1 UART transmit write (characters on SOUT), MMIO-2 GPIO toggle (parity of gpio_out; the only discriminating register, since set and output writes are idempotent), MMIO-3 I2C command with start bit (START conditions on the pins), MMIO-4 Timer 0 compare (interrupt acceptances, counted as rising edges of the commit-interrupt strobe). Injection points include the store in execute, memory and writeback stages, after the APB ready handshake, and immediately after the gateway clear strobe.

A scenario passes only if both oracles report exactly one: the ISS access stream (strong, independent) and a per-peripheral side-effect counter (weak but necessary, since the ISS cannot see a character on a pin). Negative cases: N-A zero times (a flushed store still reaches the fabric), N-B twice (even parity or count 2 after a re-assert), N-C reordered (two APB transfers on the slot), N-D an unflushed younger store. All are CFG-S only; CFG-F has no side-effect models and CFG-C has no MMIO.

11. ISS access stream as intent oracle

Finding 31. The path scoreboard starts at the core load/store unit and has no independent statement of what should be on the bus for firmware traffic. The ISS commit log supplies it: one record per committed memory instruction, matched strictly in order and one-to-one against the DUT stream at the same point, comparing address, direction, size, data and byte mask at tolerance 0. A DUT access with no ISS record is spurious; an ISS record with no DUT access is dropped. The match is in-order, not set equality, because a reordering defect can satisfy a set comparison. The core issues one request at a time and the crossbar allows one outstanding transaction, so one-to-one matching suffices; a configuration with more outstanding requires a key-based window. Scope: core-originated accesses only (bootloader traffic and fetches are excluded and recorded in the manifest). The ISS must never be fed the DUT's observed stream.

12. Unreachable contention bins

The crossbar's two masters, the core and the bootloader, are never both active: the core is held in reset for the whole image load and the bootloader issues nothing after its terminal state. So contended forms of FP-3, FP-11, PATH-0005 and PATH-0006 are reachable only in CFG-F. Closure rule (D-054): an exclusion record with four fields (rule, RTL locator, named owner, review date); the report prints hit / (total - excluded) with excluded = n; the status is UNREACHABLE-BY-DESIGN. A bin may not be closed by waiver alone, left unreported, or closed by a formal proof over an unreachable condition. Consequence: CFG-F must be run as part of sign-off (R-44).

13. ISA compliance: CFG-C and CFG-S

The counts are quoted from Rev B Table 6.4: 69 applicable (38 I + 8 M + 7 Zicsr + 16 privilege), 93 out of scope (27 C + 1 Zifencei + 65 K), 162 in the tree. The privilege 16 are 14 misalignment tests and 2 environment-call tests. G5 is evaluated as 69 of 69; 162 is an inventory figure only. "162 of 162" was wrong because the misa mask (I and M only) excludes C, Zifencei and K.

CFG-C (EXISTS)

Built from the rv32im_zicsr_5stage_exc_nointr tree compiled by riscof_riscforge.py with 35 entries (31 core-tree .v files, 2 .sv, 2 testbenches); reference model Sail C (config.ini); linker places text at 0x8000_0000. The filelist-identity defect is measured by Rev B: of 32 .v files, 20 are byte-identical to the integrated core, 9 differ (top, csr_regfile, execute_cycle, memory_cycle, fetch_cycle, wb_trap_mret_commit_controller, PC, rv32m_div, rv32m_unit) and 3 exist only in the compliance tree. So a green CFG-C report may describe a core that differs from the integrated one, and the identity check (CO-1) is a precondition, not a formality.

Pass criteria for CFG-C: applicable_failed + applicable_not_run == 0 over the 69; identity check reported with the 9 divergent files named and any divergence declared; CO-2 non-zero exit on failure; CO-5 report, suite identity and RTL hash archived together; CO-6 reference named as Sail.

CFG-S (SPECIFIED)

Five criteria, all conjunctive: S1 no failed or unrun test in the enumerated subset; S2 every access fault (mcause 5 or 7) attributed to one named error source; S3 no wild-address write; S4 the run booted (boot_done_o observed, subset non-empty); S5 the run terminated on the CFG-S tohost address, which is what proves it is not a silent second CFG-C run.
