Core interrupt path

How an interrupt line becomes a trap in the RV32IM_Zicsr core: which lines are wired into mip, how the gateway and arbiter choose a winner, what gates delivery, and how the trap and MRET return work. Written from the RTL files as they are now; for engineers writing firmware or interrupt checks.

1. Path overview

The whole interrupt path is inside the core; no external interrupt controller is in the path (top.v:204-245). That is a project decision, not a missing block: the PLIC and CLIC are not used, and the direct interface is chosen (decision and rationale, 13-channel map). Figure 1 shows it. Peripheral lines enter the gateway, the arbiter picks one winner and raises irq_pending, the EX stage converts the instruction it holds into an interrupt trap packet, and the packet is committed at WB by the same controller that handles exceptions (see core_hazards_csr_traps.html). 2. Sources wired into the core

The gateway vector is 13 bits: bit 0 is cause 7 (machine timer, MTIP) and bits 12:1 are causes 27:16 (irq_gateway.v:2). top.v:207 builds it as {fast_irq_i[11:0], timer_irq_i}. The SoC drives fast_irq_i with {4'b0, ...} followed by the twelve peripheral lines (RTL_SOC/riscforge_soc_subsystem.sv:1275-1287); the top four bits are zero. EXISTS

Lines that do not reach the arbiter.

  • fast_irq_i[15:12]: the SoC ties them to zero and top.v:207 uses only bits 11:0, so mip[31:28] is constant 0 (top.v:550). Their mie bits (31:28) are writable but have no effect.
  • ext_irq_i (mip[11], MEIP) and sw_irq_i (mip[3], MSIP) go straight into mip without passing the gateway (top.v:575-576, csr_regfile.v:217). The arbiter only looks at mie[27:16] and mie[7] (irq_arbiter.v:20), so these two can be seen in mip but can never cause a trap. The SoC ties both inputs to 0 (riscforge_soc_subsystem.sv:1289-1290); software can still set mip[3] by writing it (csr_regfile.v:211-217), which also never traps.
  • The bits of mip that come from the gateway read the gateway output pend_o, not the raw pin (top.v:550-551).
OPEN Rev B section 13 and the files disagree. Rev B 13.1 describes a gateway and arbiter six sources wide, says mip[20] to mip[26] are provably zero because the core drops mip[10:4], and describes a two-deep shadow stack with a depth-2 delivery gate. The current files are thirteen sources wide, wire causes 20 to 26, and contain no shadow stack or depth gate. irq_gateway.v, irq_arbiter.v, csr_regfile.v and top.v were last modified on 2026-10-29, and an irq_restructure verification folder from the same day exists. This page follows the files. The Rev B text appears to describe the state before that restructure; the plan has not been reconciled.

3. Gateway: capture regimes

The gateway keeps a registered copy of each raw line and a pending latch (irq_gateway.v:14-27).

  • Capture: (raw & event_mode) | (raw & ~raw_q & edge_mode). Event lines are captured in every cycle they are asserted. Edge lines are captured on a rising edge.
  • Latch: pend_q <= capture | (pend_q & ~clear_i). A capture in the same cycle as a clear wins, so a new event is never lost; further captures while already pending coalesce into one.
  • Output: for edge and event lines, the latch; for level lines (neither mode bit set), the raw line unchanged (:29-30). A level line therefore stays pending until the peripheral drops it, and the clear strobe has no effect on it.
  • Clear: clear_gateway_o is a one-hot pulse generated when an interrupt trap commits: cause 7 clears bit 0, causes 16 to 27 clear bit (cause - 15) (wb_trap_mret_commit_controller.v:80-92). The mode vectors are constants in top.v, not registers.

Consequences, EXISTS: a pending edge or event interrupt that is masked stays latched and fires when enabled. An interrupt is cleared only when it is taken, so a handler for a level line must silence the peripheral itself, otherwise the interrupt re-fires after MRET. The comment in top.v:210 states that GPIO software must deassert and rearm its output.

5. Gating by mie, mstatus.MIE and mintprio

An interrupt is offered to the pipeline only when all three hold: its pend bit is set, its mie bit is set (bit 7 for MTIP, bits 27:16 for the fast lines), and mstatus.MIE (bit 3) is set (irq_arbiter.v:20-21). The threshold mintprio is then applied to the winner's class. The EX stage adds the last condition: it must hold a valid instruction that carries no exception (execute_cycle.v:459). EXISTS

  • Trap entry clears MIE and saves it in MPIE; MRET restores it (csr_regfile.v:159-179). So by default no nested interrupt is taken inside a handler.
  • Nesting is software-managed. The header of top.v (lines 7-8) names mintprio (0x7C0) as the mechanism. Neither trap entry nor MRET changes it (csr_regfile.v:79-80). A handler that wants to be pre-empted by higher classes writes mintprio and sets MIE. mepc, mcause and the saved MPIE are single registers, so a nested trap overwrites them; the handler has to save them first.
  • No hardware nesting cap or shadow stack was found in the current RTL (no depth counter in the arbiter or the CSR file). Rev B describes a depth-2 gate and a two-deep stack; see the OPEN note in section 2. SPECIFIED by Rev B 13.5 only.
  • The RTL itself records an unverified ordering corner case: an interrupt may be accepted in EX using an old mintprio while an older mintprio write is still in flight and could commit first (csr_regfile.v:81-89). The comment lists options and says it is not implemented behaviour. OPEN

6. Taking the interrupt, and returning

Figure 3 shows the sequence when no memory stall is active.

  1. The arbiter raises irq_pending with an id and class. When EX holds a valid instruction with no exception, irq_accept_E is true (execute_cycle.v:459). That instruction does not execute: its register, memory and CSR write enables are cleared and it becomes a trap packet with cause {1, id}, mtval 0 and mepc equal to its own PC (:411-420,466-478).
  2. In the same cycle irq_flush_frontend clears IF/ID and ID/EX (top.v:309,327), removing the younger instructions. If a multi-cycle divide is running, it is aborted (div_abort, execute_cycle.v:297) and will restart after return.
  3. The packet moves through EX/MEM and MEM/WB. At WB the controller commits it as a trap: trap_valid, the redirect, the 1111 flush, wb_commit_irq (round-robin update) and the gateway clear (wb_trap_mret_commit_controller.v:64-92).
  4. csr_regfile writes mepc, mcause (bit 31 set), mtval = 0, MPIE = MIE, MIE = 0, MPP = 11. Fetch continues at the mtvec target (section 8).

Return. The handler ends with MRET. It is carried as a tag to WB; when it commits, wb_trap_redirect sends fetch to {mepc[31:2], 2'b00}, MIE is restored from MPIE, MPIE is set to 1, MPP to 11, and the pipeline is flushed (wb_trap_mret_commit_controller.v:65,103,128-132, csr_regfile.v:172-179). The flow diagram is Figure 6 on core_hazards_csr_traps.html. If the handler changed mepc the return goes there, and mintprio stays as the handler left it. EXISTS

7. Interrupt during a multi-cycle MMIO access

A memory-mapped access can hold the pipeline for several cycles through mem_stall_i: StallF, StallD, StallE and StallM are asserted and the instruction in MEM waits (hazard_unit.v:170-175). Figure 4 traces an interrupt that becomes pending while an MMIO load X is waiting in MEM and a younger instruction Y is held in EX. It is read from the RTL and has not been simulated.

OPEN Possible loss of an instruction when an interrupt is accepted during a memory stall. Facts read: (1) irq_accept_E has no mem_stall term (execute_cycle.v:459); (2) top.v ORs irq_flush_frontend into FlushD and FlushE after the hazard unit, so the DEF-001 gating in hazard_unit.v:192 does not cover it (top.v:309,327); (3) in ID/EX flush outranks hold (decode_cycle.v:273,305); (4) EX/MEM is held by StallM, so the trap packet built from Y is not stored (execute_cycle.v:389-409). On that reading Y leaves ID/EX with no packet, the instruction in IF/ID is cleared as well, and no redirect to Y's PC was found. The next valid instruction that reaches EX would then be taken, with its own PC in mepc, and Y would not be re-executed. This is the same class of fault as DEF-001. It has not been simulated, and no regression or retained evidence for it was found. It needs a directed test (an interrupt asserted while a stalled MMIO load is in MEM) before it is called a defect or cleared.
