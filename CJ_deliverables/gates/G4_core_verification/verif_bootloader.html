Bootloader verification

What boot checking exists in the repository today, what it has shown, what Rev B section 12 requires on top of it, and where the gaps are. The retained evidence shows the cold and warm happy paths pass; no failure-path, integrity or reset-during-boot test exists.

1. Testbench inventory

Five benches under bootloader/ and one SoC-level bench under RTL_SOC/. The unit benches that include the SPI master load an image (ebreak_combined.mem: 375 instruction words and 1,164 data words, 6,156 bytes) into the vendor S25FS512S flash model by backdoor writes, then check SRAM contents against the same golden words. All benches use a 10 ns clock.

4. Rev B 12 obligations

Rev B names check IDs BOOT-01 to BOOT-20, BOOT-S1 to BOOT-S6 and BOOT-N1 to BOOT-N9. In the text read for this page the IDs are defined only through the "Check" column of Table 12.2, Table 12.3 and the integrity table; BOOT-16 to BOOT-20 are given only by reference and no definition table was located. The wording below is therefore a paraphrase by state, and status means: EXISTS a stimulus and a check in the repository cover it; SPECIFIED Rev B requires it and nothing in the repository checks it; OPEN unclear or not yet determinable.

5. Boot scenarios

Figure 2 groups the scenarios by whether a test exists. Reset-related scenario IDs come from Rev B Table 11.7.

  • Cold and warm. Covered; see section 2. Rev B CT-5 asks for one of each reaching S_DONE.
  • Failure. Rev B requires each row of Table 12.3 as a directed test whose expected result is today's behaviour until the RTL changes land, then re-baselined. None is built.
  • Reset during boot. RS-12 (hard reset at any load state: load restarts, no partially loaded word survives, S_CLEAN_RELEASE not reached on the interrupted attempt) and RS-13 (hard reset in the 4-cycle hold) are new in Rev B and listed as executable today. Soft reset during a cold load (section 7 of the design page) is not in the scenario list. RS-11 (soft reset taking effect before the system reset releases) is expected to fail today.
  • SPI release ordering. BOOT-17 is the keeper of the rule that the SPI reset releases before the first APB access.

6. Boot cycle budget and fast-boot backdoor

Cycle budget

Rev B Table 12.4 estimates a cold boot of the deployed configuration at about 133,000 cycles: 30000 + 16384 x 5 + 64 x (320 + 8) + 7 = 132,919. The 5 and the 8 are planning defaults (decision D-027), not measurements, and the plan requires a directed measurement test to replace them. SPECIFIED

The 283-cycle gap between the formula and the SoC observation is plausibly the 320 cycles of command and address that the formula does not count, partly offset by the 8-cycle overhead guess; this reading has not been verified. The deterministic repeat (TC3) shows the cycle count is stable under identical stimulus. The first-instruction measurement Rev B asks for (from hard reset release to the first retired instruction at address 0) does not exist. OPEN

Fast-boot backdoor

Rev B 12.9 allows a backdoor that deposits the image into the SRAMs and releases the core directly, as the only affordable way to run large campaigns, and defines "equivalent" as a comparison of: SRAM content at release (all 16,384 words), the reset record at release, SPI master state, and the first retired instructions from address 0. Every check in BOOT-01..20, every row of Table 12.3 and every item of Table 12.2 is backdoor-ineligible; a green backdoor-only run counts as untested for them, and the manifest must carry a per-test boot mode. In simulation the default is a testbench-only deposit (D-028); a hardware load port would need one RTL change. SPECIFIED

Today: no backdoor loader exists, no boot-mode field is known to be in the run manifest (not checked), and no equivalence comparator exists. The benches use a backdoor read of the AXI memory model for checking only.
