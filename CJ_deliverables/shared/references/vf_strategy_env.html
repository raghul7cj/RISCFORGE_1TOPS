1. Strategy: weakest mechanism, independent oracle

Rev B 4 has two halves. The first is a selection rule: use the weakest mechanism that can detect the class of defect. A handshake rule is a protocol assertion, a correspondence rule is a scoreboard, a value rule is a reference model. Using an assertion for a value defect is, in Rev B's words, the most common reason a bug survives a regression: a legal handshake can still carry wrong data.

The second half is independence. A checker that reads the signal the stimulus drove, or a model derived from the RTL it judges, can only agree with the DUT. Rev B requires every model and checker to name an independence source, admissible only if it is a named artefact that exists in the repository, or a named external specification with a stated version, cited by a locator. Restating what the DUT drives, restating its arithmetic, or naming a document the repository lacks is not an independence source. SPECIFIED

Three Rev A defects are corrected by this rule (Rev B 4.1):

  • An assertion written against the RTL is not independent of the RTL. The repository cites no ARM AMBA release, so the protocol layer is judged against the pinned upstream pulp-platform implementation the fabric was taken from, not "the AMBA specification".
  • No device data sheet exists in the repository (no UART part number, no SPI, I2C or JEDEC version). Rev A rows that named data sheets as independence sources are replaced by what does exist.
  • The privileged ISA version is OPEN (TBD): no version string exists in the tree, so any L5 or L6 row carries a version obligation.

3. Verification environment

One rule defines the environment: everything that describes the design under test is generated from the canonical RTL at run time. No flow carries its own copy of the RTL, its filelist or its register offsets. Rev B calls this the highest-leverage item in the plan, because it removes the class of defect where a green report describes a design that is not the one being taped out. This is the intended state; it is not a claim about the repository today. SPECIFIED

3.2 Architecture of the environment

Figure 4 shows the pieces and how a run flows through them. The canonical RTL feeds generators, which produce the filelist for the testbench and the register header and linker script for firmware. Stimulus drives the DUT; monitors observe it; scoreboards and reference models judge; the reporter produces one verdict record; coverage and verdicts are kept in the artefact store. Three execution domains exist because the tools differ in capability (Rev B 5): an interactive domain for bring-up (Verilator, Vivado XSim, no bind, no countable coverage), a compliance domain (Icarus vvp through RISCOF, because the compliance DUT uses array-port connections the SoC-level simulators cannot elaborate), and a nightly domain where a full SystemVerilog simulator binds checkers into the fabric. Synopsys VCS U-2023.03 is the tool of record for coverage and is a licensed remote tool, not a local execution domain.

5. Stimulus plan

Stimulus comes from five sources, each with a declared target and a rule for what "covered" means; without both, stimulus volume is "an opinion" (Rev B 7). Directed stimulus proves that a specific sequence works; random proves the legal space contains no failure; fault injection proves the checkers are alive; software suites prove the system does something useful; compliance proves architectural conformance. Removing any one leaves a defect class unaddressed. Every run is configured by boot mode (cold or warm), plusargs and seed, which are the fields of section 4. Every target is derived from a rule in Rev B Table 6.5; none is a carried-forward Rev A number. Volumes that cannot be derived are tagged TBD(D-025) with a binding rule, and provisional floors are tagged ASSUMED(D-024). Boot modes: the run record's plusargs distinguish cold from warm boot. Warm boot today is triggered by an external soft_rst_ni, not by a watchdog (see the overview), so warm-boot stimulus is an external event.
