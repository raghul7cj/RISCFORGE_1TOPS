1. Introduction

This guide explains how to build the verification infrastructure for the SoC before writing the tests that use it. The order of work is C test programs first, then peripheral drivers, then interrupt service routines (ISRs), and finally a working application on the complete SoC. Test cases are deliberately out of scope: they can be derived later, or taken from your existing catalogue, once the infrastructure can run and judge them.

Guiding ideas

  • Firmware is the stimulus and the testbench is the judge. Software runs on the real core. The testbench only observes and checks.
  • Checks fire by themselves. A failure should name the property that broke, not send you reading a log.
  • Every check has an independent source of expected behaviour: an assertion, a register predictor, a pin model or an instruction-set simulator (ISS).
  • One ELF per test runs unchanged on RTL simulation, the ISS and the FPGA.
  • Build in thin slices. Prove each piece with a trivial program before adding the next.
  • Add models late. The register model, C models through DPI-C and ISS co-simulation come after the basic checks work.

Suggested tool roles: xsim for the daily inner loop, VCS or Xcelium for regressions, coverage and DPI-C co-simulation, Vivado for the FPGA build, and Jasper or VC Formal for small control blocks such as the interrupt arbiter. AI assistants, including the AMD Ross MCP servers for Vivado, fit well for drafting drivers, scripts and first versions of checkers. Every generated artefact must still pass the same checks and an independent review.

2. Unit and peripheral testing basics

Unit testbench

A unit testbench verifies one module. Its parts are a transaction, a driver that applies it, a monitor that observes the outputs, a scoreboard that compares them with a reference function, and a covergroup that records what was exercised. Sequences come in three flavours: directed, constrained-random and corner. The strength is speed and depth on small blocks such as the ALU, hazard unit or arbiter. The weakness is that the bench trusts the interface assumptions of its own model.

Peripheral testbench

A peripheral testbench wraps one IP with a bus agent (an APB master), a register model that knows reset values, access types and side effects, a pin model or protocol monitor on the external side, and an interrupt monitor. These parts are reused at SoC level, so write them as reusable components from the start.

What these levels cannot see

  • The real address decode and the bus ordering produced by the core's load/store unit.
  • Byte strobes and hidden reads generated by compiled C code.
  • Interrupts arriving at arbitrary points in the pipeline.
  • Reset and boot sequences across blocks.
  • Assumptions made in driver and ISR code.

3. SoC-level methodology

Firmware as stimulus

Tests are C programs compiled with GCC. The image is preloaded into ISRAM and DSRAM (warm boot) or loaded from a flash model by the bootloader (cold boot). The program runs on the real RTL and reports its result through a mailbox word in DSRAM that the testbench watches.

Observe and check in layers

The testbench taps the design at fixed observation points and checks each layer against an independent source. Lower layers are blamed first, because a protocol error explains many higher-level failures.

LayerWhat is observedExpected behaviour comes from
ProtocolAXI-Lite and APB handshakesAssertions
PathCore access to AXI transaction to APB transferScoreboard using the address map
RegisterPeripheral register reads and writesRegister predictor
Peripheral functionUART, GPIO, I2C, SPI, timer behaviour at the pinsPin models and protocol monitors
InterruptSource, pending, grant, accept, acknowledgeIndependent interrupt predictor
CPU stateRetired instructions, CSRs, trapsISS (Spike)
Firmware resultMailbox status, checksumThe test itself and host-computed values

First failing check

When a check fires, the failure reporter records the cycle, check ID, expected and actual values, and freezes the ring buffers that hold the last transactions of every monitor. It blames the lowest layer that failed first and marks later failures as downstream. The output is a one-page report with the last retired instructions disassembled, so a person reads one page instead of the full log.

Pass rule

A test passes only when the mailbox reports PASS, no checker failed, the checkers actually saw activity (no vacuous pass), no predicted event is left unobserved, and no timeout occurred.

4. Building the infrastructure

Build the eight steps in order. Each step ends with a proof: a small program or an injected fault that shows the step works. Do not start the next step until the proof passes.

Step 1. Toolchain, startup and mailbox

Pin the GCC version and flags (-march=rv32im_zicsr -mabi=ilp32), and make sure no library brings compressed or atomic instructions. Write the startup file (stack, .bss, .data, trap vector, call main), a linker script that places .text in ISRAM and .data, .bss, stack and mailbox in DSRAM, and a mailbox layout with status, test ID, argument, character output and error code. Produce the listing, symbol file and a pc map (PC to function and source line) from the ELF.

Proof: the same hello program prints through the mailbox on Spike and on RTL.

Step 2. Testbench shell and memory preload

Create the top module with clock and reset, a backdoor loader for the image into ISRAM and DSRAM, the mailbox address read from the ELF symbol, a per-test watchdog, and a boot-mode switch. Warm boot is the default; cold boot through the flash model is added once the bootloader is stable.

Proof: a trivial PASS program ends the simulation; an infinite loop trips the watchdog and reports the last PC.

Step 3. Monitors and transactions

Add passive monitors for fetch, retire, load/store, AXI-Lite (AW, W, B, AR and R as separate events), APB, the interrupt lines and the pins. Each monitor emits timestamped transaction objects on one shared cycle counter and keeps a ring buffer of the most recent ones. Write them as SystemVerilog interfaces plus small classes so they can become UVM agents later without a rewrite.

Proof: transaction counts match a known program, for example ten stores produce ten load/store transactions.

Step 4. Checkers and failure reporter

Bind protocol assertions on every fabric interface and add a path scoreboard: each core MMIO access must appear as one AXI transaction and one APB transfer on the slot given by the address map, with the same data, strobes and response. Add the reporter with first-fatal logic. Give every checker a fault-injection switch (for example, force one byte strobe) so you can prove it fires.

Proof: each injected fault is named by the correct check ID in the report, and every assertion has a cover that is hit.

Step 5. C test harness and register access layer

Provide macros for 32-bit volatile register access, test begin and end with ID and PASS/FAIL, check macros that write the error code, a cycle-counter timeout helper, and a panic handler. Generate address headers from the same address map the testbench uses. Use 32-bit accesses until sub-word MMIO is verified, because compilers emit byte and halfword accesses for narrow registers.

Proof: a reset-value sweep of one peripheral runs and the register predictor, once present, agrees with every read.

Step 6. Drivers and pin models

Give each peripheral a register struct, an init function, polled operations with timeouts and error codes, and a pin model with error injection (UART monitor, GPIO driver and monitor, I2C slave model, SPI flash model). Develop each driver against its pin model so the wire is checked, not only the register read-back.

Proof: one polled transfer per peripheral is verified at the pins.

Step 7. ISR framework and interrupt monitor

Write the trap entry that saves caller-saved registers, a dispatch table keyed by cause, and an unexpected-interrupt handler that fails the test. Fix the ISR rules: acknowledge, record, return, with no blocking calls. Add the interrupt monitor that logs raise, pending, grant, accept and acknowledge, together with an interrupt predictor written from the interrupt specification, not from the RTL.

Proof: a register-canary test shows no corruption across an ISR, and a timer tick test produces the exact expected count.

Step 8. Regression runner and triage

Create a manifest with test ID, source, boot mode, timeout and seeds, and a runner that builds, simulates and collects results. Every log starts with seed, git hash, ELF hash and RTL hash. Bucket failures by signature (check ID, PC, cause) and replay a failing seed with waveforms on.

Proof: a nightly run completes unattended, and a seeded failure produces exactly one report.

5. Developing drivers and ISRs on the infrastructure

With the infrastructure in place, each new peripheral follows one loop. Write a small C test using raw register access, extract the working sequence into driver functions, and run a polled test checked at the pins. When all checks are clean, add the interrupt-driven variant with its ISR and acknowledge, and confirm the interrupt monitor and predictor agree. Only then compose the application on top of the drivers. If any check fires, use the first failing check to fix the problem and rerun.

For a peripheral whose driver you must write from scratch: read the RTL register list, define the register struct, write init and a polled operation with a timeout, observe the wire, add the error cases, and look at one waveform to confirm the sequence. Third-party IP often differs from its documentation, so treat the pin model as the authority. An AI assistant can draft the driver from the register description; require that it passes the pin-level test and have a second, independent reviewer compare it with the specification.

6. Late-stage components

Add these after the basic checks are stable. Each one replaces a weaker check with a stronger independent one.

Register model

Keep one description per peripheral: address, width, reset value, per-field access (read-write, read-only, write-1-to-clear, read-clear, self-clearing) and side effects. Generate the C header, the SystemVerilog predictor table and the documentation from it; generate a UVM RAL from the same source when you reach the UVM stage. The predictor applies side effects (FIFO pop, W1C, read-clear), which a plain mirror cannot. Only peripheral and fabric registers belong here. CPU registers (GPRs, mstatus, mepc, mcause, mie, mip) are checked by the ISS comparison.

C models and DPI-C

Write a functional model in C when behaviour must be shared between the testbench and host-side unit tests, or when the expected value is awkward in SystemVerilog (CRC, UART frame generation, an interrupt predictor you want to reuse). Model register-level behaviour from the specification, not from the RTL. Import the functions into SystemVerilog with import "DPI-C", pass plain integers, keep state inside the model, and never consume simulation time in C. Watch for monitors calling a model twice for one side-effect read, and for state leaking between seeds.

ISS co-simulation

Add a retire port (RVFI style) behind an ifdef carrying PC, instruction, register write, memory access, trap and interrupt information. A DPI-C bridge passes each retire to a C++ adapter that steps Spike, configured for machine mode, rv32im_zicsr and your misa, and compares PC, register writes, CSR writes and traps. Spike does not model peripherals, so MMIO loads take the data the DUT returned. For interrupts, tell Spike which source the DUT accepted (pass mip sampled before and after the retire), and check separately in the interrupt predictor that the accepted source was legal and in the right order. Synchronise mcycle and minstret from the DUT, and start comparing at the first ISRAM instruction because Spike reserves the low addresses.

7. Debugging with the infrastructure

  1. Reproduce with the recorded seed and ELF hash, then shrink to the smallest program.
  2. Read the failure report before opening waveforms: check ID, layer, expected and actual values, last retired instructions.
  3. Look at the disassembly at the failing PC for access width, missing volatile, hidden reads and reordering.
  4. Write one hypothesis and one experiment that separates it from the next; change one thing at a time.
  5. When the cause is confirmed, add a regression test that fails without the fix and an assertion that would have caught it.

8. Carrying the infrastructure to the FPGA

The same ELF runs on the board. The mailbox output is replaced by UART output in the same PASS/FAIL line format, so one script parses simulation and board logs. Keep a retire ring buffer readable over UART after a hang and use ILA probes on the retire port, interrupt state and AXI MMIO channel. Two things differ and must be controlled: the clock-frequency constant used by every divider and timeout (one definition, shared by both builds), and the models replaced by real devices (flash, EEPROM, sensors), which must be checked against their datasheets.

Scope of this version: infrastructure methodology only. Test case derivation, coverage closure and sign-off are intentionally left for later versions that build on this infrastructure.
